威脅防護篇 - 單元 12：App-ID 應用程式識別

講師導言

前面的章節你已經會寫安全政策了，但規則裡那個 Application 欄位，到底是怎麼判斷出來的？ 這一章要拆開 App-ID：防火牆如何不看連接埠、直接認出「這是什麼應用程式」， 為什麼同樣走 53 埠，DNS 和惡意程式的 C2 回連會被分開處理， 以及當流量認不出來、或原廠推出新的 App-ID 時，你該怎麼處理才不會弄壞現有政策。 威脅內容檢查（Content-ID）留到第 13 章，解密留到第 15 章，這一章只在需要時提到它們。

Goals 本章學習目標

  • 說明什麼是「應用程式」，以及以應用程式為基礎的規則為何比以連接埠為基礎的規則更安全
  • 列出 App-ID 使用的識別技術，並依序說出它的運作流程
  • 解釋應用程式轉換（Application Shift），例如 web-browsing 轉成 facebook-base 再轉成 facebook-chat
  • 分辨相依應用程式與隱含應用程式，並知道在 Objects > Applications 查看
  • 使用 Application Filter、Application Group 與巢狀組合簡化規則，並分辨 application-default 與自訂服務
  • 以迭代方式辨識 unknown-tcp / unknown-udp 流量，並知道自訂應用程式與 Application Override 的取捨
  • 設定 App-ID 內容更新排程，並用 Review Apps、Review Policies 預先分析新應用程式對政策的影響

Concept 一、為什麼要用應用程式判斷

在 App-ID 的定義裡，應用程式（Application）是一個特定的程式或功能，它的通訊可以被標記、監看與控制。 同樣是 Google 的服務，Gmail、Google Hangouts 與 Google Calendar 各自是不同的應用程式；Microsoft SQL、Skype、BitTorrent 也各是一個。 App-ID 就是用多種技術，依「應用程式」而不只是「連接埠」來標記流量，標記結果再交給安全政策決定放行或阻擋。

🪪 生活化比喻：看證件，而不是看人從哪個門進來

  • 以連接埠判斷：警衛只管「從 53 號門進來的人都放行」。壞人只要從 53 號門走進來，一樣暢行無阻。
  • 以應用程式判斷：警衛檢查證件上寫的身分。證件寫「訪客 DNS」才放行，不管他走哪一扇門；冒牌的就攔下來。
  • 未知流量：沒有證件或證件看不懂的人，警衛會記下來，之後再決定怎麼處理。

同樣是 53 埠：DNS 與 C2 回連

教材用兩個例子對照傳統防火牆與 App-ID。第一個例子是 BitTorrent 偷走 53 埠；第二個更棘手：零時差惡意程式的 C2 回連也走 53 埠，連應用程式 IPS 都不一定認得。

比較項目 以連接埠為基礎的規則 以應用程式為基礎的規則（App-ID）
判斷依據協定與連接埠App-ID 識別出的應用程式（連接埠只是線索之一）
53 埠上的 BitTorrent埠對就放行BitTorrent 不是 DNS，被阻擋且留下紀錄
53 埠上的 C2 回連放行，管理員完全看不到C2 不是 DNS，被阻擋，且作為未知流量被偵測到
跑在非標準埠的應用程式看埠而定，容易漏判不論埠、協定或加密，都會嘗試識別
日誌可視性只知道「某個埠被允許」看得到實際的應用程式名稱
規則維護要自己研究並維護應用程式與埠的對應寫應用程式名稱即可，對應交給 App-ID

重點

App-ID 不是取代安全政策，而是替安全政策貼上更準確的標籤。規則怎麼寫仍然由你決定：標籤貼對了，規則才有意義（第 8、9 章的規則概念與 Application 頁籤仍然適用）。

踩坑：規則的 Application 欄位留著 any

如果規則的 Application 是 any，再搭配只看埠的服務設定，這條規則其實就退化成傳統的埠規則，App-ID 辛苦辨識出來的結果完全派不上用場。要享受應用程式識別的好處，規則的 Application 欄位要寫出具體的應用程式（或 Application Filter／Group）。

Operation 二、App-ID 如何運作與應用程式轉換

識別技術：多管齊下

App-ID 不是只靠一種方法，而是把以下技術組合起來，直到得出結論：

連接埠與協定

第一步先取出 IP 與連接埠，只作為初步線索。安全政策此時先以 application = any 判斷這條連線是否允許進來。

應用程式特徵碼（Signature）

依應用程式獨有的特性與交易特徵比對，同時能看出它用的是預設埠還是非標準埠。

SSL／SSH 解密

偵測到 SSL 或 SSH，且安全政策放行後，若有符合的解密政策才解密，再對解密後的內容重新套用特徵碼（解密設定見第 15 章）。

協定解碼器（Protocol Decoder）

用情境式特徵碼找出藏在其他協定裡的應用程式（例如包在網頁連線裡的即時通訊），也檢查協定是否合規，並支援 NAT 穿越與 SIP、FTP 這類協定的動態開洞。

啟發式分析（Heuristics）

對特別會躲的應用程式，特徵碼與協定分析都認不出來時，改用行為分析來判定。

App-ID 運作流程

簡化畫法，完整順序見第 1 章；實際封包處理在資料平面並行完成。

流程中的兩次政策比對

第一次比對時應用程式還不知道，所以先以 application = any 判斷「這條連線有沒有任何一條規則可能允許它」；第二次是 App-ID 識別完成後，用真正的應用程式再比一次。遇到 SSL 或 SSH 時，這次比對看到的應用程式是 ssl 或 ssh，放行後才會比對解密政策；解密後若應用程式改變，會再比對一次安全政策（細節以實機為準）。App-ID 會先識別出應用程式；整體流量處理的先後順序請看第 1 章的流程圖，解密的部分見第 15 章。

應用程式轉換（Application Shift）

同一個工作階段裡，應用程式可以中途改變。典型例子：使用者先用瀏覽器連上 Facebook，再開啟聊天功能。 流量從 web-browsing 開始，識別為 facebook-base，再轉成 facebook-chat。防火牆會隨著識別結果更新標籤；應用程式若改變，會再比對一次安全政策（細節以實機為準）。

版本差異：雲端交付的 App-ID（App-ID Cloud Engine）

  • 教材（PAN-OS 8.0 時代）的 App-ID 只來自內容更新中的資料庫，沒有雲端取得 App-ID 的概念。
  • 現行原廠文件有 App-ID Cloud Engine（ACE）：防火牆或 Panorama 可以從雲端下載「尚未有預先定義 App-ID」的應用程式的 App-ID，目的是不必等每月的內容更新。
  • 使用條件：需要 SaaS Security Inline 訂閱（Prisma Access 授權則已包含）、每台設備要有有效的裝置憑證、PAN-OS 10.1 或更新版本。
  • 它適用於被歸類為 ssl 或 web-browsing 的流量，不涵蓋私有或自訂應用程式；雲端交付的 App-ID 只能用在安全政策規則，其他類型的政策不能用。設定入口為 Device > Setup > ACE，並可搭配 Policy Optimizer 或 Application Filter 把它們納入政策。

Dependency 三、相依與隱含應用程式

很多應用程式不是單獨運作，會借用其他應用程式。這裡有兩個容易混淆的概念：

相依應用程式（Dependent）

  • 該應用程式要正常運作，另外還需要其他應用程式。
  • 教材範例：office-on-demand 相依於 ms-office365-base 與 sharepoint-online。
  • 你必須自己加規則放行這些相依的應用程式。

隱含應用程式（Implicit）

  • 許多常見應用程式會「隱含允許」它的上層（parent）應用程式。
  • 教材範例：允許 facebook-base，就隱含允許 web-browsing。
  • 不需要另外為上層應用程式寫規則。

怎麼知道誰依賴誰？

  1. 到 Objects > Applications，搜尋並點進該應用程式查看詳細資料。
  2. 在詳細資料中，找出它相依的應用程式（Depends on）與隱含使用的應用程式（Implicitly Uses）。
  3. 相依的應用程式，要確認有規則放行；隱含的則通常不必處理。

現行文件另提供 Policy Optimizer、建立 Application Filter 與 Resolve Application Dependencies 等方式，在建立規則時協助辨識相依關係；Applipedia 也能查詢應用程式資料。

踩坑：只放行應用程式本身，忘了它相依的應用程式

規則放行了 office-on-demand，使用者卻說「打不開」。原因通常是 ms-office365-base 或 sharepoint-online 沒有被放行。排查時看 Traffic 日誌是哪個應用程式被擋。另外別以為「隱含」可以放心不管：隱含支援並非涵蓋所有情況，如果防火牆來不及識別所依賴的應用程式，你仍然必須明確放行它。

版本差異：相依性的提示方式

教材（PAN-OS 8.0）只告訴你「相依應用程式需要自己加規則」，要自己到 Objects > Applications 查。PAN-OS 9.1 起新增「Resolve Application Dependencies」流程：建立規則選擇應用程式時，介面會顯示相依關係，可一併加入現有或目前的規則；Commit 時若有遺漏，會在 App Dependency 頁籤出現警告，點規則名稱就能補上。這個流程現行版本仍保留，實際畫面請以你的 PAN-OS 版本為準。

Objects 四、Filter、Group 與未知流量

Application Filter、Application Group 與巢狀

應用程式動輒上千個，規則不可能一個個列。教材介紹兩種物件，都能用在安全、QoS 與 PBF 規則裡：

物件 做法 特性
Application Filter
Objects > Application Filters > Add		 在 App-ID 資料庫中用條件篩選：依序是 category、subcategory、technology、risk、tags、characteristic 動態分組：之後新增、符合條件的應用程式會自動納入，所以用 Filter 放行時，新的 App-ID 也可能被一併放行
Application Group
Objects > Application Groups > Add		 管理員自己挑選應用程式（以及其他 Group／Filter）放進來 靜態清單，內容由管理員決定

Group 與 Filter 可以巢狀：Group 裡可以放 Filter，也可以放別的 Group，最後整組放進安全政策規則的 Application 欄位。 規則路徑：Policies > Security > Add > Application，可選單一 Application、Application Filter 或 Application Group。

版本差異：用標籤簡化規則

教材沒有提到的是，現行版本介紹了 Streamlined App-ID Policy Rules：以內容更新中隨附的應用程式標籤（tags）撰寫規則，不必每次有新 App-ID 就改政策；並可建立使用 New App-ID 特性、只比對最新內容版本新增 App-ID 的規則，先確保關鍵類別（例如驗證、軟體開發）不被中斷。這也是第五節的主題。

服務欄位：application-default 與自訂服務

規則除了 Application，還有 Service 欄位（Policies > Security > Add > Service/URL Category）決定「允許應用程式出現在哪些連接埠」：

Service 設定 效果 適用時機
application-default只允許該應用程式的預設連接埠；原廠建議搭配解密一起使用多數情況的首選
any應用程式在任何連接埠都符合，原廠提醒非標準埠上的應用程式可能代表有人在規避防護有明確理由時才用
自訂服務（Objects > Services）只允許你定義的協定與連接埠內部應用程式刻意使用非預設埠

教材流程：先到 Objects > Services 建立自訂服務，再到 Policies > Security 的規則中選用它。

踩坑：Service 欄位留 any，或沿用舊的 service-http／service-https

從舊防火牆搬過來的 web-browsing 規則，Service 常是 service-http 與 service-https，兩個埠都得開才能涵蓋明文與加密。改用 application-default，明文網頁只在 80 埠、SSL 加密只在 443 埠成立，範圍更精準。反過來，若 Service 設成 any，應用程式可以出現在任何埠，等於放棄埠這一層的限制。

Application Block Page

應用程式被安全政策規則阻擋時，網頁類的應用程式可以在使用者的瀏覽器顯示阻擋頁面，說明這次存取被擋的原因。 設定位置：Device > Response Pages > Application Block Page，可以選擇啟用或停用。

未知流量：unknown-tcp 與 unknown-udp

被允許通過、但 App-ID 認不出來的流量，會顯示成 unknown-tcp 或 unknown-udp（能辨識的則是 ftp、smtp、web-browsing 等）。 這類流量通常是：尚未收錄在 App-ID 的商用應用程式、內部或自訂應用程式，或潛在的威脅。Traffic 日誌中也可能看到 incomplete（三向交握完成但逾時前沒有資料）或 insufficient-data（有資料但封包太少不足以識別）。

日誌路徑：Monitor > Logs > Traffic，在 Application 欄查看 App-ID 識別的結果；規則則在 Policies > Security。這是一個迭代的過程，不是設定一次就結束。

控制未知應用程式的三種做法

自訂應用程式＋自訂特徵碼

Objects > Applications > Add，替內部應用程式定義特徵碼，之後可以放進安全政策，通常仍會經過 App-ID 與內容檢查（以實機為準）。

Application Override 政策

Policies > Application Override，以區域、位址、埠與協定直接指定它是哪個自訂應用程式。

安全規則直接阻擋 unknown-tcp／udp

最直接，但教材標註：可能阻擋比預期更多的流量。

版本差異：Application Override 的建議

  • 教材把 Application Override 當成與自訂應用程式並列的控制手段之一。
  • PAN-OS 10.1 起（含現行版本），原廠改為建議盡量避免：Override 會讓防火牆略過 App-ID 與第七層威脅檢查，改用較不安全的第四層狀態檢查。
  • 原廠建議的替代方式是建立帶特徵碼的自訂應用程式，或使用自訂逾時（custom timeouts），讓流量仍能在第七層被檢查；商用應用程式則向原廠要求新的 App-ID。
  • 10.0 以前的文件沒有這項警告，所以不同版本的說法不同，實務上請以你的版本與公司資安政策為準。

踩坑：看到 unknown 就全部阻擋，或用 Override 一勞永逸

未知流量裡可能混著內部系統、新應用程式，直接全擋會誤傷。比較穩妥的順序：先用暫時規則觀察、判斷身分，再決定是補自訂應用程式、向原廠提交封包，還是阻擋。至於 Override，它能解決「認不出來」，但同時讓該流量失去第七層的檢查，要把風險算進去。

Update 五、更新 App-ID 而不弄壞政策

App-ID 資料庫靠原廠的 Dynamic Updates 內容更新取得新特徵碼。問題在於：更新可能讓原本被某個大類別（例如 web-browsing 或 ssl）命中的流量，改被識別成一個新的應用程式，而那個新應用程式是否被允許，取決於你現有的規則。

項目說明
更新頻率新的威脅特徵碼與修改過的 App-ID 至少每週發布，常更頻繁；新的 App-ID 在每月第三個星期二發布（極少數情況會延後一兩天），讓管理員有可預期的時間窗口調整政策（頻率以原廠最新公告為準）
累積性最新的內容更新包含先前版本的所有特徵碼
授權只含應用程式的部分不需授權；同時含威脅特徵碼的完整 Applications and Threats 套件需要 Threat Prevention 授權（授權見第 3 章）
排程路徑Device > Dynamic Updates，在 Schedule 設定檢查頻率與時間
更新動作教材列出三種選擇：排程只下載、排程下載並安裝、手動下載並安裝
等待門檻（Threshold）新內容須釋出達一段時間後才安裝，避免偶發的問題更新；Applications and Threats 還可針對「新增或修改應用程式」的更新設定較長的門檻，爭取檢視政策的時間

版本差異：更新頻率與新功能

  • 教材畫的是「每週更新（Weekly updates）」。現行文件把它拆開：威脅特徵碼與修改過的 App-ID 至少每週，新的 App-ID 則是每月第三個星期二。
  • 較新的 12.1 版次另有 App-ID Update Safeguard（預設停用，在 Device > Setup > Content-ID 啟用）：新的或修改過的 App-ID 尚未寫進規則時，若它先前對應的 App-ID 全部被允許，就暫時沿用放行；只要有一個被擋，就維持阻擋。Previous App-ID 到下一次內容更新時就轉成新的 App-ID，不會一直沿用。是否有這個功能，請以你的版本為準。

安裝前的預先分析流程

Review Apps

  • 位置：Device > Dynamic Updates 的 Actions 欄（內容更新下載後即可使用）。
  • 新增與修改的 App-ID 分開列出，附完整細節。
  • 預期會影響整個網路的（例如 LDAP、IKE）會被標示，提醒你檢視政策。
  • 新 App-ID 有 Depends on（所依賴的特徵碼，被停用則連帶停用）與 Previously Identified As（安裝前這類流量被識別成什麼）。
  • 新 App-ID 安裝後預設啟用；想先不啟用，須在安裝前停用。

Review Policies

  • 位置：Device > Dynamic Updates 的 Actions 欄，也可以從 Objects > Applications（教材畫面）開啟。
  • 顯示新應用程式特徵碼對現有安全政策的影響：哪些規則會比對到新的應用程式。
  • 可以把待處理的應用程式加入或移出安全政策規則。
  • 安裝新的 Applications and Threats 內容時，可勾選 Disable new apps in content update，先取得最新威脅防護，準備好政策再啟用新應用程式。

兩種部署取向

原廠把組織分成安全優先（security-first）與任務關鍵（mission-critical）兩種取向，也可以依據點或部署類型混用。前者優先取得最新威脅特徵碼，後者優先維持應用程式可用。任務關鍵的環境，一般會把門檻設得較長，並為含新 App-ID 的內容另設較長的門檻，先在測試環境驗證再上線，給自己審查的空間。

踩坑：排程直接下載並安裝，卻從不看 Review Apps／Review Policies

某天某個重要應用程式突然連不上，往往是因為更新後它被識別成新的 App-ID，而你的規則只允許原本的舊標籤（例如 ssl 或 web-browsing）。排程只能解決「何時更新」，並不會替你檢查政策。更新排程設好之後，仍要持續處理每個內容版本帶來的新增與修改 App-ID。
