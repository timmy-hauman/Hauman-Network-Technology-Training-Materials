Palo Alto Networks NGFW 實戰課程

基礎篇 - 單元 4：組態管理、Commit 與日誌檢視

講師導言

如果你用過其他廠牌的防火牆，第一次在 Palo Alto 上改完設定、按下 OK，常會發現「怎麼沒有生效？」。 這不是故障，而是刻意的設計：你改的只是候選組態（Candidate），要 Commit 之後才會變成正在運作的執行組態（Running）。 這一章先把這條界線講清楚，再學怎麼預覽、驗證、多人協作、備份回復，最後學怎麼從日誌看出「剛剛到底發生了什麼事」。

Goals 本章學習目標

  • 分辨候選組態（Candidate）與執行組態（Running），並說出 Commit 時資料如何流向記憶體
  • 依序完成 Preview Changes、Change Summary、Validate Commit 與 Commit，並在 Tasks 追蹤結果
  • 在多位管理員同時作業時，選擇 Commit、Save、Revert 的範圍，並知道 Config lock 與 Commit lock 的差別
  • 說出 Save、Load、Export、Import 與版本回復各自的用途，並用 Config Audit 比對版本
  • 在 Monitor > Logs 找到對應的日誌類型，並用點選與語法組出過濾條件

Concept 一、Candidate 與 Running 組態

防火牆同時存在兩份組態： Running Configuration（執行組態）是目前正在生效的設定； Candidate Configuration（候選組態）是已經修改、但還沒 Commit 的設定。 換句話說，候選組態就是「執行組態的副本，再加上上次 Commit 之後尚未提交的修改」。

比較項目 Candidate 候選組態 Running 執行組態
狀態已修改，尚未生效目前正在生效
怎麼變動在 WebUI 或 CLI 修改設定（WebUI 按 OK 只是更新候選組態）只有 Commit 才會更新
重新開機後未手動儲存的修改可能遺失由 running-config.xml 載入，繼續生效

📝 生活化比喻：文書草稿 vs 已發布版本

  • 候選組態 = 草稿：你可以隨便改、反覆改，但讀者（也就是流量）完全看不到。
  • Commit = 按下發布：草稿變成正式版，從這一刻起才影響所有使用者。
  • 版本紀錄 = 歷史版本：每次發布都留下一份，要退回去就載入舊版再發布。

最常見的踩坑：按了 OK 就以為上線了

按 OK 只會更新候選組態，不會生效，也不會自動存檔。若這時防火牆重新開機，沒有手動 Save 的修改可能就不見了；反過來說，忘記 Commit 的修改，流量完全不會受到影響，常見於「明明改了卻沒效果」的排錯現場。

版本差異

候選與執行兩份組態的觀念，從教材的 PAN-OS 8.0 到現行 PAN-OS 12.x 都相同。教材圖中的「auto-commit」畫在開機路徑上，應是指開機或資料平面重啟時，系統自動把執行組態載入資料平面（Tasks 或 CLI 的 show jobs 可看到 AutoCom 工作）。另外，現行版本還有防火牆自己發起的自動 Commit（例如 FQDN 位址物件的更新），在提交佇列中優先於管理員發起的 Commit。

Flow 二、Commit 流程與 Preview / Validate

點選 WebUI 右上方的 Commit，會先決定要提交的範圍，再依序可做三件檢查：

功能作用
Preview Changes把候選組態與執行組態並排比較。新增以綠色、修改以黃色、刪除以紅色標示；可用 Lines of Context 調整上下文行數。預覽會開新視窗，瀏覽器需允許彈出視窗。
Change Summary列出這次要提交的每一項設定、設定類型與修改者，可用 Group By 依欄位分組。
Validate Commit列出實際 Commit 時會出現的所有錯誤與警告，不會更動執行組態。錯誤必須先排除；警告則是提醒你注意。
Commit真正把候選組態變成執行組態。到 Tasks 可查看進行中、完成或失敗的 Commit，等待中的 Commit 可取消。

按鈕名稱：教材（PAN-OS 8.0）與上表寫「Validate Commit」；也有原廠文件把它寫成「Validate Changes」。原廠文件說法不一，以實機按鈕為準。

Commit 佇列與工作管理

  • 防火牆會把 Commit 要求排進佇列，你可以在前一筆還在跑時再送出下一筆，依發起順序執行。
  • 點選 WebUI 下方的 Tasks 開啟工作管理員，預設顯示 Type、Status、Start Time、Messages 欄位，Messages 會顯示佇列順位。
  • 已開始執行的 Commit 無法取消；等待中的可在 Action 欄按 x 取消，內建（predefined）的管理員角色還可按 Clear Commit Queue 一次清空。
  • Preview、Validate、Commit、Save、Revert 都只針對「上次 Commit 之後」的修改。

重點：養成提交前的習慣

先 Preview 確認「我改的就是我以為的那些」，再 Validate 排除錯誤，最後 Commit。Validate 不會動到執行組態，所以在有固定維護時段的環境，可以提早幾小時先驗證。

踩坑：Commit 不能反悔

Revert 只能撤銷「上次 Commit 之後」的修改。要退回到上一次 Commit 之前的狀態，必須載入先前備份或系統自動留存的版本（見第四節），再 Commit 一次。

版本差異

  • 在被 Panorama 管理的防火牆上，Commit 後防火牆會檢查是否切斷了與 Panorama 的連線；若是，Commit 會失敗並退回先前的執行組態（第 18 章會再談 Panorama 的 Commit 與 Push）。

Teamwork 三、多管理員：Per-admin Commit、Save / Revert 與 Lock

多位管理員同時登入時，大家的修改都放在同一份候選組態裡。如果只想提交自己負責的部分，就要使用範圍控制。

操作 全部管理員 指定管理員或位置
CommitCommit > Commit All Changes（預設，範圍由你的角色權限決定）Commit > Commit Changes Made By，可依管理員或位置（虛擬系統、共用物件與政策、共用的 Device 與 Network 設定）篩選
SaveDevice > Setup > Operations 的 Save candidate configuration（覆寫預設快照，含所有管理員的修改）Config > Save Changes 再選 Save Changes Made By，另存為具名檔案
RevertDevice > Setup > Operations 的 Revert to running configuration；或 Config > Revert Changes 的 Revert All ChangesConfig > Revert Changes 的 Revert Changes Made By

提交或儲存「其他管理員」的修改，需要 Superuser 角色，或管理員角色設定檔中啟用 Commit For Other Admins（儲存則為 Save For Other Admins）權限。

踩坑一：「全域」操作會連同事的修改一起處理

教材特別提醒：Device > Setup > Operations 裡的 Revert、Save、Load 是全域操作，不分管理員。在這裡按 Revert to running configuration，會把所有管理員尚未提交的修改一併丟掉。只想撤銷自己的修改，請改用 Config > Revert Changes > Revert Changes Made By。要注意 Revert to last saved configuration 也只有全域版本，沒有「依管理員」的選項。

踩坑二：拆開提交時的相依關係

如果你只提交自己的修改，而這些修改和別人的修改彼此相依（例如兩人都在同一個規則區新增、刪除或調整規則順序），驗證可能會報錯。原廠建議的處理方式是：把相關管理員的修改一併納入，或直接全部提交。

Lock：避免兩個人同時改同一處

Config lock

擋住其他管理員修改候選組態。適合你要連續做一組互相關聯的設定，不希望被打斷。

Commit lock

擋住其他管理員提交候選組態。適合你的修改還沒驗證完，不想被別人的 Commit 一併帶上線。

  • 入口是 WebUI 最上方的鎖頭圖示（旁邊的數字是目前的鎖數量）：點開後選 Take a Lock，選擇 Config 或 Commit，可加上 Comment 說明原因（原廠建議填寫）。多虛擬系統的機型還要選 Location（某個 vsys 或 Shared）。
  • 只有 Superuser 或上鎖的管理員本人可以手動 Remove Lock；防火牆完成一次 Commit 後也會自動解除鎖。
  • 也可以在 Device > Setup > Management > General Settings 勾選 Automatically Acquire Commit Lock，讓任何人修改候選組態時自動取得 Commit lock（對所有管理員生效）。

版本差異

  • 教材（PAN-OS 8.0）只有 Commit 的「依管理員」與 Save、Revert 的「依管理員」概念。現行 PAN-OS 12.x 另可依位置（虛擬系統、共用政策與物件、共用 Device 與 Network 設定）篩選，也有 Automatically Acquire Commit Lock 選項（教材未提到）。
  • 教材第 26 張寫「依管理員還原到先前儲存的組態」，現行說法不同：依管理員的 Revert（Config > Revert Changes > Revert Changes Made By）是丟棄尚未提交的修改，也就是回到執行組態；「還原到最後儲存版本」（Revert to last saved configuration）只有全域操作，沒有依管理員的選項。

Backup 四、儲存、載入、匯出與版本回復

所有備份與回復的入口都集中在 Device > Setup > Operations。教材圖把它們分成「留在防火牆本機」與「經過管理電腦進出」兩類：

操作（Operations 內的項目）用途
Save candidate configuration把候選組態存成預設快照（.snapshot.xml），會覆寫舊的預設快照。存檔不會生效。
Save named configuration snapshot另存為你命名的快照，不動預設快照。
Revert to running configuration丟掉 Commit 之後所有管理員的修改，回到目前的執行組態。
Revert to last saved configuration把候選組態還原成預設快照的內容，之後可再 Commit 覆寫執行組態。
Load configuration version載入先前某次 Commit 時留下的版本（每次 Commit 都會產生一個版本），再視需要 Commit。
Load named configuration snapshot載入你先前存下或匯入的具名快照，再視需要 Commit。
Export named configuration snapshot把執行組態、具名候選快照或先前匯入的組態以 XML 匯出到管理電腦。
Export configuration version匯出指定版本的執行組態（XML）。
Import named configuration snapshot把管理電腦上的 XML 組態檔匯入防火牆；匯入後要再 Load 才會進入候選組態。

重點：從外部備份回復的順序

Import named configuration snapshot（把檔案送進防火牆）→ Load named configuration snapshot（載入成候選組態）→ Validate / Commit（真正生效）。原廠也建議把重要組態備份到防火牆以外的主機。第 3 章若載入範本組態，也是走這條路徑。

用 Config Audit 比對兩個版本

到 Device > Config Audit，可從版本清單（欄位含 Versions、Committed By、Commit Date、Object Changes、Description）選出最多兩個版本，按 Compare Versions：

  • XML Diff：左舊右新並排比對，新增綠色、刪除紅色、修改黃色。
  • Change Summary：以 Operation 欄列出 Set、Edit、Rename、Move、Delete，點物件名稱可看 XML 片段。
  • 兩個版本之間若有多次 Commit，會顯示累積後的差異。Load 與 Revert 操作不會被記錄在差異中。
  • 這就是為什麼 Commit 時填寫 Description 很有價值：它會出現在 Config Audit 的 Description 欄，事後比對一目了然。

踩坑：以為防火牆會自動幫你存候選組態

防火牆不會自動把候選組態存到永久儲存。要留下做到一半的工作，必須手動 Save；而且存到預設快照時，會把所有管理員的修改一起覆寫。多人環境建議用具名快照，檔名裡寫日期與用途。

版本差異

教材（PAN-OS 8.0）只列出 Save、Load、Revert、Export、Import 的概念圖。現行 PAN-OS 12.x 另有「Export device state」（匯出含 Panorama 範本與裝置群組設定的狀態包，用於更換設備）與 Config Audit 的 XML Diff / Change Summary。Config Audit 的 Change Summary 處理的差異上限為 25 MB，超過時請改看 XML Diff；HA 環境請在主動（Active）設備上執行稽核。

Logs 五、日誌檢視與過濾

防火牆本機維護多種日誌，入口是 Monitor > Logs，選擇日誌類型後即可看到清單。你能看到哪些類型，取決於管理員角色的權限。

日誌類型記錄什麼
Traffic每個工作階段的開始與結束，含區域、位址、應用程式、規則動作與流量位元組數
Threat流量符合安全設定檔時產生的威脅事件，含威脅名稱、嚴重性與動作
URL Filtering網站存取紀錄，依 URL 過濾設定檔產生
WildFire Submissions送交 WildFire 分析的檔案與結果判定
DNS SecurityDNS Security 服務處理過的 DNS 查詢紀錄
Data Filtering機敏資料偵測與檔案類型阻擋的紀錄
HIP Match / GlobalProtect主機資訊檔案比對結果；GlobalProtect 連線、用戶端與入口、閘道資訊（第 16 章）
IP-Tag / User-ID / DecryptionIP 標籤套用紀錄；IP 與使用者對應（第 14 章）；解密與未解密工作階段（第 15 章）
Tunnel Inspection受檢查的通道工作階段
Unified把 Traffic、Threat、URL Filtering、WildFire Submissions、Data Filtering 的最新紀錄合併在同一個檢視
Configuration每一次組態變更：管理員、用戶端類型、指令、結果，以及修改前後的值
System / Alarms系統事件（含嚴重性與描述）；系統產生的警報資訊
Authentication驗證政策（Authentication policy）所保護資源的驗證事件，可用來排錯或找出暴力破解的跡象

另有 GTP、SCTP 等較少用於一般企業的類型；實際可見的類型依機型、授權、已啟用功能與 PAN-OS 版本而異。

建立日誌過濾條件

  • 最快的做法：在日誌清單中，點選任何一個值（例如來源位址或應用程式），它就會被加進過濾條件。多個條件之間是 AND（且）的關係。
  • 過濾列旁的按鈕：Add Filter（新增條件）、Load Filter（載入已存的條件）、Apply Filter（以目前條件重新整理）、Save Filter（以名稱儲存條件）。
  • 點清單中的放大鏡圖示可開啟 Detailed Log View，查看來源與目的詳細資訊與相關工作階段；Threat 日誌另有封包擷取圖示可看本機封包擷取。
  • Unified 日誌可用 Effective Queries 選擇要包含哪些日誌類型。
  • 匯出：點 Export to CSV 圖示。預設匯出的列數上限，原廠文件說法不一（2,000 或 65,535），請以實機 Max Rows in CSV Export 欄位的預設值為準；可到 Device > Setup > Management 編輯 Logging and Reporting Settings，在 Log Export and Reporting 分頁調整。

也可以直接輸入過濾語法，運算子包括 eq、in、has、geq、leq 等。例如：

( addr.src in 10.0.0.1 ) and ( app eq ssl )
# 來源位址是 10.0.0.1，且應用程式是 ssl
( dstloc eq "IN" )
# 值剛好等於運算子關鍵字時（例如國碼 IN 與運算子 in 同字），要用雙引號包起來，避免語法錯誤

欄位名稱（如 addr.src、app）請以實機為準：先在你的 WebUI 以點選方式產生語法，再對照調整。另外，表示「不等於」的 neq 運算子，原廠文件沒有明確列出，是否可用請以實機為準。

重點：Traffic 日誌何時產生？

每條安全政策規則可以選擇在工作階段開始和／或結束時記錄，預設是在結束時記錄。排錯時可暫時加上開始時記錄，確認封包有沒有到達並比對到哪條規則（規則的 Log 設定，以及把日誌轉送到外部系統的 Log Forwarding 設定檔，請見第 9 章）。

組態日誌與規則稽核備註：查「誰改了什麼」

  • Monitor > Logs > Configuration 會記下每次組態變更的管理員、指令與修改前後的值，是追查「誰在什麼時候改了這條規則」的第一站。
  • 針對單一政策規則，可開啟 Audit Comment Archive：顯示該規則的稽核備註（Audit Comment）歷史、規則在兩次 Commit 之間的組態日誌，以及 Rule Changes（比對該規則兩個組態版本的差異）。
  • 若要求每次新增或修改規則都必須填 Audit Comment，可到 Device > Setup > Management 編輯 Policy Rulebase Settings，勾選 Require Audit Comment on Policies 啟用。這項強制檢查在單機也有效：啟用後，新增規則時必須填 Audit Comment，既有規則在下次編輯時也要填；另可用 Audit Comment Regular Expression 規範格式（例如工單編號）。

版本差異

教材（PAN-OS 8.0）只提到「每台防火牆維護多種日誌」並示範 System 與 Traffic 日誌的過濾。現行版本另有 Decryption、Tunnel Inspection、IP-Tag、User-ID、GlobalProtect、DNS Security、Authentication 等類型，並且有 Unified 合併檢視；稽核備註（Audit Comment）與 Rule Changes Archive 則是 PAN-OS 9.0 之後才有的功能。實際可見的日誌類型，請以實機 Monitor > Logs 的清單為準。
