威脅防護篇 - 單元 13：Content-ID 與安全設定檔

講師導言

前面幾章解決的是「這是什麼應用程式、誰在用、從哪個區域到哪個區域」。但流量被安全政策放行，不代表裡面的內容就是安全的： 一個正常的網頁下載，可能夾帶病毒；一條正常的 DNS 查詢，可能正在找惡意程式的指揮伺服器。 這一章的主角是 Content-ID 與安全設定檔（Security Profile）： 它們在「放行之後」再檢查一次內容，並決定要警示、阻擋，還是請使用者自己確認。 你會學到每種設定檔擋什麼、日誌去哪裡看、怎麼處理誤判，以及怎麼把設定檔真正掛到規則上，因為沒掛上去的設定檔，什麼也不會做。

Goals 本章學習目標

  • 說明 Content-ID 檢查哪些內容，並指出設定檔在流量處理流程中的位置
  • 列出主要安全設定檔類型，以及各自的防護對象與日誌位置
  • 設定 Vulnerability Protection 與 Antivirus 設定檔，並用例外處理誤判
  • 說明 Anti-Spyware 的 DNS 簽章與 DNS Sinkhole 的運作，並從日誌找出疑似受感染的主機
  • 建立 File Blocking 設定檔，分辨 alert、block、continue 三種動作與其限制
  • 用 Security Profile Group 把設定檔套用到安全政策規則

Concept 一、Content-ID 與串流式掃描

Content-ID 是防火牆的威脅防護引擎，加上一組政策，用來檢查與控制穿越防火牆的內容。 它掃描的對象包括：軟體弱點攻擊、病毒、間諜程式、惡意網址，以及受限制的檔案與資料。 它的設計是串流式（stream-based）而不是檔案式（file-based）：不必等整個檔案收完才開始檢查，而是封包一邊流過、一邊比對，才能維持即時的效能。

設定檔在流程中的位置

回想第 1 章的流量處理流程，順序如下圖：進入封包後，先做區域防護（Zone Protection），再做轉送查詢與 NAT 規則查詢（判斷目的區域，含 DNAT 檢查）和 DoS 防護政策查詢，接著做安全政策的初步檢查（這時還不看應用程式，視為 any），再建立工作階段，由 App-ID 辨識應用程式。辨識之後會再比對一次安全政策，被放行的流量才會往下走：如果應用程式是 ssl，會先比對解密政策並解密，App-ID 再辨識解密後的內容，應用程式若改變，就再比對一次安全政策，然後才交給安全設定檔做額外檢查；如果是 ssh，解密後只控制 ssh-tunnel，不做 Content-ID 檢查；其他流量直接交給安全設定檔。設定檔檢查完，有解密的流量重新加密，最後套用 NAT 轉換並送出。

橘色是安全設定檔作用的位置，已被安全政策阻擋的流量不會進入設定檔檢查；ssl 或 ssh 要比對到解密規則才會真的解密，沒有符合的規則時不解密，流量照常往下走。教材的圖是簡化畫法，順序與第 1 章相同。

🏢 生活化比喻：大樓門禁、包裹檢查與詐騙電話轉接

  • 安全政策：大樓警衛，看證件決定誰可以進門。
  • 安全設定檔：進門後的包裹檢查。X 光看有沒有違禁品（Vulnerability Protection），驗毒機看有沒有病毒（Antivirus），檢查人員比對黑名單來源（Anti-Spyware），還有人專門檢查有沒有拿走公司文件（File Blocking）。警衛放行了，包裹還是要檢查。
  • DNS Sinkhole：有人要撥電話給詐騙集團，總機把電話偷偷轉到反詐騙專線。電話接通的那一刻，就知道是哪一支分機中招了。

Threat 日誌

Vulnerability Protection、Antivirus 與 Anti-Spyware 的事件，都記錄在 Monitor > Logs > Threat。

  • 點選欄位標題，可以調整要顯示的欄位數量。
  • 每一筆都有威脅 ID（Threat ID）；之後要建立例外，就要用這個 ID。
  • 可開啟 Threat Details 視窗看詳細內容；若設定檔啟用了封包擷取（Packet Capture），日誌上會帶有封包擷取可下載。
  • 動作設為 allow 的簽章，不會產生 Threat 日誌，也沒有封包擷取；要看得到，至少選 alert。

版本差異：訂閱名稱與雲端檢查

  • 教材（PAN-OS 8.0）的威脅防護只談 Threat Prevention。現行原廠文件已經把檢查能力分成 Threat Prevention 與 Advanced Threat Prevention；授權名稱、相依關係與更新方式，請回頭看第 3 章，這裡不再重講。
  • Advanced Threat Prevention 的 Inline Cloud Analysis，設定位置就在本章的兩種設定檔裡：Anti-Spyware（偵測進階 C2）與 Vulnerability Protection（偵測指令注入與 SQL 注入）。兩者都有獨立的 Inline Cloud Analysis 頁籤，每個引擎的預設動作為 Alert。
  • 以 Inline Cloud Analysis 偵測到的威脅不會產生封包擷取，這點與一般簽章不同。
  • WildFire 現在分成三級：隨防火牆提供的基本 WildFire、WildFire 訂閱，以及另外加購的 Advanced WildFire（見第 3 章）。Advanced WildFire 不是 WildFire 的新名稱；本章只用到「哪些檔案要送去分析」這個觀念。
  • 現行 12.1 的設定檔總覽另列了一個 AI Security 類型，但說明它只適用於 Prisma AIRS Network intercept，一般 NGFW 課程不需要用到。

最常見的踩坑：設定檔建好了，卻沒有作用

  • 設定檔只對「允許」的流量生效，而且要掛在那條實際比對到流量的規則上。規則是由上往下、第一個符合就停，比對到一條沒掛設定檔的規則，後面的規則再完整也沒用。
  • 加密流量是黑盒子：HTTPS 內容沒有解密，Content-ID 看不到裡面的檔案與攻擊，設定檔實際上形同虛設。解密要在第 15 章處理。
  • 簽章來自內容更新；更新沒有排程或授權過期，設定檔雖然存在，保護卻是舊的（第 3 章）。

Profile 二、弱點防護與防毒

Vulnerability Protection：規則與預設設定檔

路徑：Objects > Security Profiles > Vulnerability Protection

設定檔內有一組規則，每條規則指定「對哪一類弱點事件，採取什麼動作」。原廠提供兩個預設設定檔（唯讀）： default 與 strict。想要自訂動作，就複製（Clone）預設設定檔後再編輯複本，或直接新增全新的設定檔。

動作怎麼選

動作意思

Exceptions：覆蓋規則的動作

  • Exceptions 頁籤可以針對單一威脅指定動作，覆蓋規則裡設定的動作。
  • 預設只列出已建立的例外；勾選 Show all signatures 才會列出所有簽章與各自的動作。
  • IP Address Exemptions：每個簽章最多 100 個單一 IP（不用遮罩），只有當工作階段的來源或目的位址符合時，例外動作才蓋過規則動作。這樣就不必為了一個特例 IP 另外複製出一份設定檔與一條規則。
  • 每條例外也可以個別調整 Packet Capture。
  • 原廠提醒：只針對確認過的誤判建立例外，建議同時開技術支援案件，問題修正後把例外移除。

版本差異：Vulnerability Protection 的 Inline Cloud Analysis

教材沒有這個頁籤。現行 12.1 多了 Inline Cloud Analysis：啟用後以深度學習引擎偵測指令注入與 SQL 注入，每個引擎可選 Allow、Alert、Reset-Client、Reset-Server、Reset-Both，預設為 Alert； 並可用 EDL URL 或 IP 型 EDL 把特定對象排除在雲端分析之外（只用在確認為誤判時）。使用這項功能需要 Advanced Threat Prevention 授權與持續的雲端連線（第 3 章）。

Antivirus：預設設定檔與動作

路徑：Objects > Security Profiles > Antivirus

Antivirus 設定檔按通訊協定解碼器（Decoder）逐一指定動作，例如 HTTP、FTP、SMTP 等。教材的畫面分成兩欄動作： 依內容更新送來的防毒簽章採取的動作（Action），以及依 WildFire 送來的簽章採取的動作（WildFire Action）。出廠就有一個唯讀的 default 設定檔。

Action 頁籤欄位說明
Signature Action依 Palo Alto Networks 標準防毒簽章處理（教材的 Action 欄）
WildFire Signature Action依 WildFire 產生的簽章處理（教材的 WildFire Action 欄）
WildFire Inline ML Action現行版本新增的第三欄：防火牆本機的機器學習模型即時判斷
Enable Packet Capture擷取符合的封包
Application Exceptions列出要不依此設定檔檢查的應用程式，並為每一個指定動作
Signature Exceptions輸入 Threat ID 後按 Add，該威脅就被設定檔忽略
  • default 設定檔檢查所有解碼器；原廠說明：SMTP、IMAP、POP3 產生 alert，其餘解碼器採各簽章預設動作。
  • 原廠建議：複製 default，把所有解碼器的 Action 與 WildFire Action 都改成 reset-both，再附加到所有允許流量的安全政策規則。
  • 例外的用途是降低誤判：從 Threat 日誌找到 Threat ID，輸入到 Signature Exceptions；或在 Application Exceptions 把特定應用程式排除。同樣要記得，只處理確認的誤判，問題解決後移除。

版本差異：WildFire 與簽章兩種動作怎麼分

  • 「簽章」動作針對已經發佈的防毒簽章；「WildFire」動作針對WildFire 分析後產生的簽章，兩者獨立設定，因為信心程度與更新節奏不同。
  • 12.1 另有 WildFire Inline ML 頁籤，可在防火牆本機用機器學習模型即時判斷檔案。每個模型可選 enable（沿用各協定的動作）、alert-only（把較嚴格的動作降為 alert）或 disable。原廠建議把樣本也轉送 WildFire 雲端，讓誤判在二次分析中被修正。
  • Action 頁籤另有 Hold for WildFire Real Time Signature Look Up：先暫停封包，等即時簽章查詢完成再決定，需要同時在 Device > Setup > Content-ID 全域啟用。
  • Antivirus 設定檔本身只決定「碰到簽章怎麼處理」；哪些檔案要送去 WildFire 分析由 Objects > Security Profiles > WildFire Analysis 決定，不在本章的設定範圍。

DNS 三、Anti-Spyware 與 DNS Sinkhole

規則與預設設定檔

路徑：Objects > Security Profiles > Anti-Spyware

Anti-Spyware 偵測的是已被植入主機的間諜程式，以及它們對外的指揮與控制（C2）連線。 出廠有 default 與 strict 兩個唯讀設定檔；自訂的方式與前面相同：複製後編輯，或另建新的。 規則欄位與 Vulnerability Protection 相似：Rule Name、Threat Name、Category、Severity、Action、Packet Capture。

嚴重度 default 設定檔 strict 設定檔
Critical / High / Medium採內容更新包定義的動作reset-both
Low採內容更新包定義的動作default 動作
Informational沒有簽章政策default 動作

以上是 PAN-OS 12.1 的預設行為。

Exceptions 的邏輯與前一節相同：針對單一威脅覆蓋規則的動作，可以逐筆調整 Packet Capture，並可加入 IP Address Exemptions（每個簽章最多 100 個）。同樣只用在確認的誤判。

DNS 簽章與 DNS Policies

惡意程式要連回指揮伺服器，第一步通常是查 DNS。Anti-Spyware 設定檔可以比對惡意網域清單，並決定遇到時怎麼做。教材的畫面有三個重點：惡意網域清單與動作、DNS 簽章例外、Sinkhole 設定。 現行版本把這些集中在 Objects > Security Profiles > Anti-Spyware > Add > DNS Policies 頁籤，例外則在 DNS Exceptions 頁籤（頁籤配置以實機為準）。

簽章來源（Signature Source）說明
Palo Alto Networks Content防火牆本機的清單，由動態內容更新維護；預設動作為 sinkhole
DNS Security雲端服務，要有 DNS Security 授權，另外還要 Threat Prevention 授權
Advanced DNS Security多了即時偵測 DNS 劫持的網域偵測器（偵測器細節以實機為準）；需要 Advanced DNS Security 授權，加上 Advanced Threat Prevention 或 Threat Prevention
External Dynamic Lists網域型 EDL；預設動作為 Allow，而 EDL 的 Allow 不會蓋過 DNS Security 的動作
  • 每個來源可以設定 Log Severity（比對到時記錄的嚴重度）、Policy Action（alert、allow、block、sinkhole）與 Packet Capture（建議對 sinkhole 的流量啟用）。
  • 要讓某個網域例外，用 DNS Exceptions 頁籤的 DNS Domain/FQDN Allow List，或啟用特定 Threat ID；不要寄望於 EDL 的 Allow。
  • 防火牆要連上 DNS Security 雲端，安全政策必須放行 paloalto-dns-security 這個 App-ID，否則連線會失敗。

版本差異：DNS 簽章與 DNS Security 現在在同一個地方

  • 教材的「DNS Signatures」是只有本機惡意網域清單的年代。現行 12.1 的 Anti-Spyware 設定檔有 Signature Policies（相當於教材的 Rules）、Signature Exceptions、DNS Policies、DNS Exceptions 與 Inline Cloud Analysis 等頁籤。
  • DNS Security 與 Advanced DNS Security 在授權上是獨立的訂閱（見第 3 章），但在設定上不是獨立的 Profile 物件：它們是 DNS Policies 頁籤裡的「簽章來源」，所以還是要把 Anti-Spyware 設定檔掛到安全政策規則上才會生效。
  • DNS Policies 頁籤還有教材沒有的 Block DNS Record Types（SVCB、HTTPS、ANY），原廠建議全部封鎖以避免使用 ECH；以及 DNS over TLS（連接埠 853）的 DNS 內容是加密的，沒有解密就看不到，實際效果以實機為準；解密的基本做法見第 15 章。
  • 預設 Sinkhole 位址：新版文件的預設是 FQDN sinkhole.paloaltonetworks.com，由內容更新維護。防火牆回給用戶端的是 CNAME，所以用戶端必須有能解析 CNAME 的內部 DNS；否則改用固定的 Sinkhole IP。

DNS Sinkhole 的運作

Sinkhole（污水池）的做法不是丟棄 DNS 查詢，而是偽造一個回應，把惡意網域指向一個無害的位址。受感染的主機以為找到了指揮伺服器，實際上連到的是 Sinkhole 位址，而這個連線會被防火牆看到。

步驟 1 到 4 發生在 DNS 解析階段，步驟 5 才是受感染主機自己發出的連線。虛線是這個查詢原本要去的外部 DNS 伺服器；惡意網域的查詢在防火牆就被攔下，改回偽造的回應。

從日誌找出受感染主機

  • 在 Monitor > Logs > Threat 可以篩選出 sinkhole 事件，例如條件 action eq sinkhole（原廠建議的篩選條件）。教材的畫面標出的是「Potentially infected host」。
  • 要看清楚來源是誰：如果防火牆看到的 DNS 查詢是由「本地 DNS 伺服器」送出的，日誌上的來源位址就是這台 DNS 伺服器，不是真正中招的主機。
  • 真正受感染的主機，要靠它後來連向 Sinkhole 位址的流量去找：原廠說明，Sinkhole 讓受感染的用戶端連到 Sinkhole IP，之後可以在 Traffic 日誌找到這些用戶端。所以承載這條連線的安全政策規則，要記得啟用 Log at Session End。
  • 預設的 Sinkhole 位址是 FQDN，背後的 IP 可能會更換，所以不要只靠固定 IP 去篩選 Traffic 日誌；建議為這個 FQDN 建一個位址物件，搭配一條專用規則，日誌就能依規則篩選（做法以實機為準）。
  • 如果用戶端直接把 DNS 查詢送過防火牆（沒有經過內部 DNS 伺服器轉發），日誌來源就是用戶端本身。原廠建議：防火牆看不到 DNS 查詢的發起者時（例如防火牆在本地 DNS 伺服器的外側），啟用 sinkhole；如果無法 sinkhole，至少要 block。

踩坑：Threat 日誌裡的「來源」是你自己的 DNS 伺服器

看到整排 sinkhole 事件的來源都是同一台內部 DNS 伺服器，千萬不要去清查那台 DNS 伺服器。真正要找的是「連到 Sinkhole 位址的內部主機」。 另一個常見問題是：防火牆根本沒機會看到 DNS 查詢（用戶端用了 DNS over HTTPS，或查詢走加密通道），簽章就無從比對，這要靠解密（第 15 章）與 App-ID 控管。

File 四、檔案封鎖

路徑：Objects > Security Profiles > File Blocking > Add

File Blocking 有兩個目的：防止惡意資料進入，以及防止機敏資料外流。 它的判斷依據不是檔案內容，而是三個條件的組合：應用程式（Application）、檔案類型（File Types）、方向（Direction：Upload、Download、Both），符合之後就執行規則指定的動作。一個設定檔可以有多條規則。

動作行為適合的情境
alert放行檔案，並寫入日誌先觀察、盤點有哪些檔案在流動
block阻擋檔案傳輸，並寫入日誌高風險類型，例如可執行檔、批次檔
continue寫入日誌，並回應一個頁面，請使用者確認後才繼續傳輸提醒使用者可能是順手下載（drive-by download）

Data Filtering 日誌

  • File Blocking 事件記錄在 Monitor > Logs > Data Filtering（實際顯示位置以實機為準），內容包含被處理的檔案名稱與檔案類型。
  • 欄位的意思：Source 是送出檔案的系統，Destination 是接收檔案的系統，判讀方向時不要弄反。
  • 原廠說明，Data Filtering 日誌同時涵蓋「機敏資料」與「File Blocking 設定檔」兩種事件；例如規則阻擋 .exe 時，這個日誌會顯示被擋的檔案。

Continue 回應頁

continue 動作會要求使用者自己許可才完成傳輸，因此有幾個限制：

  • 只有瀏覽器能顯示確認頁，所以教材與原廠都說：只適用 web-browsing 應用程式。其他應用程式沒有辦法提示使用者，傳輸會直接被擋下。
  • HTTPS 網站需要先有解密政策，防火牆才看得到檔案（第 15 章）。
  • 如果伺服器把 HTTP 回應標頭與檔案內容分在不同封包送出，即使動作是 continue，檔案仍會被阻擋。
  • 日誌中的應用程式名稱可能與瀏覽器看到的不同（例如 sharepoint 系列），設定前先查日誌確認實際的 App-ID。
  • 想換成自己公司的說明文字，到 Device > Response Pages 建立自訂頁面。

多層編碼的檔案

檔案常被層層包裝：例如一份 .docx 先壓成 zip，zip 再用 HTTP 的 chunked 與 gzip 傳輸。教材寫防火牆最多解開四層編碼再檢查，現行版本的上限以實機為準； 超過上限的檔案不會被完整解碼，所以教材教你在 File Blocking 規則裡，把「超過四層的多層編碼檔案」直接阻擋。

  • 檔案類型清單裡有一個 multi-level-encoding 類型，就是為此設計的。
  • 原廠預設設定檔：strict file blocking 有阻擋 multi-level-encoding；basic file blocking 的清單則沒有列出。需要時，複製 strict 再依需求調整。
預設設定檔內容（原廠說明）
basic file blocking適合較不敏感的應用。上傳與下載都阻擋 PE 檔、Java 檔、Help 檔，以及 .vbe、.hta、.wsf、.torrent、.7z、.rar、.bat；加密的 rar 與 zip 則請使用者確認；其餘類型 alert
strict file blocking適合最敏感的應用。包含上列全部，再加上 flash、.tar、multi-level-encoding、.cab、.msi，且加密的 rar 與 zip 直接阻擋

Data Filtering 設定檔（補充）

教材把 Data Filtering 日誌放在 File Blocking 之後，是因為兩者共用同一個日誌。 Objects > Security Profiles > Data Filtering 本身則是另一種設定檔：先在 Objects > Custom Objects > Data Patterns 定義資料樣式，再在設定檔裡指定應用程式、檔案類型、方向、Alert Threshold（出現幾次就警示）與 Block Threshold（出現幾次就阻擋）、日誌嚴重度，以及是否啟用 Data Capture（查看擷取資料需要另外設定密碼）。

補充：File Blocking 的動作與送 WildFire

  • File Blocking 的動作只有 alert、continue、block 三種，教材與現行 12.1 一樣，沒有 forward（轉送 WildFire）選項。如果你在其他舊資料看到「把檔案轉送 WildFire」的說法，現在的做法是另建 WildFire Analysis 設定檔，依「應用程式、檔案類型、方向」決定要送去 public-cloud 還是 private-cloud。
  • 預設的 WildFire Analysis 設定檔會把所有未知檔案轉送分析；WildFire Analysis 設定檔要另外掛到允許規則上（或放進群組），它不依賴 File Blocking。
  • 12.1 的 WildFire Analysis 設定檔還可以啟用 Advanced WildFire Inline Cloud Analysis（方向只限下載）；詳細授權依第 3 章。
  • strict、basic 兩個預設設定檔在內容更新 653 版（含）以後提供，可以複製修改。

踩坑：continue 對非瀏覽器應用等於 block，HTTPS 沒解密則等於沒設

把 continue 用在 web-browsing 以外的應用程式（例如雲端同步軟體），使用者看不到確認頁，傳輸就直接失敗，常被誤認為「網路壞了」。 另外，HTTPS 的檔案在沒有解密的情況下，防火牆看不到檔案類型，規則就不會命中。測試時把 Application 暫時設為 any、先看 Data Filtering 日誌，比較容易釐清是哪一層的問題。

Group 五、安全設定檔群組與套用

設定檔很多，規則也很多，如果每條規則都要一個個勾選五、六種設定檔，既麻煩又容易漏。 Security Profile Group 的做法是：把常一起使用的設定檔打包成一組，規則只要選這一個群組，就能簡化規則管理。

群組名稱 Outbound-Web 只是示意。

建立群組與套用到規則

  1. 到 Objects > Security Profile Groups > Add，輸入名稱，把需要的設定檔加進去。群組可包含 Antivirus、Anti-Spyware、Vulnerability Protection、URL Filtering、File Blocking、Data Filtering 與 WildFire Analysis 設定檔；WildFire Analysis 要掛到規則上（個別選或放進群組），未知檔案才會送去分析。
  2. 到 Policies > Security > Add（或編輯既有規則），在 Actions 頁籤的 Profile Setting 選擇：
    • Profiles：逐一指定個別設定檔；或
    • Group：指定一個 Security Profile Group。
  3. 同一個 Actions 頁籤，Log at Session End 預設已勾選，確認沒有被取消，才有完整的流量日誌（前面找感染主機會用到）。
  4. Commit 之後才會生效（第 4 章）。

重點：名為 default 的群組有特別待遇

原廠說明：若把一個群組命名為 default，新增安全政策規則時就會自動套用這個群組，不必手動選擇。這很適合把你的標準防護當成預設值；個別規則不需要時，建立時改選別的群組或設定即可。 此外，修改群組內的設定檔，所有引用該群組的規則會一起套用新設定，不用逐條規則修改。

建議的做法

  • 每條允許流量的規則都要掛上設定檔或群組。原廠建議把 Vulnerability Protection 套用到所有允許流量的規則上，防範攻擊嘗試。
  • 依風險建立幾組群組，例如「對外上網」「內部伺服器」「僅警示」，而不是每條規則量身訂做。
  • 剛導入時，可先以 alert 為主觀察日誌、處理誤判，再逐步改成阻擋，避免一開始就中斷業務。
  • 設定檔存在、群組存在，都不代表流量被檢查，請隨時回到 Policies > Security 確認規則的 Profile Setting 欄位。

版本差異：最佳實務範本與群組內容

  • 教材沒有談最佳實務設定檔。現在可以從第 3 章的 IronSkillet 取得一套 Day 1 的設定檔與群組範本，載入前的注意事項與版本分支，請回看第 3 章。
  • 教材的設定檔類型圖，列出 Antivirus、Anti-Spyware、Vulnerability Protection、URL Filtering、File Blocking、Security Profile Group、WildFire Analysis、Data Filtering 八項。現行 12.1 對群組可納入類型的列舉只到 Antivirus、Anti-Spyware、Vulnerability Protection、URL Filtering、File Blocking、Data Filtering，沒有列出 WildFire Analysis；原廠文件說法不完整，但實務上群組可以放 WildFire Analysis 設定檔，操作時請以你設備的畫面為準。
  • Strata Cloud Manager 與 PAN-OS 的操作位置不同：PAN-OS 與 Panorama 用 Objects > Security Profile Groups；本課程以 PAN-OS 的操作為主。

踩坑：群組建好了，規則卻選了「None」

Profile Setting 預設不一定選你想要的群組。新增規則後務必檢查「Profile Setting」欄：顯示的是群組名稱，還是空白？ 另外，Deny 或 Drop 的規則掛設定檔沒有意義（流量根本被擋掉了，不會進到設定檔），只有 Allow 規則需要。
