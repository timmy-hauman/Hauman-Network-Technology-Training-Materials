政策篇 - 單元 9：規則設定與政策維運

講師導言

上一章我們談的是安全政策的觀念：由上往下比對、第一條符合就停、預設規則、規則遮蔽。 這一章要動手：一條規則的每個分頁到底填什麼，以及規則上線之後，怎麼持續維護、怎麼把舊的埠號式規則一步步改成應用程式式規則。 寫規則只是開始，半年後規則變成幾百條、沒人敢刪，才是真正的難題。這一章的後半段，就是教你避開那個局面。

Goals 本章學習目標

  • 依序說明一條安全規則各分頁（General、Source、Destination、Application、Service/URL Category、Actions）的欄位與預設值
  • 在規則中使用位址物件、External Dynamic List 與地區（GeoIP）作為來源或目的
  • 處理 Application 相依項目，並看懂 Commit 時的 App Dependency 警告
  • 解釋 application-default 的作用，並能建立自訂 Service
  • 分辨 Allow、Deny、Drop、Reset 的差異，並設定日誌、Log Forwarding 設定檔、排程與預設規則的日誌
  • 使用 Tag、Tag 群組與稽核註解，讓大量規則維持可讀、可追溯
  • 用 Highlight Unused Rules、Rule Usage 與 Policy Optimizer 清理規則並完成 port-based 到 App-ID 的遷移
  • 使用 Test Policy Match 與 Global Find 驗證與搜尋設定

Rule Tabs 一、規則各分頁：General、Source、Destination

新增規則的路徑是 Policies > Security > Add。 一條規則由多個分頁組成：各分頁之間是「而且」的關係，所有條件都符合，這條規則才算命中；同一個欄位裡放了多個項目，則是「或」的關係。 規則建立之後，才會多出一個 Usage 分頁（第五節說明）。

各分頁欄位一覽

分頁主要欄位預設值與提醒
GeneralName、Rule Type、Description、Tags、Group Rules By Tag、Audit CommentRule Type 預設 universal；名稱區分大小寫且不可重複；Tags 與 Description 選填但強烈建議填；Group Rules By Tag 是否在此分頁，以實機畫面為準（第四節）
SourceSource Zone、Source Address（含 Negate）、Source User、Source Device全部預設 any；位址比對的是 NAT 之前的位址
DestinationDestination Zone、Destination Address（含 Negate）、Destination Device預設 any；位址是 NAT 前，區域是 NAT 後（第 10、11 章）
Application應用程式、應用程式群組、應用程式篩選器預設 any，應盡量改成具體的應用程式

ActionsAction、Profile Setting、Log Setting、Schedule 等Action 預設 Allow；日誌預設只在連線結束時記錄

General 分頁

  • Rule Type：universal（預設、最常用）同時涵蓋區域內與區域間流量；intrazone 只管同一區域內，不能指定目的區域；interzone 只管不同區域之間。細節在第 8 章。
  • Tags：用關鍵字替規則分類，方便過濾與分組（第四節）。
  • Audit Comment：每次修改規則時寫下「為什麼改、改了什麼、誰改的」，會隨規則留存。這個欄位的內容有長度上限，實際上限請以你的畫面為準。
  • Audit Comment Archive 連結：開啟該規則的稽核歷史，分三個頁籤。 Audit Comments 顯示每次提交的註解、管理員與設定版本； Config Logs 顯示兩次 Commit 之間對這條規則做過的設定變更記錄； Rule Changes 讓你選兩個設定版本，並排比較規則差異。

強制大家寫標籤與稽核註解

路徑是 Device > Setup > Management > Policy Rulebase Settings。可以要求規則必須有 Description、Tag、Audit Comment，也可以用規則運算式（regex）規定註解格式，例如要求要有工單編號。 設定完成後新增的規則就必須填寫，既有規則則要自己補上。

版本差異：規則名稱長度、User 分頁

  • 名稱長度：新版教材講師備註寫「最多 31 個字元」，但現行原廠文件寫「最多 63 個字元」。實作時以 63 為準，不過跨設備與 Panorama 共用的規則，建議名稱不要寫得太長。
  • User 分頁：現行欄位說明與建立規則的步驟把 Source User 放在 Source 分頁，同版的概述頁仍寫獨立的 User 分頁，8.0 教材是獨立分頁；以實機畫面為準。
  • Source Device：教材寫的是 IoT 裝置；現行欄位說明列的選項是 any、no-hip、quarantine、select。
  • User 欄位要發揮作用，必須先啟用 User-ID，第 14 章才會完整說明。目前只要知道選項：any、pre-logon、known-user、unknown、select。
  • Audit Comment Archive 與 Tag 群組這些功能自 PAN-OS 9.0 起提供；若規則是由 Panorama 推送的，稽核歷史可能要在 Panorama 上查看，以實機為準。

Source 與 Destination 分頁：位址從哪裡來

位址欄位預設是 any，按 Add 之後可以選下列幾種來源，也可以混用：

位址物件與位址群組

  • 先在 Objects > Addresses > Add 建立一個物件，代表一或多個 IP（單一位址、網段、範圍或 FQDN）。
  • 規則直接引用物件名稱，之後位址變動只要改物件，不必逐條改規則。
  • 多個物件可再包成位址群組。

External Dynamic List（EDL）

  • 由外部網址定期提供清單的物件，路徑 Objects > External Dynamic Lists。
  • IP 類型的 EDL 可直接當來源或目的位址，清單更新時不需要重新 Commit。
  • 常見用途：封鎖已知惡意來源、放行雲端服務位址。

地區（Region，GeoIP）

  • 以國家或地區為單位，由原廠維護的內部資料庫對應 IP 到國家代碼。
  • 適合「某些國家一律不准進來」這種規則。
  • 內部的私有網段請另外用位址物件表示，不要假設它們會被歸到某個國家。

Negate（反向選取）

  • 勾選後，規則會比對「不在清單內」的所有位址。例如清單放一個網段，就代表該網段以外的全部位址。
  • 對地區使用 Negate 時要小心：必須把含有私有位址的地區也一併列入，否則內部之間的連線可能中斷，上線前請用實機驗證。
  • IP Wildcard Mask 類型的位址物件只能用在安全規則；和 Negate 搭配時的行為，以實機為準。

踩坑：Negate 的範圍比想像的大

Negate 表示「除了這些以外的全部」，範圍通常比你想的大很多。例如在 Allow 規則的來源位址放內網網段再勾 Negate，等於允許網際網路上所有位址。 用 Negate 之前，請先用 Test Policy Match（第五節）確認結果符合預期。

App & Service 二、Application 與 Service 搭配

Application 欄位決定「這是什麼應用程式」，Service 欄位決定「它可以走哪些連接埠」。兩者搭配，才是新世代防火牆規則的標準寫法。 App-ID 如何辨識應用程式、為什麼同一個應用程式會有父子關係，留到第 12 章深入說明，這裡只談規則怎麼寫。

Application 分頁與相依項目

  • 預設是 any，建議改為具體的應用程式（或應用程式群組、篩選器）。
  • 加入應用程式後，右側的 Depends On 窗格會列出該應用程式運作時還需要放行的其他應用程式。沒有一併放行，應用程式可能無法正常運作。
  • 可以按 Add to Current Rule 加進目前這條規則，或 Add to Existing Rule 加進另一條既有規則。
  • 選父應用程式會包含所有子功能，原廠日後新增的子功能也會自動納入。例如選 facebook 就包含 facebook-chat、facebook-mail 等；若只選其中幾個子功能，其餘功能就不會被放行。

Commit 時，防火牆會檢查「規則裡的應用程式，其相依項目是否被任何一條規則放行」。注意這裡的判斷範圍是整個政策，不是單一規則。 沒有滿足的項目會逐條規則列在 Commit 視窗的 App Dependency 頁籤；點選規則旁的 Count 數字可看缺哪些應用程式，點規則名稱可直接開啟規則補上，補完再 Commit 一次，確認警告消失。

踩坑：Commit 的相依警告被忽略

App Dependency 是警告，Commit 仍會完成（這一點原廠文件沒有明寫，以實機為準），所以很容易被略過。結果是應用程式「明明有放行卻用不起來」，使用者回報的症狀常常只有「網頁開一半」或「功能不完整」。 原廠文件也提到，沒解決的相依項目每次 Commit 都會再次出現警告。每次改完規則，請養成看一眼 Commit 視窗頁籤的習慣。

Service/URL Category 分頁

Service 選項意思使用建議
application-default應用程式只能使用 App-ID 資料庫預先定義的預設協定與連接埠。允許類規則首選
Select（指定服務）只允許你加進來的服務物件（協定與連接埠）。企業自訂埠的內部應用程式
any任何協定、任何連接埠都可以，限制最少。除非有明確理由，避免使用
  • application-default 的價值：應用程式跑在非標準埠，常是規避偵測或惡意行為的徵兆。使用它之後，同一個應用程式走不尋常的埠就不會命中這條規則。
  • 就算設成 application-default，防火牆仍會在所有連接埠上辨識應用程式，只是這條規則只對預設埠上的流量生效。
  • 加了 URL Category 的規則，必須有對應授權才能使用 PAN-DB 分類（第 3、13 章）。預設是 any，也可以加入多個分類。

🏢 生活化比喻：大樓訪客登記

  • Application：訪客登記單上寫的「來找誰、辦什麼事」。表上沒寫的人，即使走得進大廳也不放行。
  • application-default：這類訪客只能走他該走的那扇門。送貨的人從貨運口進來沒問題，從消防逃生門出現就很可疑。
  • Depends On：開會需要的投影機與茶水也要一起登記。只放行主角、漏了配角，會議還是開不起來。

這條規則的重點：有明確的來源區域與位址、指定應用程式、Service 用 application-default、有日誌、有稽核註解。每一欄都盡量不是 any。

踩坑：全部都是 any 的 Allow 規則

區域、位址、Application、Service 全部 any 再加 Allow，等於這台防火牆變成一般路由器，而且它會遮蔽（shadow）排在後面的所有規則（第 8 章）。 急著排除問題而臨時建立這種規則，事後卻忘了拿掉，是現場最常見的資安缺口之一。要臨時放行，也請至少限縮來源、設定排程或在稽核註解寫清楚期限。

Actions & Logs 三、Actions 與日誌

Action：六種處置方式

Action行為
Allow放行，預設值。
Deny封鎖，並依照該應用程式本身定義的預設 Deny 動作處理。這個預設動作可在 Objects > Applications 查看該應用程式的詳細資料。
Drop靜默丟棄，並覆蓋應用程式的預設 Deny 動作；不會送出 TCP reset。
Reset client對發起連線的一方（client）送 TCP reset。
Reset server對回應的一方（server）送 TCP reset。
Reset both兩端都送 TCP reset。
  • Send ICMP Unreachable：僅適用於 Layer 3 介面，讓來源端能優雅地結束連線。現行欄位說明寫它用於被丟棄的 TCP 流量與所有 UDP 流量；TCP 的 Reset 動作本身已經送出 reset，通常不會再多送 ICMP。教材把它列在 Drop 與各種 Reset 之下，說法略有出入，以實機為準。
  • Reset 只在連線（session）已成立之後才會送出；如果在三向交握完成之前就被擋掉，就不會有 reset。
  • 為什麼 Deny 的預設不是單純丟棄？防火牆要先建立 TCP 連線，才能辨識出是什麼應用程式。連線建立後如果靜默丟包，應用程式可能卡住、持續重送，白白占用資源。所以教材（2017–2020 版）指出，當時超過半數應用程式的預設 Deny 動作是送 TCP reset；個別應用程式請到 Objects > Applications 查看。

踩坑：誤以為 Deny 與 Drop 一樣

兩者在日誌裡也不同。Traffic 日誌的 Type 欄位（欄位說明稱為 subtype）出現 drop，代表在辨識出應用程式之前就被丟棄，而且沒有規則放行；出現 deny，代表辨識出應用程式之後才被丟棄，可能是有規則封鎖，也可能是沒有規則放行。在辨識出應用程式之前就丟棄時，Application 欄會顯示 not-applicable。 對內部使用者想讓他們「快點得到拒絕訊息而不是卡住」的場合，用 Deny 或 Reset；對外部掃描者，Drop 讓對方什麼都得不到。

版本差異：deny 與 drop 的日誌意義

教材以「命中的規則是否指定了具體的應用程式」來解釋 deny 與 drop；現行欄位說明則改以「丟棄時是否已經辨識出應用程式」來定義。本章採用現行的定義。看日誌時請先看 Application 欄與命中的規則，不要只憑 Type 欄位推論規則怎麼寫。

日誌設定

Log at Session End

  • 預設勾選。連線結束時寫一筆 Traffic 日誌，含流量位元組數、持續時間等完整資訊。
  • 平常維運只開這個就夠用。

Log at Session Start

  • 預設不勾。連線一開始就寫一筆，能看到初期的連線建立與應用程式辨識。
  • 只適合短期除錯：每條連線寫兩筆日誌，會增加管理平面 CPU 負擔與磁碟用量。
  • Log Forwarding：選一個 Log Forwarding 設定檔，把日誌送往外部系統（Syslog、Panorama 等），設定檔的建立方式見本章下方的「建立 Log Forwarding 設定檔」。
  • 日誌查看路徑：Monitor > Logs > Traffic。點放大鏡可看單筆詳細資料；ICMP 這類短連線的 count 若大於 1，表示該筆合併了多個同來源同目的的連線。
  • 只有勾了 Log at Session Start，URL 分類切換時才會在 Traffic 日誌出現各自的記錄。

建立 Log Forwarding 設定檔

設定檔只決定「哪一類日誌、符合什麼條件、送去哪裡」。規則本身要有勾選 Log at Session End（或 Start），才有 Traffic 日誌可以轉送。步驟如下：

  1. 先準備目的地：Syslog、Email、SNMP Trap 或 HTTP 的伺服器設定檔，路徑在 Device > Server Profiles。只送往 Panorama 的話，這一步可以省略。
  2. 進入 Objects > Log Forwarding > Add，輸入 Name。想讓新建立的安全規則與區域自動套用這個設定檔，就把名稱取為 default。
  3. 在設定檔內按 Add 新增一筆比對清單（match list）：輸入名稱，選 Log Type（例如 traffic）。Filter 預設是轉送該類型的全部日誌；只要轉送一部分時，用 Filter Builder 建立條件。
  4. 在同一個視窗加入目的地：Panorama，或剛才準備好的 SNMP、Email、Syslog、HTTP 伺服器設定檔，然後按 OK。
  5. 回到規則的 Actions 分頁，在 Log Forwarding 欄位選這個設定檔，Commit 之後到接收端確認有收到日誌。

System、Configuration 這類不屬於規則的日誌，轉送設定放在 Device > Log Settings。各欄位的名稱與位置以實機畫面為準。

排程（Schedule）

  • 預設規則永遠有效。要限制生效時間，先到 Objects > Schedules > Add 建立排程，再到規則的 Actions 分頁選取。
  • 支援三種：每日、每週指定星期、非循環的指定日期區間；每一種都可以設多組起訖時間，時間用 24 小時制（細節以你版本的畫面為準）。
  • 已建立的連線不受影響：例如排程規則到點開始封鎖 FTP，原本已在傳輸的 FTP 不會被中斷，只有新的連線會被擋。

區域內與區域間預設規則的日誌

第 8 章提過兩條隱含的預設規則：intrazone-default（放行區域內）與 interzone-default（拒絕區域間）。要在 Traffic 日誌裡看見它們放行或擋掉的流量，得先對規則做 Override，再自己打開日誌。 這兩條規則的日誌預設值，各份文件說法不一（見本節最後的版本差異框），所以步驟裡有一步是親眼確認核取方塊。步驟如下：

  1. 進入 Policies > Security，捲到規則清單最下方，選取 interzone-default（或 intrazone-default）。
  2. 按 Override，在 Actions 頁籤的 Log Setting 區勾選 Log at Session End。要把這些日誌送往外部系統，再選一個 Log Forwarding 設定檔（建立方式見上方的「建立 Log Forwarding 設定檔」）。
  3. 需要短期除錯時再加上 Log at Session Start。
  4. 回頭親眼確認兩個核取方塊的狀態和你要的一致，再 Commit。
  5. 想恢復成原本的設定：選取該規則，按 Revert，再按 Yes 確認。

除了日誌，預設規則也可以套用安全設定檔（第 13 章）。原廠建議開啟記錄，才能看到防火牆遇到的所有流量。

版本差異：預設規則日誌的預設值

  • 教材寫預設規則預設不記錄日誌；現行原廠文件寫 Override 後 Log at Session Start 預設勾選、Session End 預設不勾選，說法不一，以實機畫面為準。
  • 現行文件的寫法和一般自訂規則（Session End 預設勾選、Session Start 預設不勾）剛好相反。文字是否有誤，或各版本介面的預設值是否改變，無法由文件確認。
  • 建議做法：Override 預設規則之後，親眼確認兩個核取方塊的實際狀態，再依需求勾選。

Tags & Objects 四、Tags 與物件

Tag：替物件與規則貼標籤

  • 建立路徑：Objects > Tags > Add。可設定名稱、顏色與註解。
  • Tag 可以貼在位址物件、位址群組、區域、服務、服務群組與政策規則上。規則與物件都可以有多個 Tag；若有多個，介面上只顯示第一個 Tag 的顏色。
  • 規則清單可以用 Tag 過濾，只顯示帶有該標籤的規則。隱含的預設規則永遠會顯示。
  • 命名建議：用目的命名，例如 Decrypt、No-decrypt、Mail-Servers、Temporary，而不是用人名。

Tag 群組：把規則按標籤分組

  • 先在每條規則的編輯視窗找到 Group Rules By Tag 欄位，選一個 Tag 做為分組依據（這個欄位通常在 General 分頁，以實機畫面為準），按 OK。再到 Policies > Security，勾選規則清單下方的 View Rulebase as Groups，就能以群組方式檢視規則。
  • 群組的顯示順序與規則在規則庫中的順序一致，所以同一個 Tag 群組可能在清單中出現好幾次，以保留規則的優先順序。
  • 在群組上執行的動作（新增、刪除、搬移、複製）會套用到該群組的所有規則，不論它們在規則庫的哪個位置。
  • 先建立 Tag 並套用到規則上，才能用它來分組。

版本差異：Tag Browser 與 Tag 群組

較舊的 PAN-OS 版本有 Tag Browser；教材指出 PAN-OS 9.0 之後以「Tag 群組」取代，現行版本的操作就是上面的 Group Rules By Tag 欄位加上 View Rulebase as Groups 選項。若你看到的是舊介面，功能名稱會不同。 教材另提到自 9.0 起可強制規則必須有 Tag，該設定位於 Device > Setup > Management 的規則庫設定區；是否因缺 Tag 而導致 Commit 失敗，以你版本的畫面選項為準。

自訂 Service：定義協定與連接埠

規則裡的 Service 欄位選「指定服務」時，要先有服務物件。路徑是 Objects > Services > Add：

欄位說明
Name / Description名稱建議能看出用途，例如 tcp-8443-app。
ProtocolTCP 或 UDP，二選一，不能同時選。
Destination Port必填。可以寫單一埠、用連字號的範圍，或用逗號分隔的清單，三種格式可混用，範圍 0 到 65535。
Source Port選填，大多數情況留空。
Tags選填。
  • 預設只有兩個預先定義的服務：service-http（教材寫 TCP 80 與 8080）與 service-https。其餘都要自己建。
  • 多個服務可再包成服務群組。
  • 原廠建議：原本用 service-http 與 service-https 控制 web-browsing 的規則，改用 application-default 較好，因為它能強制明文網頁只走 80、加密網頁只走 443。

重點：何時才需要自訂 Service

大多數知名應用程式，application-default 就夠用，不需要建服務物件。真正需要自訂 Service 的，通常是公司內部自行開發、跑在特殊埠的應用程式。 那種情況下，規則的 Application 通常會是 ssl、web-browsing 或 unknown-tcp 等，再用自訂 Service 把埠限制死。

Operations 五、政策維運：Usage、Policy Optimizer、Test Policy

管理規則清單

  • 清單下方工具列有 Add、Delete、Clone、Override、Revert、Enable、Disable、Move 等操作。
  • Move 可上移、下移、移到最上或最下，也可用滑鼠拖曳。左邊的行號不是規則的一部分，規則搬動時行號不會跟著動。
  • Disable 是停用但保留，停用的規則以灰色斜體顯示。想暫時關閉、先備好規則、或排除問題時很好用。
  • 每位管理員可以自訂顯示的欄位：點任一欄標題即可勾選要顯示的欄位，只影響自己的畫面。
  • Clone 會複製選取的規則當範本，名稱預設為 rule 加編號，放在原規則下方，記得改名並檢查位置。

Usage 分頁：單條規則的使用情形

規則建立後，開啟規則會看到 Usage 分頁，依區段顯示：

  • Basics：規則的建立時間與最後修改時間。
  • Activity：Hit Count（命中次數）、第一次與最後一次命中的時間。
  • Applications：這條規則看到過幾種應用程式。點 Compare Applications & Applications Seen 連結，可進入從 port-based 遷移到 App-ID 的工具。
  • Traffic：近 30 天這條規則上的流量（位元組）。

找出沒在用的規則

規則越多，越難維護，也越容易留下過度開放的存取。清理規則可以降低攻擊面、簡化管理。有兩個工具：

Highlight Unused Rules

  • 位置：Policies > Security 的工具列。
  • 找出自防火牆上次重新啟動以來未被使用的規則，以黃色點狀底色標示；有啟用 Policy Rule Hit Count 時，以命中資料判斷。
  • 也適合用來檢查從別牌防火牆搬過來的規則，是否仍有被用到。

Rule Usage 篩選

  • 位置：Policies > Security > Policy Optimizer > Rule Usage。
  • Timeframe：要看多少天的資料。
  • Usage：Any、Unused（期間內沒命中）、Used（期間內有命中）。
  • Exclude rules reset during the last N days：略過最近重設過命中計數器的規則（範圍 1 到 5000 天）。
  • 欄位含 Hit Count、Last Hit、First Hit、Modified、Created。
  • Reset Rule Hit Counter：位於清單底部選單，可對全部或選取的規則清除命中統計。典型用法：修改規則之後歸零，再觀察是否有流量命中，用來驗證修改成果。
  • 找到未使用的規則後，建議先 Disable 觀察一段時間，確認沒有人抱怨，再刪除。

踩坑：觀察期太短就刪規則

有些流量一季或一年才出現一次，例如季結算、年度備份、災難復原演練。看到「沒命中」就刪，等到那一天才發現服務不通。 判斷未使用時要看足夠長的期間。Hit Count 會保留穿過重新開機、升級與資料平面重啟，但手動 Reset 之後就從零開始，觀察期要從重設那天算起（見下方版本差異）。

版本差異：未使用規則的判斷基準

  • 教材說防火牆追蹤的是「自上次資料平面重新啟動以來沒被用到的規則」，也說命中資料重設之後，被清除的部分就找不回來。這是舊的說法。
  • 本章（和第 8 章一致）採用現行說法：總命中次數在重新開機、資料平面重啟與升級後都會保留，只有手動重設才會歸零，第一次與最後一次命中時間則不能重設。Highlight Unused Rules 標示的是自防火牆上次重新啟動以來未使用的規則，以黃色點狀底色顯示；有啟用命中計數時，以命中資料判斷。
  • 實務上不要只憑底色就刪規則，請同時看 Hit Count、First Hit、Last Hit 與你設定的觀察期間。

Policy Optimizer：從 port-based 遷移到 App-ID

許多設備是從傳統防火牆搬過來的，規則寫的是「某來源到某目的、開放 TCP 80 與 443」，這就是 port-based 規則（Application 欄是 any）。 它看不出到底是誰在使用那些埠。Policy Optimizer 幫你把這類規則改成明確列出應用程式的規則。路徑是 Policies > Security > Policy Optimizer，本章用到三個檢視（頁籤）：

頁籤用途
Rules Without App Controls
部分原廠文件與舊版介面稱 No App Specified		列出所有 port-based 規則（Apps Allowed 為 any）。開啟 Applications & Usage 可看見實際命中該規則的應用程式。
Unused Apps列出已經指定應用程式、但其中有些應用程式從沒在這條規則上出現過的規則，也就是開放得比實際需要多。
Rule Usage依命中資料與時間範圍篩選規則，找出過時或未使用的規則（見上一節）。

三種轉換方式

  • Create Cloned Rule：保留原本的 port-based 規則，並把應用程式式的新規則放在它正上方。原廠稱這是最安全的遷移方式。
  • Add to This Rule：直接把看過的應用程式加進這條規則，並以新規則取代、刪掉原規則，風險較高，因為原規則被刪除後，新規則漏列的合法應用程式就沒有規則可以接住，會被擋下。
  • Match Usage：一鍵把所有看過的應用程式複製進規則。只適合單純的規則，例如只看到 SSH 的 TCP 22。

在 Applications & Usage 視窗，Timeframe 可選 7 天、15 天、30 天或 Anytime；原廠建議遷移時選 Anytime，評估最完整。

🚪 生活化比喻：把「通行證」換成「點名簿」

  • port-based 規則：拿著 80 與 443 這張通行證，誰來都能進，沒人知道進去幹嘛。
  • App-ID 規則：一份點名簿，名單上有的才放行，其餘一律攔下。
  • 遷移的做法：先把點名簿放在舊通行證前面試行。舊通行證還有人在用，代表名單漏了人；等舊通行證長期沒人刷，才能放心撤掉。

踩坑：Policy Optimizer 沒資料或資料不準

  • Apps Seen 約每小時更新一次，剛改完規則別立刻判斷。
  • 原廠指出 Policy Optimizer 只採計 Log at Session End，會忽略 Log at Session Start。規則若沒有開啟 Log at Session End，就看不到資料。
  • 只開放極少觀察期就轉換，可能漏掉低頻應用程式。建議先累積足夠的資料。

版本差異：Policy Optimizer 的檢視名稱與載入方式

  • 檢視名稱：Policy Optimizer 自 PAN-OS 9.0 起提供，Rule Usage 篩選的名稱與路徑在教材與現行文件一致。列出「應用程式為 any 的規則」那個檢視（教材沒有點名），部分原廠文件與舊版介面稱 No App Specified，現行介面多寫成 Rules Without App Controls，原廠文件說法不一，以實機畫面為準。
  • 其他檢視：現行介面說明還列出 New App Viewer（需要 SaaS Security 訂閱）與 Log Forwarding for Security Services（一次替多條規則指定 Log Forwarding 設定檔），教材沒有提到。
  • 載入方式：較新的 12.1 維護版本，原廠表示 Policy Optimizer 資料改為「需要時才載入」以提升效能，並建議只在需要時才切換到 Policy Optimizer 檢視。你的版本是否適用此行為，以實機為準。

Test Policy Match：先模擬、再上線

  • PAN-OS 9.0 起，可在網頁介面輸入一組模擬流量條件，檢查它會命中哪一條規則，不必再背 CLI 指令。
  • 入口有兩處：Policies > Security 工具列的 Test Policy Match，以及 Device > Troubleshooting 的 Security Policy Match。
  • 可輸入的條件包括 From／To 區域、Source、Destination、Destination Port、Protocol、Source User、Application、Category；還有選項決定要顯示「所有可能的符合規則，直到第一條 Allow」或只顯示第一條命中的規則。欄位與選項的實際名稱，以你版本的畫面為準。
  • CLI 對應指令為 test security-policy-match。
  • Troubleshooting 頁面另有連線測試，可確認設備能連上 WildFire、日誌收集器等資源。
  • 搭配 Commit 前的驗證：新規則或 Negate 規則寫完，先測再 Commit，可以省下很多回頭修正的時間。

Global Find：全域搜尋設定

  • 在候選設定（candidate configuration）與內容資料庫中搜尋一段文字，例如 IP 位址、物件名稱、規則名稱、威脅 ID、應用程式名稱。
  • 啟動方式：畫面上方的 Search 連結，或在欄位的下拉箭頭選單中選 Global Find。結果依類別分組，點連結就能跳到該設定位置。
  • 典型用途：準備刪除某個位址物件前，先找出還有哪些規則、群組引用它；找出所有帶某個 Tag 的物件；查某個應用程式有沒有被用在規則、應用程式群組或報表查詢中。
  • 如果你在規則的註解裡寫了工單編號，之後可以直接搜尋工單編號，找到當時改的地方（稽核註解欄位是否也搜得到，以實機為準）。
  • 限制：不搜尋日誌、位址範圍與動態配發的 DHCP 位址；個別使用者或群組名稱，除非有被寫進政策，否則也搜不到。能搜的只有防火牆寫進候選設定的內容。這些範圍與限制以你版本的畫面為準。
