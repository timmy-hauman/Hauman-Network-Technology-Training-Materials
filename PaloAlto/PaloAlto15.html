Palo Alto Networks NGFW 實戰課程

進階篇 - 單元 15：SSL/TLS 解密

講師導言

前面兩章，App-ID 幫我們看懂「這是什麼應用程式」，Content-ID 幫我們檢查「裡面夾帶了什麼」。但今天絕大多數的網路連線都是加密的： 防火牆看不進去的內容，就沒辦法比對，也沒辦法阻擋。 這一章要學的就是讓防火牆「有條件地」看進加密連線：哪些流量要解密、用什麼方式解密、憑證要怎麼配合、哪些流量刻意不解密，以及解密之後的效能、日誌與疑難排解。 解密也牽涉隱私與治理，所以我們會同時談「技術上能不能做」與「應該不應該做」要找誰一起決定。

Goals 本章學習目標

  • 說明為什麼加密流量會讓 App-ID 與 Content-ID 失去作用，以及解密在流量處理流程中的位置
  • 分辨 SSL Forward Proxy、SSL Inbound Inspection、SSH Proxy 三種解密類型的方向、憑證需求與限制
  • 說明 Forward Trust 與 Forward Untrust 憑證各自的用途，以及根憑證為什麼必須先派送給用戶端
  • 建立解密政策規則（Policies > Decryption）與解密設定檔（Objects > Decryption Profile），並為敏感類別與技術上無法解密的流量設定例外
  • 說明 TLS 1.3、效能與容量規劃對解密部署的影響
  • 用 Decryption 日誌與 Traffic 日誌驗證解密是否生效，並依 Error Index 分類排解問題

Concept 一、為什麼要解密？它在流程的哪裡？

加密流量可能藏著惡意程式，也可能藏著要外流的機敏資料。原廠的立場是加密流量不應該被自動信任；解密的目的包括阻擋惡意的加密流量、避免機敏資料離開網路、確認核准的應用程式跑在安全的網路上，以及找出違反政策的行為。 一句話概括：你擋不了你沒有檢查的流量。

沒有解密時

  • 內容是密文，Content-ID 無從比對
  • 第 13 章提過：File Blocking 的 Continue 動作用在 HTTPS 網站時，要先有解密政策才有效
  • URL 類別的例外規則也無法套用到 HTTPS 網站

解密之後

  • 防火牆把加密流量解成明文，再交給 App-ID、Content-ID 與安全設定檔檢查
  • 檢查完之後，在轉送出去之前重新加密
  • 可搭配 Advanced Threat Prevention、Advanced URL Filtering 等雲端交付服務使用

🛃 生活化比喻：海關拆封檢查，再重新封口

  • 加密流量：密封的貨櫃，海關只看得到貨櫃外面的標籤，看不到裡面裝了什麼。
  • 解密：海關依規定拆封，把貨物拿出來過 X 光、驗毒、核對清單，這就是 Content-ID 的工作。
  • 重新加密：檢查通過，用新的封條封好再放行。收貨的人拿到的還是一個完整封好的貨櫃。
  • No Decrypt 規則：有些貨物依規定、約定或機密性質，海關決定不拆封，只核對封條與文件是否正常。

比喻只用來理解流程：真實的解密是防火牆在兩條各自獨立的加密連線之間轉手，下一節會畫出來。

解密在封包流程中的位置

回想第 1 章的流量處理流程。下圖沿用同樣的階段名稱，標出解密政策、解密與重新加密落在整個順序的哪裡：

圖中 ssl 與 ssh 分兩條路：SSH 解密後只控制 ssh-tunnel，不做 Content-ID 檢查，所以不會進入 Content-ID。沒有符合的解密規則、或規則是 No Decrypt 時，流量不解密，走「其他流量」的路徑。階段名稱與順序與第 1 章相同。

流程圖差異：教材的圖是簡化畫法

  • 教材原本的流程圖是簡化畫法，把「檢查是否加密、解密」畫在 App-ID 之前。原廠的處理順序是：進入封包 → 區域防護（Zone Protection）→ 轉送查詢與 NAT 規則查詢（判斷目的區域，含 DNAT 檢查）→ DoS 防護政策查詢 → 安全政策初步檢查（此時還不看應用程式，視為 any）→ 建立工作階段 → App-ID 辨識應用程式 → 安全政策再比對 → 放行後，是 ssl 或 ssh 才比對解密政策並解密。ssl 解密後，App-ID 再辨識解密後的內容，應用程式改變時再比對安全政策，然後 Content-ID 套用安全設定檔；ssh 解密（SSH Proxy）後只控制 ssh-tunnel，不做 Content-ID 檢查；其他流量直接 Content-ID 套用安全設定檔。最後需要時重新加密 → 套用 NAT 轉換 → 轉送出去。第 1 章的流程圖已依這個順序畫出。
  • App-ID 再辨識解密後的內容之後，應用程式若改變，會再比對一次安全政策。所以規則要放行解密後出現的應用程式，不能只放行 ssl（細節以實機為準）。
  • 不論畫法，共通的重點都是：解密發生在 Content-ID 檢查之前，重新加密發生在進入轉送階段之前。

版本差異：PAN-OS 12.1.2 的 Decryption 日誌欄位

  • PAN-OS 12.1.2 起，Decryption 日誌欄位改以 Client / Server 前綴區分用戶端側與伺服器側的連線，並新增解密狀態、排除原因與憑證撤銷狀態等欄位。

Types 二、三種解密類型

解密政策規則的 Options 頁籤，動作選 Decrypt 之後要再選一個 Type。三種類型對應三種情境：

比較項目 SSL Forward Proxy SSL Inbound Inspection SSH Proxy
方向與用途往外：內部使用者連到網際網路的 SSL/TLS 流量往內：外部連到你自己內部伺服器的 SSL/TLS 流量解密 SSH，辨識並可阻擋 SSH 連接埠轉送（ssh-tunnel）；不檢查通道內的內容與威脅
需要的憑證防火牆上的 Forward Trust 與 Forward Untrust 憑證內部伺服器的憑證與私鑰，匯入防火牆；每條規則最多 12 張不需要憑證
用戶端要做什麼必須信任簽發複製憑證的根 CA，否則出現憑證警告不用額外安裝；用戶端收到的是伺服器自己的憑證原廠未提到憑證相關動作
規則的 Type 值SSL Forward ProxySSL Inbound InspectionSSH Proxy
共通限制無法解密使用用戶端驗證（client authentication）或憑證釘選（pinned certificate）的連線；解密後的 SSL 工作階段不支援 HA 同步；代理（proxy）處理的流量不支援 DSCP 與 QoS解密後的 SSH 工作階段同樣不做 HA 同步；Decryption 日誌不涵蓋 SSH Proxy 流量
其他注意解密只能在 virtual wire、Layer 2、Layer 3 介面上進行Tap 模式的介面不支援 Inbound Inspection要阻擋 SSH 通道，需另外寫安全政策：ssh-tunnel 應用程式 Deny，並放行 ssh 應用程式

SSL Forward Proxy：防火牆是受信任的中介

防火牆會開出兩條各自獨立的 TLS 連線：一條在用戶端與防火牆之間，一條在防火牆與真正的伺服器之間。對用戶端，防火牆扮演伺服器；對伺服器，防火牆扮演用戶端，兩邊都以為自己直接和對方對話，防火牆就能在中間看到明文。

SSL Inbound Inspection：保護你自己的伺服器

你把受保護伺服器的憑證與私鑰匯入防火牆，並加到規則裡。連線進來時，防火牆確認伺服器送出的憑證與規則內的某一張相符，就把伺服器憑證交給用戶端，並建立兩條各自擁有新工作階段金鑰的加密連線，再檢查明文。

重點：換憑證不中斷的順序

一條 Inbound Inspection 規則最多可放 12 張憑證。換新憑證時先在防火牆匯入新憑證與私鑰、加進規則，再把新憑證裝到網站伺服器。反過來做，伺服器送出的憑證和規則內的不符，連線就會被結束。

版本差異

  • 多張憑證：單一規則放多張憑證需要 PAN-OS 10.2 以上。Panorama 把含多張憑證的規則推到較舊的防火牆時，舊防火牆只保留依字母排序的第一張，PAN-OS 10.1 以前請用獨立的 Template 或 Device Group（第 18 章）。
  • TLS 1.3 與 HSM：私鑰放在 HSM 時，Inbound Inspection 的 TLS 1.3 支援在 PAN-OS 11.2 才加入，並需要 CLI 指令開啟。
  • 後量子密碼學（PQC）：PAN-OS 12.1.2 起，解密設定檔可啟用後量子金鑰封裝機制（需要 TLSv1.3），用於 SSL Forward Proxy 與 SSL Inbound Inspection 等；防火牆能在用戶端側與伺服器側各自使用新式或傳統加密。

Certificates 三、憑證與信任：Forward Trust、Forward Untrust 與根憑證派送

Forward Proxy 的核心是「防火牆替每個網站現場簽發一張複製憑證」。用戶端的瀏覽器能不能接受這張憑證，完全取決於它信不信任簽發者。防火牆上有兩個角色的憑證：

Forward Trust 憑證

  • 伺服器憑證的簽發者是防火牆信任的 CA 時使用
  • 防火牆用它簽發複製憑證給用戶端
  • 用戶端必須信任它背後的根 CA，才不會出現警告
  • 私鑰只留在防火牆，不可匯出給用戶端

Forward Untrust 憑證

  • 伺服器憑證的簽發者防火牆不信任時使用
  • 用戶端會因此看到憑證警告，這是預期的行為
  • 每台防火牆可用同一張
  • 絕不可安裝到用戶端，也不可放進網路設備的信任清單

信任鏈與根憑證派送

設定位置與步驟概要

  1. Forward Trust（最佳實務：企業 CA 簽發）：在 Device > Certificate Management > Certificates > Custom Certificates 按 Generate 產生 CSR（Signed By 選 External Authority (CSR)），送企業 CA 簽發後匯入；匯入時憑證名稱必須與 CSR 名稱完全相同，再勾選 Forward Trust Certificate。 對 Windows 用戶端，原廠建議用「Subordinate Certification Authority」範本簽發，並只把這張下層 CA 憑證標為 Forward Trust。
  2. Forward Trust（替代做法：自簽）：先產生自簽根 CA 並勾選 Trusted Root CA，再為每一台防火牆各產生一張由它簽發的下層 CA 憑證（勾選 Certificate Authority）。
  3. 派送根憑證給用戶端：用戶端若已信任企業根 CA 可略過。否則要匯出根憑證（PEM 格式、不要匯出私鑰），匯入每台用戶端的受信任根憑證存放區；在 Windows 要確認放進「受信任的根憑證授權單位」，預設會放進「個人」。可用 GPO 自動化，或用 GlobalProtect 的 Portal Agent 設定（Network > GlobalProtect > Portals，Trusted Root CA 並啟用 Install in Local Root Certificate Store）。
  4. Forward Untrust：在 Custom Certificates 產生一張 Signed By 留空、勾選 Certificate Authority 的憑證，再勾選 Forward Untrust Certificate。
  5. 建立規則並 Commit：在 Policies > Decryption 新增規則，Action 選 Decrypt、Type 選 SSL Forward Proxy，並建議附上解密設定檔（下一節）。

踩坑一：用戶端不信任 Forward Trust 的根 CA

原廠明說：沒有把根憑證派送給用戶端，使用者在每個被解密的 SSL 網站都會看到憑證警告。症狀是「規則一啟用，幾乎所有 HTTPS 網站都跳警告」。解法是先派送根憑證，並用少數測試用戶端驗證後再擴大規則範圍。另外，個人裝置、訪客、沒有加入網域的設備，也是推行前要先想好的邊緣情況。

踩坑二：把 Forward Untrust 憑證也裝到用戶端

一旦用戶端信任了 Forward Untrust 憑證，防火牆不信任的網站也會被用戶端當成可信，使用者就再也看不到警告。原廠明確要求：Forward Untrust 憑證不可安裝到用戶端，也不可匯出到網路設備的信任清單。

版本差異

  • 憑證管理的選單名稱：現行文件寫 Custom Certificates，PAN-OS 11.2 及更早版本的名稱是 Device Certificates，兩者是同一個位置。
  • PAN-OS 12.1.2 新增：防火牆可依伺服器憑證中的 AIA 欄位自動取回缺少的中繼憑證（快取最長約一週，首次連線仍可能失敗，之後從快取成功）。另有 Bypass Server Certificate Verification 設定，會關閉其他所有伺服器憑證驗證，只適合暫時、針對可信服務使用。

Policy 四、解密政策、解密設定檔與例外

解密政策規則

路徑：Policies > Decryption。規則的結構與安全政策相似，由上往下比對，第一條符合的規則生效。

頁籤內容
General名稱、說明、標籤
Source來源區域、位址、位址群組、使用者與群組（可用 Negate 排除）等
Destination目的區域、位址、位址群組、External Dynamic List 等
Service/URL Category預設涵蓋任何 TCP/UDP 連接埠；可加服務、URL 類別（預先定義或自訂）與 EDL。application-default 對寫排除規則很有用
OptionsAction（Decrypt 或 No Decrypt）、Type（Action 為 Decrypt 時選）、Decryption Profile，以及 Log Successful SSL Handshake、Log Unsuccessful SSL Handshake、Log Forwarding

規則順序

  • 把「排除解密」的規則放在最上面，一般的解密規則在後面。
  • 原廠也建議在規則庫最底部放一條針對高風險與中風險 URL 類別的解密規則，當作安全網。
  • 原廠建議先把安全政策遷移成以應用程式為基礎的規則，再建解密規則。若先在以連接埠為基礎的規則上建好解密、之後才遷移，application-default 規則可能把解密後出現在非預設埠的流量擋掉；先遷移，這類問題在概念驗證階段就會浮現。

解密設定檔（Decryption Profile）

路徑：Objects > Decryption Profile，建立後在解密規則的 Options 頁籤選用。規則決定「解不解、用哪種方式」，設定檔決定「解的時候有哪些檢查與限制」。原廠建議每一條解密規則都套用設定檔。設定檔的頁籤如下：

位置 主要設定（括號為原廠建議或說明）
SSL Decryption > SSL Forward Proxy > Server Certificate Validation Block sessions with expired certificates（建議）；Block sessions with untrusted issuers（建議）；Block sessions with unknown certificate status（最嚴格，可能擋到重要業務網站）；Block sessions on SNI mismatch with Server Certificate（使用顯式或透明代理時建議）；Block sessions on the certificate status check timeout（安全與使用體驗的取捨）；Restrict certificate extensions；Append certificate's CN value to SAN extension；Automatically Fetch Intermediate Certificates；Bypass Server Certificate Verification
SSL Forward Proxy > Unsupported Mode Checks Block sessions with unsupported versions（建議一律啟用）；Block sessions with unsupported cipher suites；Block sessions with client authentication（除非重要應用程式需要用戶端驗證，這類流量改用獨立設定檔）
SSL Forward Proxy > Failure Checks 與 Client Extension Block sessions if resources not available；Block sessions if HSM not available；Block downgrade on no resources；Strip ALPN（移除 ALPN 值以停用 HTTP/2 檢查，HTTP/2 會降為 HTTP/1.1 或被歸為 unknown TCP）
SSL Inbound Inspection Unsupported Mode Checks（版本、加密套件）與 Failure Checks（資源、HSM、降級）；沒有 Server Certificate Validation 與 Client Extension 區塊。不同能力的伺服器請用不同設定檔
SSL Protocol Settings Min Version / Max Version；Key Exchange Algorithms（RSA、DHE、ECDHE 預設都啟用，只有 DHE 與 ECDHE 提供 PFS）；Encryption Algorithms（建議不要允許 3DES 與 RC4；Min Version 設在 TLSv1.2 以上時，這兩項會自動取消勾選，較低的 Min Version 要自己取消）；Authentication Algorithms（MD5 預設封鎖，SHA1 若沒有必要網站依賴建議封鎖）
No Decryption 給 No Decrypt 規則用：對沒有解密的流量，仍可封鎖憑證過期與簽發者不受信任的連線
SSH Proxy Unsupported Mode Checks（不支援的 SSH 版本或演算法）與 Failure Checks（SSH 錯誤、資源不足）

踩坑三：允許不支援的模式，流量被「悄悄」放過去

設定檔若不封鎖不支援的模式，遇到不支援的版本、加密套件或用戶端驗證時，防火牆會把該伺服器記進 Local SSL Decryption Exclusion Cache，之後 12 小時內到同一台伺服器的連線都不再解密、也就不被檢查（快取最多 1,024 筆；修改解密規則或設定檔時會被清空）。如果你的政策是「無法檢查的就不放行」，要在設定檔啟用封鎖選項。

不解密的兩種原因，兩種做法

業務、法規或隱私考量 → No Decrypt 規則

例：財務、健康、政府等敏感類別。範例做法：

  • 在 Policies > Decryption 新增規則，Source 與 Destination 設 Any
  • Service/URL Category 加入 financial-services 與 health-and-medicine
  • Options 的 Action 選 No Decrypt，附上 No Decryption 設定檔
  • 把規則移到解密規則庫的最上面

技術上無法解密 → 解密排除清單

例：憑證釘選、雙向認證（mutual authentication）的網站與應用程式。

  • 位置：Device > Certificate Management > SSL Decryption Exclusions
  • 預先定義的清單預設就排除解密，由 Applications and Threats 內容更新維護；也可 Disable 單筆項目
  • 清單裡沒有的、會讓解密出問題的應用程式，可加入自訂排除
  • 這份清單不是拿來放「因法規或隱私而不想解」的網站，那類要寫 No Decrypt 規則

踩坑四：有釘選憑證的應用程式突然連不上

使用憑證釘選或用戶端憑證驗證的應用程式（常見於行動 App 與部分更新服務），遇到 Forward Proxy 的複製憑證會直接拒絕。處理順序：先到 Decryption 日誌確認失敗原因，再決定是加入排除、單獨寫 No Decrypt 規則，或是為它們建立專用的規則與設定檔。如果政策是嚴格只放行可解密的流量，沒有被任何清單涵蓋的這類連線就會被擋。

原廠文件說法不一：設定檔的最低版本

  • 原廠不同說明對 Min Version 的建議用語不同：有的偏向設定為 TLSv1.3 以取得最強安全性；有的則建議基準值為 Min Version TLSv1.2、Max Version 設為 Max，Min Version 設為 TLSv1.3 只用在確定只使用 TLS 1.3 的流量。實務上可用 TLSv1.2 當基準，需要更嚴的流量另開規則與設定檔。
  • 要允許較舊協定的網站，原廠建議用另一份設定檔並綁在只涵蓋該流量的規則上（例如搭配自訂 URL 類別），不要放寬預設設定檔。

Operations 五、TLS 1.3、效能、驗證與疑難排解

TLS 1.3

  • Forward Proxy 與 Inbound Inspection 都支援 TLS 1.3，支援的加密套件為 TLS13-AES-128-GCM-SHA256、TLS13-AES-256-GCM-SHA384、TLS13-CHACHA20-POLY1305-SHA256。
  • 要在解密規則上啟用，須套用「最低或最高版本設為 TLSv1.3」的解密設定檔；沒有啟用時，PAN-OS 預設最高到 TLSv1.2。Max Version 選 Max 就會對支援的網站自動使用最新版，也涵蓋未來的新版本。
  • 伺服器不支援 TLS 1.3 時，防火牆會選擇伺服器支援的版本；從 1.3 降到 1.2 的流量仍會被解密與檢查。
  • TLS 1.3 把憑證資訊也加密了，防火牆讀不到，所以不要把 No Decryption 設定檔套用到只處理 TLS 1.3 的規則，它擋不了過期或不受信任簽發者。TLS 1.2 以前的流量仍適用。
  • 行動 App 常用憑證釘選，原廠建議涵蓋它們的規則把 Max Version 設為 TLSv1.2，或寫 No Decrypt 規則，否則部分流量可能被丟棄。
  • 沒有解密的流量也要寫規則來管：只有被解密規則管到的未解密流量才會留下日誌。

效能與容量規劃

解密是耗資源的工作。可以解多少，取決於 SSL 流量的規模、TLS 版本、加密套件、驗證方式。原廠建議與原廠業務或工程師一起評估目前與未來的需求，並確認符合效能期待。

分階段導入

  1. 先建一條 No Decrypt 規則，了解使用者實際去了哪些網站與應用程式
  2. 以低風險的範圍做概念驗證（proof of concept）
  3. 用 Decryption 日誌找出並排除問題
  4. 每一階段都檢視使用者體驗與解密報表，再擴大範圍

決定先解哪些

  • 原廠的目標：在資源允許的範圍內，盡量解密非隱私、非敏感的流量
  • 優先考慮高風險與中風險的 URL 類別、關鍵伺服器、業務關鍵流量
  • 設定檔的「資源不足時封鎖」是安全與可用性的取捨
  • 解密後的 SSL 工作階段不做 HA 同步：切換後不會續傳，新連線依政策重新解密（第 17 章）

踩坑五：沒有做容量規劃就全面啟用

一次把所有流量都套上解密、又同時把設定檔調到最嚴格，資源的需求會一起墊高。原廠指出安全設定越嚴格，解密通常消耗越多資源。資源不足時，Decryption 日誌可能出現 Resource 類的錯誤，而設定檔的「資源不足時封鎖」也可能讓連線被結束。對策：分階段、先看現況、與原廠一起評估規模，再逐步擴大。

Decryption 日誌

路徑：Monitor > Logs > Decryption。預設只記錄失敗的 TLS 交握；要記錄成功的交握，要在解密規則的 Options 頁籤勾選 Log Successful SSL Handshake（預設關閉，並請先確認日誌空間）。Log Unsuccessful SSL Handshake 預設啟用。

  • 每筆在 PAN-OS 11.0 有 60 多個欄位（12.1.2 欄位改版後的數目以實機為準），涵蓋所套用的解密規則與類型、憑證細節、TLS 版本、金鑰交換與加密演算法、SNI，以及錯誤資訊。
  • Error Index 欄位把失敗分成八類：Certificate、Cipher、Feature、HSM、Protocol、Resource、Resume、Version；Error 欄位給出細節。兩者也在詳細日誌檢視的 Handshake Details 區。
  • 在握手期間被阻擋的網頁流量不會產生 Decryption 日誌，要去 URL Filtering 日誌找；SSH Proxy 的流量也不在 Decryption 日誌內。
  • Decryption 日誌的 App-ID 來自 Traffic 日誌；Traffic 日誌若關閉，應用程式會顯示 incomplete。
  • ACC 的 SSL Activity（PAN-OS 11 系列起）有解密與未解密流量、失敗原因、TLS 版本與金鑰交換等小工具，可先找出問題流量，再用 Jump to Logs 跳到對應日誌；12.x 的名稱與位置以實機為準。
  • 日誌可轉成自訂報表（排程、PDF/CSV/XML）。

驗證：有沒有真的解密？

到 Monitor > Logs > Traffic 用篩選條件檢查，Decrypted 欄位會顯示 yes 或 no：

想確認的事篩選條件
被解密的工作階段( flags has proxy )，結果的 Decrypted 欄為 yes
沒被解密的 SSL 流量( not flags has proxy ) and ( app eq ssl )，Decrypted 欄為 no
特定一條工作階段( sessionid eq 137020 )（數字僅為範例）
所有 TLS 與 SSH 流量（解密與否都含）( s_encrypted neq 0 )

也可以點日誌的放大鏡進詳細檢視，核對 Decrypted 旗標當作第二個確認。

疑難排解流程

日誌中的錯誤（Error）意思與常見處理（摘自原廠分類）
Untrusted issuer CA憑證鏈有效，但簽發者不在信任錨點中。建議改用受信任的外部 CA，不要用不受信任或自簽的 CA
Server and firewall's certificate mismatch伺服器送出的憑證與防火牆上的不符（例如 Inbound Inspection 換憑證的時機不對）：確認伺服器憑證未過期、伺服器上放的是正確憑證，並重新匯入防火牆
SNI didn't match with subject name or SANSNI 與憑證主體名稱或 SAN 不一致
Unsupported cipher加密套件不相容。讓設定檔的加密套件和兩端都相容，必要時為該流量新增專用規則
Client and server version mismatch / Client and decrypt profile version mismatchTLS 版本不相容。調整設定檔的版本範圍，必要時另建專用規則
Oversized chain received憑證鏈超過 5 張，建議換成需要較少中繼憑證的憑證
Out of the firewall resources防火牆資源不足，回頭檢視容量規劃

Cipher 與 Version 類錯誤會帶有位元遮罩（bitmask）值，原廠說明需用操作模式的 CLI 指令轉換，指令請查你所用版本的原廠文件。

隱私與治理：技術之外的決定

  • 原廠建議在制定策略時，讓法務、財務、人資、主管、資安與資訊單位一起參與，並考量法規遵循、隱私、效能衝擊與特定的安全需求。
  • 因業務、法律、法規或個人因素不想解密的流量（例如財務、健康、政府類別），用 No Decrypt 規則處理；高風險但同時涉及敏感資訊的網站，可選擇封鎖或不解密，以避免隱私爭議。
  • 推行前先向受影響的使用者說明網站存取會有什麼變化。
  • Decryption Port Mirroring（把解密後的明文送到第三方工具）轉送的內容包含敏感資訊，且以明文傳送，需妥善保護傳輸與儲存；解密日誌也可能含敏感內容，建議一併管控存取。原廠並提醒部分國家對 SSL 流量的檢查與留存有規範，正式使用前建議諮詢公司法律顧問。
  • 本章只說明原廠文件如何描述，不構成對任何地區法規的判斷。
