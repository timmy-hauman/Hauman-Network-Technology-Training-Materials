歡迎來到 Palo Alto Networks 防火牆課程！第一堂課不急著敲指令，我們先弄懂一件事：它跟你以前用過的防火牆，骨子裡哪裡不一樣？ 答案藏在兩個設計裡：單通道並行處理，以及管理平面與資料平面分離。搞懂這兩件事，後面所有章節的設定邏輯都會順很多。

Concept 一、為什麼需要新世代防火牆？

傳統防火牆（Stateful Firewall）靠 來源/目的 IP + 通訊協定 + 連接埠 決定放行或阻擋。 但今天的應用程式幾乎都走 80 / 443，連接埠已經看不出「這是誰」。 NGFW 的做法是把判斷依據換成三個維度：應用程式（App）、使用者（User）、內容（Content）。

比較項目 傳統防火牆 Palo Alto NGFW
判斷依據IP、通訊協定、連接埠應用程式（App-ID）、使用者（User-ID）、內容（Content-ID）
80 / 443 上的流量一律視為網頁辨識出是 Gmail、Facebook 聊天，還是惡意程式的回連
威脅檢查常需另外加設備同一台設備、同一條政策內完成

重點

在 Palo Alto 的世界裡，「連接埠」只是輔助條件。例如 DNS 流量走 53 埠沒錯，但不是 DNS 協定的流量即使走 53 埠，App-ID 也不會把它當成 DNS。這就是 App-ID 的價值（第 12 章會詳談）。若惡意程式把 C2 藏在真正的 DNS 查詢裡，則要靠 Anti-Spyware／DNS Security（第 13 章）。

Concept 二、核心設計：單通道並行處理

原廠把這個架構稱為 Single-Pass Parallel Processing（SP3），由兩個互補的概念組成：

單通道（Single Pass）

每個封包只讀一遍，在同一趟內完成：

  • 用 App-ID 技術分類流量
  • 使用者／群組對應（User-ID）
  • 內容掃描：威脅、URL、機敏資料
  • 每種類型只需一份政策

並行處理（Parallel Processing）

不同功能交給專用的硬體引擎同時處理：

  • 功能專屬的並行硬體處理引擎
  • 管理平面與資料平面各自獨立

✈️ 生活化比喻：機場安檢

  • 傳統多層檢查：行李先排隊照 X 光，再排隊驗爆裂物，再排隊查違禁品。每一關各讀一次行李，每一關都可能塞車。
  • 單通道：一條動線走到底，行李一次通過所有檢查。
  • 並行處理：每種檢查有專屬的檢查員與機器，同時動作，不必互相等待。

SP3 的基本概念在各版本相同，原廠早在 2011 年就以「掃描一切、只掃描一次」形容它。

版本差異

現行 PAN-OS 12.x 的原廠文件，已把 Advanced Threat Prevention、Advanced WildFire、Advanced URL Filtering、Advanced DNS Security 等歸類在「雲端交付安全服務（Cloud-Delivered Security Services）」之下，訂閱的組合和教材年代不同，第 3 章授權與第 13 章會再說明。

Architecture 三、管理平面與資料平面

Palo Alto 防火牆把「管理設備」和「轉送流量」拆在兩組互相獨立的資源上。 你在 Web 介面跑大報表、改設定、查日誌，不會搶走處理流量的資源。

元件負責什麼
管理平面設定、日誌、報表。有獨立的處理器、記憶體與硬碟。
網路處理前端的網路處理，硬體加速的逐封包路由查詢、MAC 查詢與 NAT。
安全處理高密度並行處理，加速 App-ID、User-ID、SSL/IPsec、應用程式解碼、解壓縮等標準化的複雜功能。
特徵比對以串流方式、用統一特徵格式比對弱點攻擊（IPS）、病毒、間諜程式、信用卡號與美國社會安全碼（SSN）等機敏資料。

版本差異

上表的四個元件來自教材（PAN-OS 8.0 時代）的硬體架構圖。實際硬體分工會因機型而異，VM-Series 等虛擬平台沒有專用晶片，由虛擬 CPU 以軟體方式完成。

Flow 四、封包的旅程：流量處理流程

後面學政策、NAT、解密時，腦中都要有這張圖。流程分三段：工作階段建立 → 檢查與強制執行 → 轉送前處理。入口只做區域防護（Zone Protection）；DoS 防護政策查詢排在轉送與 NAT 規則查詢之後、安全政策初步檢查之前。第一個封包進來時，應用程式還不知道，所以會先以 any 做一次安全政策初步檢查，建立工作階段後才由 App-ID 辨識應用程式，再以辨識出的應用程式比對一次安全政策。 放行之後，如果是 ssl 或 ssh，才會比對解密政策並解密：ssl 解密後會再辨識一次，應用程式改變時再比對安全政策，然後套用安全設定檔；ssh 解密後只控制 ssh-tunnel，不做 Content-ID 檢查。其他流量直接套用安全設定檔，最後需要時重新加密、套用 NAT 轉換，再轉送出去。

教材投影片的流程圖是簡化畫法（把解密畫在 App-ID 之前，DoS 防護也和區域防護畫在同一格），本圖依原廠的處理順序重畫。

最常見的踩坑：NAT 與安全政策誰先？

圖中標 * 的每一次安全政策比對（初步檢查、再比對，以及應用程式改變時的再比對），重點都一樣：用的是「NAT 之前」的 IP 位址，但目的區域要用 NAT 之後的。 寫 Destination NAT 對應的安全規則時，位址欄填原始（公開）位址，區域欄填轉換後（內部）所在的區域。第 10、11 章會用實例再練一次。

工作階段（Session）與流（Flow）

  • 每個封包會對應到一個工作階段，每個工作階段再對應到一條安全政策規則。
  • 一個工作階段可能有一或兩條流：TCP 是兩條（去程 c2s、回程 s2c），多播這類單向流量只有一條。
  • 發起方向（c2s）必須有規則允許；回程（s2c）自動放行，所以你只需要寫「誰可以主動發起連線」的規則（不論是對內或對外）。
  • 防火牆的「伺服器」是指回應流量的一方，不是主機是否提供服務，兩者定義不同。

管理方式：四種入口

Web 介面（WebUI）

最常用，以 HTTPS 連線。依功能分頁：Dashboard、ACC、Monitor、Policies、Objects、Network、Device。

命令列（CLI）

以 SSH 或序列埠 Console 連線，分「操作模式」與「設定模式」，除錯與批次操作很方便。

API（REST／XML）

供自動化與整合使用，可用腳本查詢狀態或修改設定。

Panorama

集中管理多台防火牆，統一設定、報表與日誌收集（第 18 章）。
