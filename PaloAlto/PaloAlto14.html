Palo Alto Networks NGFW 實戰課程

進階篇 - 單元 14：User-ID

講師導言

前面幾章的安全規則，條件幾乎都是「位址、區域、應用程式」。但真正想問的問題常常是：這是誰在用？ 財務部的人可以連 ERP，工程師可以用 SSH，訪客只能上網。位址會因為 DHCP、換座位、出差而改變，人不會。 這一章的主角是 User-ID：防火牆如何知道「某個位址此刻是誰」、如何知道「這個人屬於哪些群組」，以及怎麼把這兩份資訊用在規則、日誌與排錯上。 你也會學到它的風險：對應表一旦過期或被繞過，規則就會悄悄地套錯人。

Goals 本章學習目標

  • 說明為什麼要用使用者與群組寫規則，以及 User-ID 的兩份資料：IP 對使用者、使用者對群組
  • 列出主要的 IP 對使用者對應方式，並比較各自的資訊來源、適用情境與注意事項
  • 分辨 Windows-based 與 PAN-OS 整合式 User-ID agent，說明伺服器監控、服務帳號權限與包含／排除網段
  • 設定 LDAP 群組對應（Group Mapping Settings），並在區域啟用 User Identification
  • 在安全規則的 Source User 使用使用者與群組，並在日誌中看到使用者名稱
  • 用 show user 系列指令驗證與排錯，並說出 IP 重用、DHCP 租約、服務帳號權限等風險

Concept 一、為什麼要用「身分」寫政策？

User-ID 讓防火牆辨識使用者，而不是只看 IP 位址。原廠把好處歸納成三件事：

可視性

在 ACC 或日誌檢視器中，看到「誰」在使用哪些應用程式，而不只是哪個位址。

政策控制

把使用者資訊接到安全規則，讓敏感應用程式只開放給有業務需求的人。

日誌、報表、鑑識

產出以使用者為單位的報表，事件調查時能直接指出是哪個帳號。

防火牆需要兩份名單

要執行使用者與群組政策，防火牆必須同時握有兩份資料，缺一份就做不成：

  • IP 對使用者的對應（user mapping）：封包進來時，這個來源位址現在是誰。這是第二節的主題。
  • 使用者對群組的對應（group mapping）：這個人屬於哪些群組，讓你能在規則中直接選群組。這是第三節的主題。

🪑 生活化比喻：辦公室座位表與組織圖

  • IP 位址：座位編號。你只知道「A12 座位的人想進機房」，但不知道坐的是誰。
  • IP 對使用者對應表：座位表。登記每個座位現在坐著誰。座位表沒更新，警衛就會把前一個人的權限給了現在坐下的人。
  • 使用者對群組對應：組織圖。規則只寫「財務部可以進」，部門人員異動時，改組織圖就好，不必改每一條規則。

踩坑：使用者位址在到防火牆前就被 NAT

原廠說明明確寫道，如果使用者的來源 IP 在防火牆做對應之前就已被 NAT 轉換，User-ID 在這種環境下無法運作。上游若有設備把整個網段轉成同一個位址，防火牆看到的就是一個「人」，群組規則自然無從談起。設計拓樸時，要確保防火牆看到的是使用者的真實位址（NAT 與規則的先後關係可回頭複習第 1、10、11 章）。

Mapping 二、防火牆如何學會「IP 是誰」

原廠說明 User-ID 提供多種對應方式，要依使用者在哪裡登入、存取什麼資源來挑選，也可以混合使用，不同站點用不同方式。 各種方式收集到的資訊，都會匯入防火牆的 IP 對使用者對應表，之後的政策、日誌與報表都讀這張表。

對應方式比較

方式 資訊來源 典型使用情境 注意事項
Server Monitoring（伺服器監控） User-ID agent 讀網域控制站、Exchange、Novell eDirectory 的安全事件日誌，看 Kerberos 票證、Exchange 存取、檔案與列印服務連線等登入活動 使用者在公司內部以網域帳號登入的 Windows 環境，最常見的做法 網域必須記錄登入成功事件；使用者可登入網域內任何伺服器，所以每一台都要監控才不漏。需要專用服務帳號
Syslog 無線控制器、802.1x 設備、Apple Open Directory、Proxy、NAC 等送來的登入與登出 syslog，經 Syslog Parse Profile 解析 非 Windows 登入來源，或位址經常變動、需要靠登出事件及時清掉舊對應的環境 訊息必須是單行文字、每則最多 8,000 bytes；UDP 訊息要放得進單一封包。由 agent 擔任 syslog 監聽端

XML API 你寫的腳本擷取登入與登出事件，用 HTTP 請求送給 PAN-OS 整合式 agent 或防火牆，以 API key 驗證 第三方 VPN、802.1x 無線網路等標準方法加不進對應的情況 腳本由你自己維護，登入與登出都要送，否則舊對應會殘留
Port Mapping（Terminal Server Agent） 裝在 Windows 或 Citrix 終端機伺服器上，替各使用者的處理程序指派來源連接埠，回報給 User-ID 許多人共用同一個 IP 的終端機環境 只靠 IP 無法區分人，必須連來源連接埠一起看。不支援的終端機（例如 Linux）改走 XML API（支援範圍以實機為準）
XFF 標頭 Proxy 在 HTTP／HTTPS 請求加上的 X-Forwarded-For 標頭，內含用戶端位址 使用者躲在 Proxy 後面，防火牆看到的來源位址是 Proxy 本身 只適用 HTTP／HTTPS，且 Proxy 必須真的加上標頭；用在 HTTPS 時是否要先解密，以實機為準
Cloud Identity Engine（CIE） 由雲端目錄同步（Directory Sync）取得使用者與群組屬性，再經 User Context 分享身分資料給防火牆、Panorama、Prisma Access 雲端目錄（如 Microsoft Entra ID）與地端 AD 混合、設備多、不想讓每台防火牆互相轉送對應的環境 服務本身免費，但使用目錄資料的執法點可能需要特定授權
Client Probing（用戶端探測） agent 以 WMI 探測用戶端，確認對應是否仍有效，或查詢未對應位址的使用者 舊式的內部 Windows 工作站環境 原廠強烈建議停用，高安全網路尤其不適合；詳見下方

兩種 User-ID agent

伺服器監控與 syslog 這兩種方式，都由 User-ID agent 執行。agent 有兩種型態，做的事相同：

比較項目 Windows-based agent PAN-OS 整合式 agent
跑在哪裡網域的成員伺服器，要靠近被監控的伺服器；每個有被監控伺服器的站點至少裝一個防火牆本身，不需另外裝軟體
與防火牆的流量大部分流量發生在 agent 與被監控伺服器之間；傳給防火牆的只有自上次以來的對應變動防火牆直接連被監控伺服器（WMI 或 WinRM）
服務帳號與 Server Operators不需要 Server Operators 權限只有要監控「使用者工作階段」才需要，原廠不建議，且該群組也能關機與重開機
Syslog 監聽TCP 與 UDP 的 514SSL 的 6514 與 UDP 的 514，並可使用隨 Applications 內容更新提供的預先定義 Parse Profile
設定位置在 agent 軟體中設定，防火牆再設定去連 agentDevice > User Identification > User Mapping

伺服器監控的傳輸方式

PAN-OS 整合式 agent 在監控 Active Directory 與 Exchange 時，可選 WMI、WinRM-HTTP 或 WinRM-HTTPS。事件來源必須產生登入成功（4624）、驗證票證授予（4768）、服務票證授予（4769）與票證更新（4770）事件。每台防火牆最多監控 100 台伺服器、每個虛擬系統最多 50 個 syslog 傳送端。

踩坑：Client Probing 不要開

原廠說這不是高安全網路建議的 User-ID 取得方式：它信任終端回報的資料，設定錯誤就形成風險；若在外部或不受信任的介面上啟用，agent 可能把服務帳號的使用者名稱、網域與密碼雜湊送到網路外面；探測的流量也隨對應數量增加。優先選擇網域控制站、Syslog、XML API，或 Authentication Portal 這些較受信任的來源。

Authentication Portal 的重點

  • 路徑：Device > User Identification > Authentication Portal Settings，再加上 Authentication policy 規則來觸發。沒有 Authentication policy 規則，登入頁不會出現。
  • 兩種模式：Redirect 將未知的工作階段以 HTTP 302 導到防火牆的 Layer 3 介面，可避免憑證錯誤，是較建議的模式；Transparent 由防火牆冒充原目的網站並回 HTTP 401，因為沒有該網站真正的憑證，瀏覽器會跳憑證錯誤，原廠建議只在必要時使用。Kerberos SSO 與 MFA 都要求 Redirect 模式。
  • 三種驗證方式：Web Form（所有瀏覽器與作業系統適用）、Kerberos SSO（需要 Kerberos 基礎架構，防火牆要有 Kerberos 帳號）、用戶端憑證（每台使用者電腦要有憑證，防火牆要信任簽發的 CA）。Kerberos SSO 失敗時，會依設定退回 Web Form 或用戶端憑證。
  • Redirect 模式要為 Redirect Host 建 DNS A 記錄（用 Kerberos SSO 時另加 PTR 記錄）；入口 Layer 3 介面的 Interface Management Profile 要啟用 Response Pages 與 User-ID。
  • Timer 預設 60 分鐘（範圍 1 至 1,440）：驗證成功後，對應存活多久；到期對應就被移除。
  • Authentication Portal 搭配解密：Redirect 模式只能搭配 SSL Forward Proxy，SSL Inbound Inspection 不支援 Redirect 模式；兩種解密類型的差異見第 15 章。

版本差異

  • 本章的欄位名稱與預設值以 PAN-OS 11.1 之後的行為為主，12.x 的欄位細節可能略有不同，以實機為準。
  • Authentication Portal 若沒有指定 SSL/TLS Service Profile，PAN-OS 12.1 以前只協商 TLS 1.2；12.2 以後可協商 TLS 1.2 或 1.3。
  • Cloud Identity Engine 在防火牆上的設定路徑與參數（Device > User Identification > Cloud Identity Engine、更新間隔預設 60 分鐘等），本章以 PAN-OS 10.1 的資料為準，12.x 的欄位名稱請以實機為準。CIE 的雲端端點設定是另一套獨立的設定，本章不展開。
  • 舊版（9.1）曾提到 Kerberos 失敗後退回 NTLM（未能逐版核對，以實機為準）；10.x 之後的驗證方式只列 Web Form、Kerberos SSO 與用戶端憑證三種。

Config 三、設定 agent 與群組對應

這一節用最常見的組合示範：PAN-OS 整合式 agent 監控網域控制站，再用 LDAP 做群組對應。順序是先帳號、再兩條線（IP 對使用者、使用者對群組）、最後啟用與驗證。

步驟 1：專用服務帳號（最小權限）

每個要監控的網域各建一個專用 Active Directory 帳號。原廠要求只給 agent 需要的最小權限，依你啟用的功能而定：

用途 需要的權限
伺服器監控加入 Event Log Readers（內建群組），才能讀安全事件日誌
WMI 傳輸加入 Distributed COM Users
WMI 探測（不建議）被探測的每台用戶端要允許 Root\CIMV2 的 Enable Account 與 Remote Enable，並加入本機 Distributed COM Users 與 Remote Desktop Users
Windows-based agent 主機本機「Log on as a service」權限；若帳號不是網域或本機管理員，還需要安裝資料夾與登錄機碼的權限
工作階段監控（整合式 agent）需要 Server Operators，原廠不建議；Enable Session 選項請保持停用，登入登出事件改走 Syslog 或 XML API
一律要做的「拒絕」拒絕互動式登入（log on as a batch job、log on locally、log on through Remote Desktop Services），並在帳號 Dial-in 內拒絕 Network Access Permission

步驟 2：IP 對使用者（監控伺服器）

  • 路徑：Device > User Identification > User Mapping。在 Server Monitoring 區新增伺服器，輸入名稱，選類型：Microsoft Active Directory、Microsoft Exchange、Novell eDirectory 或 Syslog Sender。
  • AD 與 Exchange 要選傳輸協定：WMI、WinRM-HTTP 或 WinRM-HTTPS。WinRM 搭配 Kerberos 時網路位址要用 FQDN；使用 WMI 時，伺服器位址請填 IP（填 FQDN 會觸發 Kerberos，而 Kerberos 不支援 WMI），帳號則用 domain\username 格式。可選擇透過 DNS 自動探索網域控制站，但 Exchange 與 eDirectory 必須手動新增。
  • 編輯 Palo Alto Networks User-ID Agent Setup：在 Server Monitor Account 分頁填入服務帳號（domain\username 格式）；Server Monitor 分頁的 Server Log Monitor Frequency 範圍 1 至 3,600 秒，預設 2 秒，較舊的網域控制站或高延遲連線至少用 5 秒。
  • Ignore User List 分頁：排除不需對應的帳號（例如 kiosk 帳號），也可強制這些使用者走 Authentication Portal。清單定義在作為 agent 的防火牆上，最多 5,000 筆，萬用字元 * 只能放在最後一個字元。

步驟 3：包含／排除網段

  • 同樣在 User Mapping 頁，新增 Include/Exclude Networks 項目，確認已啟用。Include 把對應範圍限制在指定網段；Exclude 從已包含的範圍中挖掉一部分。
  • 最佳實務：一定要明確定義 Include，讓 agent 只對應內部使用者，避免替外部位址做對應。

踩坑：只加 Exclude、沒加 Include

原廠明說：只有 Exclude 而沒有任何 Include，agent 會把所有網段都排除。對應表因此一片空白，但畫面上所有狀態看起來都正常，是很容易花很久才找到的原因。

步驟 4：使用者對群組（LDAP 群組對應）

  1. 先建 LDAP 伺服器設定檔：Device > Server Profiles > LDAP。最多放四台同類型的伺服器；每台設定名稱、位址、埠號（預設 389）；選伺服器類型（例如 active-directory 會自動填入屬性）；設定 Base DN（搜尋起點）與 Bind DN（完整的 LDAP DN，例如 cn=…,dc=…，或 UPN，例如 administrator@acme.local）與密碼；Bind Timeout 與 Search Timeout 預設都是 30 秒。
  2. 建群組對應：Device > User Identification > Group Mapping Settings，新增設定、選上面的 LDAP 設定檔。Update Interval 範圍 60 至 86,400 秒，預設 3,600 秒；User Domain 留空則由防火牆自動偵測 AD 網域名稱，要填就填 NetBIOS 網域名稱。
  3. 用 Group Include List 限制規則裡可選的群組，或用 Custom Group（以 LDAP 過濾條件定義，例如 Department 為 Marketing 的使用者）。兩者合計每個群組對應設定最多 640 筆；沒指定就是全部群組都可用。Custom Group 在日誌查詢與報表中也能使用。
  4. Active Directory 預設屬性：Primary Username 是 sAMAccountName，Alternate Username 1 是 userPrincipalName；Group Name 是 name、Group Member 是 member。要用到網域以外的屬性，在 User Mapping 的 Setup 設定 User Attributes（畫面位置以實機為準）。
  5. Commit。Custom Group 要先 Commit 才會出現在規則裡。

多網域、多樹系的設計

  • 單一網域：一個群組對應設定、LDAP 設定檔列最多四台網域控制站即可。為同一網域多加設定並不會增加備援。
  • 多網域或多樹系：每個網域或樹系放一台伺服器，並確保使用者名稱在各樹系之間唯一。
  • Universal Groups：一個設定檔連 Global Catalog（埠號 3268，SSL 為 3269），另一個連根網域的網域控制站（埠號 389）。

踩坑：SAML、RADIUS、TACACS+ 不會填群組表

原廠明確說明：防火牆只會在驗證設定檔的 User Group Attribute 用 SAML 群組屬性，拿來和 Allow List 比對、控制誰能登入，不會用它填使用者對群組表。要寫群組規則、設定 GlobalProtect 組態或做群組日誌查詢，需要 LDAP 群組對應或 Cloud Identity Engine 這種可持續查詢的群組來源。

版本差異

步驟 2 至 4 的欄位名稱與預設值以 PAN-OS 11.1 之後的行為為主；若你的實機版本介面略有出入，以實機欄位為準。

Policy 四、區域啟用、規則使用與使用者日誌

啟用 User Identification（區域層級）

對應表建好了，還要告訴防火牆「這個區域進來的流量要套用對應」：Network > Zones，點區域名稱，勾選 Enable User Identification。 如果關閉，防火牆的日誌、報表與政策都會排除使用者對應資訊。

區域設定 行為
Enable User Identification只在受信任的區域啟用。開在網際網路等不受信任的區域，探測可能把 agent 服務帳號名稱、網域名稱與加密的密碼雜湊送出保護網路外。
User Identification ACL：Include List沒填就是所有已探索的對應都套用在此區域；填了，就是白名單，其他網段隱含排除。
User Identification ACL：Exclude List從 Include List 的範圍中再挖掉一部分。例如 Include 10.0.0.0/8、Exclude 10.2.50.0/22，結果是 10.0.0.0/8 內除了 10.2.50.0/22 之外都套用。只有 Exclude 沒有 Include，則會排除對應資訊。

在安全規則使用使用者與群組

路徑：Policies > Security，編輯規則，在 Source 分頁設定來源區域、來源位址與Source User。Source User 預設為 any；可以選特定使用者或群組，也可以選 known-user（已有使用者對應的位址）、unknown（沒有對應的位址），或 pre-logon（以 GlobalProtect 連線、但還沒登入電腦的遠端使用者；Pre-logon 連線方式見第 16 章）。原廠說明：規則的 User 欄位要生效，該區域必須已啟用 User-ID。

上表為教學示意，群組名稱與規則名稱是假設的；原廠範例政策包括「只讓 IT 部門使用 SSH、telnet、FTP」與「所有人可讀社群網站、只有行銷部門可張貼」。規則順序與比對邏輯請回頭看第 8、9 章。

原廠建議與順序

  • 規則優先用群組而非個別使用者，人員異動時改目錄就好，不必改規則。
  • Authentication 規則在 Security policy 之前評估；以驗證取得的對應會蓋過其他 User-ID 方式的對應。
  • 使用者條件還能和應用程式資訊（類別、子類別、底層技術、特性）合併使用，套用在出站或入站流量。

版本差異

現行欄位說明與建立規則的步驟把 Source User 放在 Source 分頁，同版的概述頁仍寫獨立的 User 分頁，8.0 教材是獨立分頁；以實機畫面為準。不論在哪個分頁，欄位名稱與選項（any、pre-logon、使用者或群組、known-user、unknown）都一樣。

使用者日誌

  • Monitor > Logs > Traffic 的 Source User 欄位：確認流量有沒有標上使用者名稱。
  • Monitor > Logs > User-ID 的 User Provided by Source 欄位：看這筆對應是由哪個來源提供的（欄位名稱以實機為準）。
  • ACC 與 Monitor > Reports 可依使用者彙整應用程式使用；show log userid 系列指令可在 CLI 查詢對應是怎麼學到的。

風險與最佳實務

踩坑：IP 重用與 DHCP 租約

對應表是「某個位址在某個時間點是誰」。如果使用者離開了、DHCP 把同一個位址發給另一台裝置，而舊對應還沒過期，新裝置就可能暫時繼承前一個人的權限。防火牆的 Device > User Identification > User Mapping > User-ID Agent Setup > Cache 提供 Enable User Identification Timeout 與 User Identification Timeout (min)：到期後防火牆清除該筆並重新收集；預設 45 分鐘、範圍 1 至 3,600。原廠建議設成 DHCP 租約時間的一半（英文為 half-life），或 Kerberos 票證的存活時間。用 Redistribution 轉送來的對應，每台防火牆依自己的逾時清除，不是依轉送端的設定。Authentication Portal 取得的對應不受這個逾時管，而是用 Portal 自己的 Timer。

踩坑：服務帳號權限過大

agent 的帳號如果被拿走，攻擊者就多了一把進網域的鑰匙。依原廠做法：最小權限、不加入 Server Operators、拒絕互動式登入與撥入、不要在不受信任的區域開 User Identification，也不要開 Client Probing。Allow matching usernames without domains（位於 Cache 區）只有在各網域間使用者名稱不重複時才開，否則會認錯人。

最佳實務清單

  • User-ID 只在受信任區域啟用；Include／Exclude 一律明確定義，只對應內部網段。
  • 專用服務帳號、最小權限；Windows-based agent 要就近放在被監控伺服器旁，每個站點至少一個。
  • 用 Security policy 限制 paloalto-userid-agent 應用程式：只在 agent 區域、被監控伺服器區域、agent 與轉送對應的防火牆之間允許，對網際網路等外部區域拒絕。
  • HA 環境請記得啟用 Config Sync（第 17 章）；Panorama 如何取得使用者與群組見第 18 章，防火牆之間轉送對應（Data Redistribution）本課程不展開。
  • 規則優先寫群組；GlobalProtect 的細節見第 16 章；Authentication Portal 搭配解密時只用 SSL Forward Proxy，兩種解密類型的差異見第 15 章。
