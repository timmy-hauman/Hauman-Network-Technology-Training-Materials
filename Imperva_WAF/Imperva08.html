單元 8:Dynamic Profiling(動態剖析)

上一章 課程目錄 下一章

講師導言

簽章只能抓「已知的壞東西」。Dynamic Profiling(動態剖析)走的是另一條路:先從真實流量學出每個 URL「正常長什麼樣」,再對偏離者告警或阻擋。 它能抓到簽章抓不到的、針對自家程式碼的攻擊,但有三個前提:學習期的流量要乾淨、門檻要設得合理、上線前要調校。 這一章就是帶你走完 Web Profile 學什麼、Learning 怎麼變成 Protect,以及上線前怎麼降誤報。

Goals 本章學習目標

  • 說出一份 Web Profile 學哪些東西,以及「違規流量不會被學進去」的意義
  • 分辨 URL 的 Learning、Protect(與 cookie 的 Ignore)三種模式
  • 說出自動切換到 Protect 的預設門檻(240 小時等),並判斷哪些 URL 會被漏掉
  • 依 10 個步驟完成「Simulation → 調校 → Active」的上線流程
  • 遇到 profile violation 時,依序判斷是真攻擊還是誤報,並選對處理方式

承接第 7 章:一份 Web Profile 對應一個 Web Application(shop、member)。

一、Web Profile 學什麼

用保全認人來想

簽章像「黑名單」,看到通緝犯才攔。Profile 像保全記住每位住戶的長相與作息:不管你是不是通緝犯,只要你的行為「不像這棟樓的人」就會被注意。前提是,保全剛上班時看到的必須是正常住戶,不能把闖空門的也當成住戶記起來。

類別學習內容
結構目錄、URL(含 URL Patterns,把 /item/123 這類動態路徑歸成一類)
方法每個 URL 允許的 HTTP 方法(GET、POST、PUT、DELETE…)
參數名稱、是否必填、長度範圍、值型別、是否 read-only
Cookie哪些 cookie 由伺服器設定、是否會被用戶端改動(防竄改 / 注入)
登入登入 URL、帳號欄位、成功 / 失敗判斷(Application User Tracking,供第 9 章自訂政策與第 11 章使用)
XML / SOAP每個 URL 允許的 SOAP action 與 XML 結構

官方說明的幾個關鍵行為

  • 安裝後就開始學:系統一裝好便開始學習 web 使用行為,達到合適的學習量後切到 Protect。
  • profile 可人工修改:可新增、刪除項目來微調。
  • 學習期間不是裸奔:profile 建立期間,應用仍受 ADC 內容(簽章)與自訂政策保護。
  • 違規流量不會被學進去:例如帶有異常 HTTP 行為或被判定為 worm 的請求,不會成為 profile 的一部分。

技巧:用政策限縮學習範圍。既然「違反既有政策的行為不會被學習」,只想讓 profile 學 GET 與 POST,就先定義一條把其他方法標為違規的政策(第 9 章)。

二、URL 的模式:Learning 與 Protect

每個 URL 各自處在一種模式(以 URL 為粒度,不是整個站一起切):

模式行為
Learning不對此 URL 強制 profile 政策,仍在學它怎麼被存取
Protect強制 profile 政策,偏離即產生 violation,依 Web Profile Policy 的動作處理
Ignore只用在 cookie 保護

關於「Protect and Lock」

舊版說法有第三種狀態「Protect and Lock」(管理者手動鎖定,停止自動調整)。現行文件可手動切換 URL 模式(單一 URL 或多個 URL),但本次查證未看到「Lock」這個名稱【待實機確認】。

換算一下

240 小時 = 10 天。shop.example.com 若有月底結帳、季末活動之類低頻功能,10 天內可能根本沒出現,這些 URL 會在被真正使用時才開始學。這正是第六節上線前調校要處理的。

實驗室與正式環境

官方建議:實驗室流量少時,可把 read-only 成功率暫調為 50、出現次數調為 6,以便測試;但這兩個值越低,誤報與漏報都越多,正式環境請改回預設。

四、Learning Exceptions、Profile Size Limits 與 XML / SOAP

Administration Guide 的 Dynamic Profiling 區有四個視窗:Learning Exceptions、Profile Optimization、Profile Size Limits、Switching to Protect Mode Thresholds (Web)。

視窗用途何時要動
Learning Exceptions指定不要學習的流量弱點掃描器、壓測、監控探針的來源 IP 必須排除,否則它們的異常請求會被當成「正常」學進去【推論:依功能名稱;欄位細節【待實機確認】】
Profile Size Limits限制 profile 的大小(URL、參數數量)有大量動態 URL 的站台,避免 profile 爆量拖慢 MX
Profile Optimization整併 / 最佳化 profile 內容URL Patterns 沒歸好、profile 過於零碎時
Protect Mode Thresholds第三節的門檻低流量站台或學習期需要拉長時

此外,可以關閉自動 Web Profiling(只用簽章與自訂政策),適用於流量極低、無法學出可靠 profile 的應用【待實機確認:開關位置】。

XML / SOAP

  • profile 會自動辨識承載 SOAP / XML 的 URL,逐 URL 學習允許的 SOAP action 與 XML 結構(舊簡報的觀念仍適用)。
  • 舊版列出的解析選項(Parse SOAP XML Only、Ignore Attributes、Parse Empty Elements、Maximum Parsing Depth)在現行版本的名稱與位置【待實機確認】。
  • 現代站台多為 JSON API;JSON 參數如何進 profile、與 API Security 整合的分工見第 11 章【待實機確認:JSON profiling 的細節】。

五、動手玩:Profiling 學習時間軸

拖動滑桿看時間過了多久、URL 什麼時候轉 Protect;再送出一個「偏離 profile」的請求,看是否產生 violation、最後是告警還是阻擋。官方只說明三個因素決定轉換時機,並沒有列出提早轉換的確切條件,所以「高頻 URL 是否已提早轉 Protect」交給你假設。

以 shop、member 兩個 application 為例:

示意畫面:欄位名稱依 Imperva 官方文件,步驟編號對應下方上線流程,版面以實機為準。
  1. 1確認 Site Tree 正確(第 7 章):Servers IP 完整、TLS 能解(否則 profile 只學到殘缺資料)、host 對應把 /member/ 分到 member。
  2. 2Server Group 設 Simulation:Main > Setup > Sites > SG-Shop > Definitions > Operation Mode 選 Simulation,學習與初期觀察期間不阻擋。
  3. 3排除非正常流量:在 Learning Exceptions 排除掃描器、壓測、監控探針的來源【待實機確認】。
  4. 4用政策限縮學習:例如先啟用一條只允許 GET / POST / HEAD 的政策,其他方法不會被學進 profile。
  5. 5讓業務流程跑完一輪:請 QA 或業務單位在學習期內走過註冊、登入、加入購物車、結帳、改密碼、退貨等完整流程;低頻功能(月結、活動頁)也要點到。
  6. 6檢查 profile:看 Learned URLs 與 Web Profile 報表,確認沒有學到明顯的攻擊樣式(例如某參數長度上限被學成 5000)【待實機確認:Main workspace 中 profile 檢視的路徑】。
  7. 7觀察 Protect 後的 violation:URL 陸續自動轉 Protect;此時仍在 Simulation,violation 只告警。
  8. 8逐條調校(下一節),直到 violation 幾乎都是真攻擊。
  9. 9改 Active:Operation Mode 改回 Active,並逐步把 Web Profile Policy 的動作從告警改為阻擋(第 9 章);先從 member 的高風險 URL(登入、改密碼)開始。
  10. 10應用改版時:新 URL 會自動進 Learning;大改版前可把受影響 URL 手動切回 Learning【待實機確認:Switching Between the URL Modes 的操作位置】。

七、降誤報調校步驟

遇到一條 profile violation,依序判斷:

判斷處理
真攻擊不動 profile;確認動作正確即可
合法但 profile 沒學到(低頻 URL、新參數)把該 URL / 參數加入 profile,或把 URL 切回 Learning 讓它重學
參數型別學太窄(例如姓名欄位只學到英文)手動放寬參數的值型別 / 長度
動態路徑被當成大量獨立 URL調整 URL Patterns,把 /item/{id} 歸一類
特定來源的正常行為(內部系統呼叫 API)在 Web Profile Policy 加例外(限定來源、URL),範圍越小越好【待實機確認:例外欄位】
cookie 被前端 JS 正常改寫檢查該 cookie 的模式,必要時設為 Ignore

三個原則

  • 先修 profile、後加例外:例外會永久開洞,profile 修正只影響該參數。
  • 不要用「關掉整條 Web Profile Policy」解決單一誤報:那等於回到純簽章防護。
  • 每次調整記錄原因與工單號:v15.0 起系統事件會記錄「誰改了什麼」(第 12 章),兩者對得起來。

八、常見踩坑

學習期混進掃描流量

弱點掃描或壓測在學習期間跑,攻擊樣式被學成「正常」;排程要錯開或用 Learning Exceptions 排除。

實驗室門檻帶到正式環境

read-only 50 / 6 的測試值留著,誤報與漏報都上升。

TLS 解不開就開始學

profile 只有網路層資訊,轉 Protect 後幾乎沒有防護力;先確認第 7 章的 TLS 設定。

低頻功能沒走到

240 小時內沒出現的 URL,不會在 profile 內,要等上線後第一次被用才開始被學。Protect 期間出現的新 URL 預設會自動進 Learning 開始學;是否另外觸發未授權 URL 類的違規,依設定而定【待實機確認】。

一個 application 塞進多個站

profile 被最寬鬆的站撐大,失去正面模型的意義(第 7 章)。

直接 Active

沒經 Simulation 觀察就阻擋,第一天就會遇到「Turn It Off」的壓力。
