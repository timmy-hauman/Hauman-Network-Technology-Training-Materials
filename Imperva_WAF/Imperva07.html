講師導言

Gateway 註冊上線後,它還不知道「要保護誰」。Site Tree 就是在告訴 WAF:哪些伺服器 IP、哪些埠、哪些 TLS 金鑰、哪些 host 屬於哪個應用。 政策要套在 Site Tree 的物件上才會生效,Dynamic Profiling 也以 Web Application 為單位學習,所以這一層切得好不好,直接決定第 8、9 章能不能調得動。 很多「明明設了政策卻沒反應」的問題,根源都在這一章。

Goals 本章學習目標

  • 說出 Site、Server Group、Web Service、Web Application 四層各定義什麼、政策套在哪一層
  • 建立 Site、Server Group(含 Servers IP 與 Operation Mode)與 Web Service
  • 設定 TLS 金鑰,並判斷「模式 × TLS 版本」能不能解密
  • 設定 Host/URL 對應,決定何時該拆分 Web Application
  • 辨認 Site Tree 常見踩坑:政策不繼承、Servers 漏填、忘了 Activate

範例環境:Site HQ > SG-Shop > HTTPS-Shop > shop / member;對外網站 shop.example.com。

一、四個層級與各自的用途

用大樓來想

  • Site 像一棟大樓(機房、事業單位的分群),本身不做檢查。
  • Server Group 像一層樓的門禁:這層有哪些房間(伺服器 IP),第一道關卡在這裡。
  • Web Service 像這層的走廊與大門:哪個埠、用什麼鑰匙(TLS)進出。
  • Web Application 像房間裡的各個辦公室:哪個 host、哪條路徑,各有自己的規矩(Web Profile)。
層級定義什麼在這層生效的政策(例)
Site組織上的分群(機房、事業單位)無,純容器
Server Group一組提供相同服務的伺服器 IP、運作模式Firewall、Network Protocol Validation、Stream Signature
Web Service埠、TLS、字元集、靜態檔清單、錯誤頁、Reverse ProxyHTTP Protocol Validation、HTTP Protocol Signatures、Web Service Correlated Validation、Web Service Custom
Web Application哪些 host / URL 屬於這個應用;一個 Application 對應一份 Web ProfileWeb Profile、Web Application Signatures、Web Application Custom、Bot Mitigation、Anti Scraping

官方描述的檢查順序

流量進來時,先在 Server Group 層(第一個封包就套 Firewall 等政策),再看 Service 層的協定(例如 HTTP Protocol Validation),最後在 Application 層檢查請求本身(參數型別、長度)。政策類型細節見第 9 章。

所有 Site Tree 操作都在 Main > Setup > Sites。變更後按 Save;若系統是 delayed activation mode(延遲生效模式),還要再執行 Activate 才會生效。

四、TLS:金鑰、TLS Settings 與 SNI

WAF 要檢查 HTTPS 內容,必須能解密。現行版本分三個地方設定:

設定位置說明
伺服器金鑰(憑證 + 私鑰)Web Service > Definitions > Encryption Support(Adding TLS Keys)被動 / Bridge 模式用私鑰解密;Reverse Proxy 用它終結 TLS
Cipher、ECC、TLS 協定版本Global Objects 的 TLS Settings(v14.4 起)全域物件,可被多個 service 引用
SNIservice 的 Reverse Proxy 頁(v14.3 起)同一 IP:443 承載多個憑證時使用
HSMnCipher card / netHSM;v15 起支援 Thales Luna Network HSM【16.0】CA 版不支援 Luna / nCipher HSM

匯入金鑰步驟

  1. 1Main > Setup > Sites > SG-Shop > HTTPS-Shop > Definitions。
  2. 2在 Encryption Support 區新增 TLS Key【待實機確認:按鈕名稱】。
  3. 3上傳 shop.example.com 的憑證與私鑰(支援格式:舊簡報列 PKCS、PEM,現行格式清單【待實機確認】)。
  4. 4在 TLS Ports 填 443,按 Save。

模式決定能不能解密

實務意義

shop.example.com 若對外只開 TLS 1.3 / ECDHE,Gateway 用 Sniffing 時匯入了私鑰也解不開,告警會只剩網路層。要嘛改 NGRP / ABR,要嘛把解密交給 LB 後在 LB 與 Web 之間檢查明文(第 5 章)。

五、Error Page 與 Forwarded Connections

Error Page(Definitions 分頁 > Error Page)

選項行為
Use Default Error Page違規被阻擋時顯示預設錯誤頁
Redirect以 302 代表受保護伺服器轉址到指定 URL
Page用 HTML 加預定義 placeholder 自訂內容
HTTP Response Code錯誤頁回應的狀態碼
Web Error Page Policies依違規類型送不同錯誤頁

Sniffing 模式只能對伺服器端送 TCP reset,用戶端看不到錯誤頁(第 4 章);錯誤頁設定只在 inline 模式有意義。建議在錯誤頁放「事件編號」placeholder,讓客服能把使用者回報對應到 MX 告警【待實機確認:placeholder 名稱】。

Forwarded Connections

流量若經過 LB 或 proxy 做了 SNAT,WAF 看到的來源 IP 會全部是 LB 的 IP,信譽過濾(第 10 章)與依 IP 的告警全部失準。Forwarded Connections 用來告訴 WAF「從哪些 proxy 來的連線,真實用戶端 IP 要從哪個 header(如 X-Forwarded-For)取」【推論:依舊簡報與一般用途;現行欄位名稱與所在分頁【待實機確認】】。

為什麼要拆

一個 Application 對應一份 Web Profile。member(登入、個資、改密碼)與 shop(商品瀏覽、搜尋)的參數型態與敏感度完全不同,混在一起學會讓 profile 變得過寬(搜尋框允許任意字串,連帶讓登入欄位也放寬)。原則:

  • 參數用法或安全需求不同 → 拆 application。
  • 環境簡單、只有一個站 → 用預設 application 即可。
  • 別過度切分:每個 application 都要各自累積足夠流量才能轉 Protect(第 8 章)。

八、常見踩坑

政策不會往下繼承

官方明講,政策套在 Server Group 之後才新建的 child service 不會自動繼承該政策;新增 service / application 後要回各政策的 Apply To 分頁補勾。

LB 後擴容忘記加 IP

Servers 沒列的實 IP 流量直接不受保護,且不會有告警提醒。

忘了 Activate

delayed activation 模式下只按 Save 不會生效,常被誤判成「政策沒作用」。

匯了金鑰還是看不到 HTTPS 內容

多半是 TLS 1.3 / ECDHE 遇上 Sniffing 或 Bridge;先查 cipher 再查金鑰。

SNAT 後來源 IP 全一樣

沒設 Forwarded Connections,信譽與依 IP 的政策全部失準。

字元集用預設 Western European

中文參數可能被誤判為異常編碼【推論】。
