單元 4:部署模式

上一章 課程目錄 下一章

講師導言

裝 WAF 之前,最先要決定的不是型號,而是部署模式。模式決定 Gateway 能不能真的擋下攻擊、要不要改 IP 與 DNS、能不能回錯誤頁,還有一件今天最容易被忽略的事:能不能解開現代的 TLS 流量。 這一章先分 Inline 與 Sniffing 兩大類,再逐一認識各模式,最後用一張能力比較表收斂。請特別留意第七節,那是整套課程最重要的一個結論。

Goals 本章學習目標

  • 說出 Inline 與 Sniffing 的差別,以及 Sniffing 擋不住什麼
  • 認得 Gateway Mode 選單的四個值,並分辨 TRP、ABR 與它們的關係
  • 比較 Bridge、TRP、Reverse Proxy(NGRP)、ABR、Sniffing 的能力
  • 解釋為什麼被動模式與純 Bridge 解不了 TLS 1.3 與 ECDHE / DHE 流量
  • 依需求(阻擋、改 DNS、TLS 版本、HA、v16.0)選出合適的部署模式

本章接續第 3 章的 Gateway Group,下一章(第 5 章)再談平台、型號與 HA。

一、兩大類:Inline 與 Sniffing

用機場來想

  • Inline 像安檢門:每個人都得走過去,不合格的當場攔下,但排隊會多花一點時間。
  • Sniffing 像旁邊的監視器:不擋路、也不拖慢誰,但發現可疑的人時,人已經走進去了,只能呼叫警衛追上去。

二、現行模式一覽與 Gateway Mode 選單

在 Gateway Group 上,Gateway Mode 選單只有四個值:STP Bridge、IMPVHA Bridge、Sniffing、Reverse Proxy。 TRP 與 ABR 不是獨立選項,而是建立在這些模式上的運作方式。

三、Bridge 與 Sniffing

STP Bridge 與 IMPVHA Bridge

  • Gateway 以 L2 bridge 串在路徑上,沒有自己的資料面 IP,不必改伺服器 IP、DNS、路由,適合「不能動網路架構」的現場。
  • STP Bridge:用在既有的高可用網路,依靠交換器的 Spanning Tree 在兩台 Gateway 之間切換。
  • IMPVHA Bridge:交換器不支援 STP、STP 太複雜,或環境使用 RSTP 時,改用 Imperva 自己的 HA 機制。
  • 網路 HA 只有 bridge 模式有(Reverse Proxy 與 Sniffing 沒有),見第 5 章。
  • 硬體搭配具 bypass 能力的網卡時可設 Fail Open,Gateway 故障時流量直接通過(第 5 章)。
  • TLS 限制:只能解 TLS 1.2 的 TLS_RSA_*(靜態 RSA 金鑰交換)cipher,詳見第六、七節。
  • 自訂錯誤頁、cookie 簽章等內容改寫在純 bridge 下能做到什麼程度,這次查證的官方頁面沒有直接寫明【待實機確認】。

Sniffing

  • 交換器 SPAN 埠或 TAP 把流量複製給 Gateway;Gateway 不在路徑上,壞了也不影響網站。
  • 阻擋只能從 blocking interface 對伺服器端送 TCP reset;用戶端只會看到逾時,不能回錯誤頁,也擋不了資料外洩。
  • 適合:先導入觀察、只要監控與告警,或網路團隊不允許任何 inline 設備的環境。
  • 舊簡報的競品段落曾批評「只能 sniffing、靠 reset 阻擋」的產品擋不了單封包攻擊;同樣的限制也適用於 WAF Gateway 自己的 Sniffing 模式。
  • TLS 限制最嚴格:只能解 TLS_RSA_*,而且官方 cipher 表明確寫 DHE cipher 不支援 Sniffing。

四、Reverse Proxy(NGRP)

非透通 Reverse Proxy:用戶端連到 Gateway 的 IP,Gateway 代替後端 Web 伺服器回應,再自己連到後端。Gateway 對用戶端與伺服器都可見,用戶端與伺服器彼此不直接可見。Gateway 不當 bridge,只監聽指定的 port,其他流量一律忽略。

官方列出的優點

  1. SSL off-loading:終結 SSL,減輕伺服器負擔。
  2. 可對 cookie 簽章與加密。
  3. 可保護分散在多個子網段、彼此不相鄰的 Web 伺服器。
  4. 完整的代理功能(連線終結,含 SSL 終結)與較好的代理效能。
  5. TLS 1.3 與 ECDHE / DHE cipher 都支援(第六節)。

設定位置:Web 伺服器群組在 Main > Setup > Sites 中 Server Group 的 Definitions 頁籤、Reverse Proxy 區段指定(官方 Administration Guide)。另有 One Arm(單臂)部署方式。Web Service 層的 Reverse Proxy 設定細節見第 7 章。

KRP → NGRP

v14.1 移除 Kernel Reverse Proxy,改用 user-space 的 NGRP,主因是支援更多 cipher。代價是 X6510、X8510、X10K 這類舊機型上連線數與每秒連線數下降,從舊版升級要重新評估容量。

故障影響

官方特別註明,非透通 Reverse Proxy 的 Gateway 故障時,Web 伺服器就連不到了,所以通常要搭配 HA。Reverse Proxy 的冗餘方式是 VRRP(第 5 章)。

五、TRP 與 ABR:透通的代理

TRP(Transparent Reverse Proxy)

  • 在 bridge 部署中,只對特定 Web service 套用 TRP 規則,讓 Gateway 對這些服務做透通代理,其他服務維持一般 bridge。官方文件稱為「Transparent Reverse Proxy - Selected Web Servers」。
  • 透通:用戶端仍然連原本伺服器的 IP,不必改 DNS。
  • TLS 能力介於 bridge 與 Reverse Proxy 之間:官方 cipher 表中,部分 ECDHE_RSA / DHE_RSA 的 GCM 與 CBC-SHA256 cipher 標示支援 TRP,但 TLS 1.3 不支援 TRP。
  • 路線圖:TRP 由 ABR 取代(v15.3 Patch 20 / v15.4 更正後的說法)。新部署不要再以 TRP 為主。

ABR(Advanced Bridge,gen2)

ABR 是「支援進階 cipher 的 TRP 模式」,讓透通部署也能處理 TLS 1.3 與 PFS。

轉換方式(官方 v16.0 User Guide,v15.5 同樣適用)

  1. 1從 Bridge 模式的 Gateway 開始。
  2. 2把要保護的服務改成 TRP 規則。
  3. 3移除該 service 的 HTTP / HTTPS port 設定。
  4. 4用 impcfg 或 impctl gateway ngrp enable 啟用。
  5. 5轉換後在 MX 中顯示為 gen2。

ABR 的限制與建議

  • 限制:不支援 network violations、Discovery & Classification、一般 bridge 規則。
  • 建議:用到同一條 TRP 規則的 Gateway Group 成員全部跑 ABR,不要混用。

七、全課程重點:被動模式解不了 TLS 1.3 與 ECDHE / DHE

全課程最重要的一個結論

地端 Sniffing 與純 Bridge 只能解密 TLS 1.2 的靜態 RSA 金鑰交換(TLS_RSA_*), 無法解密 TLS 1.3,也無法解密任何使用 ECDHE / DHE(具 Perfect Forward Secrecy)的流量。 要檢查這類流量,必須改用 Reverse Proxy(NGRP)或 ABR。

【推論:由官方 cipher 表直接推得】

為什麼?

  1. 被動解密的原理:WAF 手上有伺服器私鑰,看到 TLS 握手時,用私鑰解出用戶端以 RSA 加密送出的 pre-master secret,再算出 session key。
  2. ECDHE / DHE 的 session key 由雙方臨時產生的 Diffie-Hellman 金鑰算出,臨時私鑰從不在網路上傳送;伺服器的憑證私鑰只用來簽章,拿到它也算不出 session key。這就是 Perfect Forward Secrecy。
  3. TLS 1.3 移除靜態 RSA 金鑰交換,完整握手一律用 (EC)DHE,所以所有 TLS 1.3 連線都無法被動解密。
  4. 能解密 PFS 流量的唯一方式是 WAF 自己參與握手,也就是 Reverse Proxy 或 ABR 這類「終結 TLS 再重新連線」的模式。

現場影響

  • 現代瀏覽器與伺服器預設優先使用 TLS 1.3 與 ECDHE。舊簡報「Sniffing / Bridge 匯入 SSL 憑證就能檢查 HTTPS」的做法,今天多半只能看到加密流量,等於沒有檢查。
  • 為了遷就被動 WAF 而把伺服器降級成只支援 TLS_RSA_*、關閉 TLS 1.3,會犧牲前向保密,與現行安全建議相違,不建議這樣做【推論】。

八、如何選擇模式,以及怎麼改模式

依序回答下列問題:

  1. 1計畫在支援期內升 v16.0? 是 → 只能選 Reverse Proxy 或 ABR。
  2. 2需要 WAF 自己檢查 TLS 1.3 / ECDHE 流量? 是 → Reverse Proxy 或 ABR。
  3. 3不能改 IP / DNS? 是 → ABR(TRP 將由 ABR 取代,不建議新建)。
  4. 4需要硬體 bypass(Fail Open)? 是 → 硬體 Gateway 的 Bridge 模式;要同時兼顧 TLS 1.3,就得讓 LB 先終結 TLS。
  5. 5只要監控、不允許 inline? 是 → Sniffing,但要接受第七節的 TLS 限制與「無錯誤頁、無法擋外洩」。

第 15 章會用範例環境實際走一次這個選擇過程。

改變 Gateway 模式

官方建議用 impcfg:Top > Manage SecureSphere Gateway > Change operation mode,改完按 S 存檔、A 套用。Gateway Group 的 Mode 在 MX 上只能檢視,模式不同的 Gateway 要搬到對應的群組【推論】。

十、常見踩坑

Sniffing 匯入了憑證卻看不到攻擊

流量是 TLS 1.3 或 ECDHE,被動解不開;告警少不代表沒有攻擊。先檢查連線實際協商的協定與 cipher。

以為 Sniffing 擋得住

只能對伺服器送 reset,用戶端看到逾時,單封包攻擊與資料外洩擋不了。

Reverse Proxy 只放一台 Gateway

Gateway 一掛,網站就斷,要搭配 VRRP。

從舊版 KRP 升級沒有重估容量

NGRP 在 X6510 / X8510 / X10K 上連線數下降。

ABR 與一般 bridge 規則混用

ABR 不支援一般 bridge 規則與 network violations,轉換前先盤點。

新部署仍用 TRP

路線圖已由 ABR 取代,現在就直接規劃 ABR。
