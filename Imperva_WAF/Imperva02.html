講師導言

上一章我們弄清楚了產品現在叫什麼、跑哪一版。這一章回答每個客戶都會問的問題:「我們已經有防火牆、IPS 了,為什麼還要 WAF?」 答案一句話:防火牆管的是誰可以連進來,WAF 管的是連進來之後,HTTP 請求裡面帶了什麼。 把這個定位講清楚,後面幾章的部署與調校才有意義。

Goals 本章學習目標

  • 說出 WAF 檢查的是 HTTP 請求內部(URL、參數、header、cookie、body),而不是 IP 和 port
  • 區分正面與負面安全模型,並對應到 WAF Gateway 的 Signatures 與 Dynamic Profiling
  • 說明 Virtual Patching 的三種來源與建議流程
  • 把 WAF 與網路防火牆、IPS、NGFW、CDN 的分工講清楚,知道它們是互補而不是替代
  • 判斷一個站台該用地端 WAF Gateway 還是 Cloud WAF

一、WAF 解決什麼問題

用大樓警衛來想

  • 網路防火牆像大門口的警衛:只看你的識別證(IP、port),證件對就放行,不會打開你帶進來的箱子。
  • WAF像櫃台旁的安檢:專門檢查你這次辦事送進來的文件(URL、參數、cookie、body),看內容有沒有不對勁。

網路防火牆依 IP、port 放行,對 Web 伺服器的 443 通常整個打開。攻擊者真正動手的地方在 HTTP 請求內部:URL、參數、header、cookie、body。WAF 的工作就是在這一層把請求拆開來檢查(舊簡報 p.15、p.117)。

一個請求裡,WAF 會看哪些部位

POST /member/login?lang=zh-TW HTTP/1.1        ← URL 路徑、query 參數
Host: shop.example.com                         ← 對應到哪個 Web Application
Cookie: SESSIONID=8f3a...                      ← session 追蹤、cookie 竄改
Content-Type: application/x-www-form-urlencoded

account=user01&password=********               ← body 參數(型別、長度、內容)
  • Host 決定這個請求屬於 Site Tree 中的哪個 Web Application(第 7 章)。
  • URL 與參數 對照 Web Profile:這個 URL 學過嗎?參數是必填嗎?型別與長度符合嗎?(舊簡報 p.22、p.25)
  • Cookie 與登入表單 用來追蹤 session 與使用者身分(舊簡報 p.23)。
  • 回應 也會檢查,例如回應中出現信用卡號(資料外洩)或大量相同錯誤碼(舊簡報 p.60、p.62)。

WAF 要擋哪四類請求

舊簡報 p.15 把 WAF 要擋的請求分成四類,到今天仍然適用:

與 OWASP Top 10 的關係

WAF 是降低 OWASP Top 10 風險的常見控制之一,但不是每一類都擋得住。v15.4 起 MX 提供 OWASP Top 10 報表(CA 功能,第 12 章)。下表以風險類型說明 WAF 的能力範圍,不綁定 OWASP 特定年版的編號;實際分類與編號請以 OWASP 官方最新版為準【推論】。

風險類型WAF 能處理的程度說明
注入(SQL、命令、XSS)高簽章比對 + Profile 限制參數型別與長度
身分驗證失效(撞庫、暴力破解)部分ATO、Bot Protection、Correlation;仍需帳號鎖定與 MFA

安全設定錯誤(目錄列舉、預設頁)部分Profile 擋沒學過的 URL;簽章擋已知掃描行為
使用含漏洞的元件部分Virtual Patching 爭取修補時間,不取代升級
不安全的設計、加密失效低要從程式與架構面修正

二、正面與負面安全模型

黑名單與白名單

負面模型像一張「通緝名單」:認得名單上的壞人就攔下,名單上沒有的就放行。正面模型像一張「賓客名單」:只放名單上的人進來,不在名單上的一律有問題。

項目負面安全模型(Negative / blacklist)正面安全模型(Positive / whitelist)
判斷方式比對已知攻擊特徵只允許「學到的正常行為」,偏離即違規
WAF Gateway 中的實作Signatures、ADC 內容、Emergency Feed、Threat IntelligenceDynamic Profiling 產生的 Web Profile
優點上線即生效,不需學習期能擋沒有特徵的新手法(含 0-day)
缺點擋不到沒有特徵的新手法需要學習期;應用改版時容易誤報
維護方式跟著 ADC 更新(約每兩週一次)自動學習 + 手動調整 Profile

舊簡報把 Web Profile 形容為受保護應用的「地圖」,是一種「允許什麼」的正面政策,和黑名單式的負面政策互補(舊簡報 p.20)。Profile 以 URL 為粒度,從 Learning 進入 Protect,管理者也可手動鎖定為 Protect and Lock(舊簡報 p.29;新版細節見第 8 章)。

WAF 調校的兩難

舊簡報 p.21 點出這個兩難,今天仍是維運的核心問題:

  • 太嚴:合法操作被擋,業務單位抱怨,最後要求「把 WAF 關掉」。
  • 太鬆:漏掉 0-day 與變形攻擊。

WAF Gateway 用兩個方法降低這個兩難:

  1. 自動學習並追蹤應用變更:Dynamic Profiling 依實際流量學習,應用改版後自動調整,減少手動維護。
  2. Correlation(關聯判斷):只阻擋「多個條件同時成立」的確定攻擊,降低誤擋(舊簡報 p.58–60)。現名為 Web Service Correlated Validation 與 Web Correlation Policy(第 9 章)。

建議的上線順序

先讓負面模型(簽章、協定檢查)上線阻擋明確攻擊,同時讓 Profile 學習;學習期滿、誤報調完,再讓 Profile 違規進入阻擋(第 8、15 章)。

三、Virtual Patching(虛擬修補)

Virtual Patching:應用程式真正修好之前,先在 WAF 上加一條只針對該漏洞的規則,縮短暴露窗口。舊簡報指出季度掃描只能「發現」漏洞、不能縮短暴露時間,要搭配 Virtual Patching 才有意義(舊簡報 p.15、p.121)。

三種來源

來源做法適用情境
弱點掃描結果匯入第三方掃描報告 → 建立 Scanner Integration Policy → 執行 Web Scanner Assessment Job自家網站被掃出的漏洞(第 11 章)
ADC / Emergency Feed重大漏洞時,Emergency Feed Services 先推送簽章;相關政策預設停用,需手動啟用公開 CVE、常見框架或元件漏洞(第 9 章)
自寫 Custom Policy用 Web Service Custom 等政策,依 URL、參數、header 等比對條件自寫規則掃描器不支援、或需要精準限縮範圍時

建議流程

  1. 1確認漏洞的位置:哪個 Web Application、URL、HTTP 方法、參數。
  2. 2建立規則,先只告警不阻擋,觀察一段時間確認沒有誤報。
  3. 3改為阻擋,並把規則名稱、對應漏洞編號記到變更紀錄。
  4. 4開單給開發單位修補;修好、複掃確認後移除規則,避免規則越積越多。

法規面

舊簡報以 PCI DSS 6.6 說明 WAF 的合規用途(舊簡報 p.15、p.98)。PCI DSS 之後已改版,條文編號不同,引用前請以 PCI SSC 官方正本核對【待實機確認】。Imperva 官方文件把 Client-Side Protection 定位為協助 PCI DSS 6.4.3 與 11.6.1(第 14 章)。

這張表是依舊簡報 p.117–120 的觀念、以今天的產品樣貌重新整理的技術定位,不是特定廠商的規格比較【推論】。

三個重點

  • 互補,不是替代:防火牆擋「不該來的連線」,WAF 擋「連線裡不該有的內容」(舊簡報 p.118–119)。NGFW 能辨識「這是某個 Web 應用的流量」,但不知道「這個網站的 account 參數應該是 20 字以內的英數字」。
  • 舊簡報「IPS 看不到 SSL」已不成立:今天的 IPS / NGFW 多半能設定 TLS 解密。WAF 的差異在於理解應用邏輯與學習正常行為,而不是「能不能看 SSL」【推論】。
  • CDN 與 WAF 常合在一起:Imperva Cloud WAF 本身就是部署在 CDN PoP 上的安全反向代理加 WAF(第 14 章)。

五、一個請求經過哪些防線

以範例環境為例,shop.example.com 的請求依序經過下面這些設備。各層的分工不同,缺任何一層,對應的那類風險就沒人管。

  • 負載平衡器與 WAF 誰前誰後有兩種做法,影響 Server Group 要填哪些 IP、WAF 能否處理 TLS 1.3,詳見第 5 章 5.6。
  • 前面每多一層代理(CDN、LB),WAF 看到的來源 IP 就可能變成代理的位址。信譽情資、地理封鎖都依來源 IP 判斷,所以要靠 X-Forwarded-For 這類 header 還原真實來源(第 7 章 Forwarded Connections)【推論】。

六、地端 WAF Gateway 或 Cloud WAF

考量偏向地端 WAF Gateway偏向 Cloud WAF
保護對象內部系統(如 erp.corp.example.com)、不經公網 DNS 的站台對外公開網站
TLS 金鑰與資料必須留在內網可接受 TLS 在 Imperva PoP 終結
部署限制不能改 DNS / IP,需要透通部署(Bridge、Sniffing、ABR)可以改 DNS(CNAME / A record)
大流量 DDoS另有上游對策(ISP、清洗服務)需要內建吸收能力
調校深度需要 Dynamic Profiling 細部調校希望由原廠維護規則、少調校
維運人力有人負責 MX、容量規劃、ADC 更新不想管硬體與容量
使用者分布集中在單一地區多地區,需要 CDN 加速

以上依官方文件歸納【推論】。兩者也能並用:Attack Analytics 可同時分析地端與雲端事件(統一分析,不是統一政策管理);另有 Elastic WAF 把 Cloud WAF 引擎裝進客戶自己的 Kubernetes。詳見第 14 章。

八、常見踩坑

把 WAF 當修補的替代品

Virtual Patching 是爭取時間,規則要有到期日,程式仍要修。

以為有 NGFW / IPS 就不需要 WAF(或反過來)

兩者看的層級與判斷方式不同,見第四節比較表。

一上線就全面阻擋

Profile 還沒學完就阻擋,誤報一多就被要求關掉(舊簡報 p.21)。先告警、再阻擋。

只保護對外網站

內部 ERP、會員 API 一樣是攻擊目標,尤其 API 常被忽略。

WAF 前面有 CDN / LB 卻沒還原來源 IP

封鎖、信譽判斷全部打到代理的位址,可能一次擋掉所有使用者。

拿地端 WAF 扛 L3/L4 大流量 DDoS

Gateway 有容量上限,超載時依 Overload Policy 處理(第 3 章);大流量要在上游解決。
