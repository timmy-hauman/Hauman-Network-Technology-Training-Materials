講師導言

這一章處理兩個問題:是誰在打,以及是不是機器在打。前者靠 Threat Intelligence Services(原 ThreatRadar)提供的 IP 信譽與社群防禦;後者從內建的 Bot Mitigation、Anti Scraping,一路到雲端的 Advanced Bot Protection(ABP)。 開始之前先記住兩件事:ThreatRadar 現在的文件名稱是 Threat Intelligence Services;舊簡報的 Trusteer Fraud Prevention 整合不適用於現行版本。

Goals 本章學習目標

  • 說出 Threat Intelligence Services 的四大類內容,以及它與舊名 ThreatRadar 的關係
  • 依站台敏感度,為 Reputation 情資設計分級處置,而不是「惡意 IP 一律阻擋」
  • 分辨 Bot Mitigation、Anti Scraping、CAPTCHA 與 ABP 各自適合的情境
  • 列出 ABP 整合的前提與設定流程,並知道上線初期為什麼要用 Simulation Async Mode
  • 知道 ATO 與 FPS 的現況,以及為什麼不要再規劃 Trusteer 整合

承接第 9 章的政策與 Action;連線需求見第 3 章通訊埠表。

一、Threat Intelligence Services 全貌

名稱提醒:ThreatRadar 就是現在的 Threat Intelligence Services

ThreatRadar 現在的文件名稱是 Threat Intelligence Services。部分頁面與政策名稱仍保留 ThreatRadar 字樣(例如政策類型「ThreatRadar Bot Protection」、比對條件「Client Type [ThreatRadar Bot Protection]」);GUI 與文件也仍大量出現 SecureSphere。看到舊名不代表是舊功能。

類別內容用法
Intelligence (Reputation Services)Anonymous Proxies、Comment Spam IPs、GeoLocation、IP Forensics、Malicious IPs、Phishing URLs、TOR IPs依來源 IP 信譽或地理位置告警 / 阻擋
Intelligence (Community Defense)社群共享的攻擊情資【待實機確認:現行提供的項目】
Anti Automation (Bot Protection)bot 分類(ThreatRadar Bot Protection)依 Client Type 判斷是否為自動化工具
Emergency Feed Services重大漏洞的緊急簽章見第 9 章 9.3

連線需求與授權

  • MX 經 443 連 *.impervacloud.com 取得情資;ATO、FPS 則是 Gateway 經 443 連 *.impervacloud.com(第 3 章通訊埠表)。
  • MX 不能直連網際網路時要設 proxy(External HTTP Settings)。情資停更不會有明顯錯誤,只會讓信譽資料越來越舊【推論】。
  • Threat Intelligence 為訂閱服務,啟用前確認授權包含哪些項目【待實機確認:授權項目與 GUI 啟用位置】。

二、用 Reputation 做分級處置

不建議「惡意 IP 一律阻擋」,因為誤判的代價依站台而不同。以 shop.example.com 為例,瀏覽區的 shop 和登入、改密碼的 member 就該分開處理:

情資shop(瀏覽)member(登入 / 改密碼)
Malicious IPs阻擋阻擋
TOR IPs告警阻擋或 CAPTCHA
Anonymous Proxies告警告警 + 提高其他政策敏感度
GeoLocation(非營業國家)告警依業務決定
Comment Spam IPs只對留言 / 評論 URL 阻擋—

實作方式:使用 Reputation 類政策,或在 Web Application Custom 政策中組合信譽條件與 URL 條件(第 9 章第五節)【待實機確認:Reputation 政策的類型名稱與條件名稱】。

前提:來源 IP 必須是真實用戶端 IP

Gateway 若在 SNAT 的 LB 後面,又沒有設 Forwarded Connections(第 7 章 7.5),所有請求看起來都是 LB 的 IP,信譽完全無效。

四、Advanced Bot Protection(ABP)整合

內建政策主要辨識行為與簡單挑戰。面對會換 IP、清 cookie 的大量自動化攻擊,WAF Gateway 可以整合 Imperva 雲端的 Advanced Bot Protection,由 ABP 追蹤與封鎖惡意用戶端。

前提(官方)

項目要求
版本MX 與 Gateway 皆 v14.7 以上;【16.0】CA 版也列為支援
授權購買 ABP 授權(同時取得雲端主控台存取,MX 選單會出現 Advanced Bot Protection 分頁)
DNSMX 與 Gateway 都要設好並驗證 DNS
MX 連線依 Component Communication 表可連 Imperva 雲端
Gateway 連線443 直連網際網路,或經 HTTP proxy 連 *.imperva.com、*.impervaabp.net、*.distil.ninja
Gateway 模式必須是 ABR 或 NGRP,Main > Setup > Gateways 中 Gateway 名稱旁顯示 (GEN2)

示意畫面:欄位名稱依 Imperva 官方文件,版面、按鈕位置與配色以實機為準。
  1. 1確認連線與授權:MX、Gateway 都能連到雲端服務(DNS 與 SSL);確認 Imperva 已啟用授權。
  2. 2在 MX:Main > Policies > Security > Advanced Bot Protection,啟用政策。
  3. 3在政策的 Applied to 分頁,勾選 HTTPS-Shop(必要的 service)。
  4. 4在 Advanced 分頁確認參數:
    • Ignore static resources:依 service 的靜態檔清單(字典在 Global Objects 的 file-type groups)略過靜態資源。
    • Simulation Async Mode:測試用,Gateway 不等 ABP 回應,只告警。
    • Transaction Timeout:等待 ABP 回應的毫秒數。
  5. 5按 Refresh Gateway ABP Config,讓設定同步到 Unified Management Console(UMC)。
  6. 6右上角 Save。
  7. 7在 UMC:Applications > Advanced Bot Protection > Settings > Website Groups,選該 service,進入後在 Website 區加入 shop.example.com。

怎麼驗證設好了

  1. MX 上該政策描述出現 Account ID 與 Hostname。
  2. UMC 的 ABP 服務設定中,shop.example.com 旁看得到流量(RPS)。
  3. 用瀏覽器開發者工具確認回應中已注入 ABP 的 JavaScript。
  4. 在 ABP 雲端主控台對測試網站加 block policy,MX 應出現 violation「Malicious Bot Traffic Was Detected」。

容量與隱私注意

  • 受 ABP 政策保護的請求,Gateway 要等 ABP 回應才放行,系統負載會上升;流量越大、到 ABP 的延遲越高,影響越大。上線初期用 Simulation Async Mode 觀察。
  • 送往 ABP 的流量,除了 ABP 需要的特定 header 外都會遮罩。
  • 只有被政策 Applied to 的站台才會送 ABP 檢查;站台在 ABP 主控台出現,不代表已受保護。

五、ATO 與 Fraud Prevention 現況

Account Takeover(ATO)Protection 仍以政策類型存在,分「Configuration」(蒐集資料、回報雲端)與「Enforcement」(依結果處置)兩類:

類型代表政策
Device IntelligenceATO - Device Intelligence Profiling / for failed logins / for successful logins;High Risk Login、+ Anonymous Proxy、+ TOR IP 等 Enforcement
Privileged AccountPrivileged Account Brute Force(+ Bot)Enforcement
Credential StuffingLow / Medium Risk API(登入失敗時送帳號,Medium 另送雜湊密碼);Credential Stuffing(+ Bot)Enforcement
Dictionary AttackDictionary Attack(+ Bot)Enforcement

搭配的比對條件是 Account Takeover Protection Results:Credential Stuffing 看雲端給的 Breach Risk(Low / Medium / High,High 會被阻擋);Device Intelligence 看 Profiling Done 與 Result(風險分數,官方寫明來自 iovation)。這些政策需要 Application User Tracking 先定義好登入 URL(第 8、11 章),Gateway 要能連 *.impervacloud.com:443。

Fraud Prevention Services(FPS) 仍保留架構:Snippet Injection 政策 + Web Custom 政策的 Fraud Prevention Results 條件(Provider、Tag Name、If Information is Missing)。目前可選的 provider,以及 ATO / FPS 是否仍單獨販售【待實機確認】。

舊 Trusteer 整合不適用

舊簡報描述的流程是「WAF 把瀏覽器轉址到 Trusteer、下載惡意程式檢查、結果回傳 WAF 決定放行或阻擋」。本次查閱的現行 v16.0 政策類型與比對條件頁面沒有 Trusteer,Device Intelligence 的風險來源寫的是 iovation;舊簡報列舉的惡意程式家族也早已不是現今威脅重點。

本課程與實作都不要再規劃 Trusteer 整合。帳號接管情境改用 ATO 政策,大量自動化攻擊改用 ABP。
