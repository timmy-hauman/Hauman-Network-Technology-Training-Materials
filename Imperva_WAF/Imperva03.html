單元 3:架構與元件

講師導言

前兩章講完「這是什麼產品」與「WAF 為什麼存在」,這一章開始拆開來看它由哪些零件組成。WAF Gateway 是典型的資料面 + 管理面分離架構: Gateway 負責檢查流量,MX 負責集中管理,ADC 內容與威脅情資從雲端下載。 實務上最常卡關的不是設定本身,而是防火牆沒開對埠——所以這一章最後會用範例環境,帶你列出要請防火牆管理者開的規則。

Goals 本章學習目標

  • 說出 MX、Gateway、SOM、ADC 各自在資料面或管理面的角色
  • 建立 Gateway Group,並解釋 Name、Platform、Gateway Mode、Fail Mode、Overload Policy
  • 區分 Fail Open、Fail Close、High Availability 的行為與使用限制
  • 完成 ADC 內容的手動與排程更新,並說明維護合約過期的影響
  • 依元件通訊埠表,列出範例環境要請防火牆管理者開哪些規則

一、架構總覽:資料面與管理面

用連鎖商店來想

  • Gateway 像各分店的門口檢查員:實際站在流量前面檢查、攔截。
  • MX 像總公司:規則手冊(政策、Web Profile)在這裡制定,再發到各分店。
  • SOM 像區域總部:有好幾個總公司(多台 MX)時才需要。
  • ADC 像外部研究單位:定期送來最新的黑名單與規則更新。
元件平面主要工作範例環境
WAF Gateway資料面檢查、阻擋流量;產生 violation 與告警;可直接送 sysloggw01、gw02
WAF Management Server(MX)管理面設定、政策、Web Profile、告警、報表、授權、REST APImx01
WAF Management Server Manager(SOM)管理面(上層)統管多台 MX、匯入政策範例環境不使用
ADC / Threat Intelligence 雲端服務外部簽章與政策內容、信譽情資、Bot 資料經 MX / Gateway 對外 443

二、WAF Gateway 與 Gateway Group

Gateway:實際處理流量的元件

  • 依 Gateway Group 設定的模式(Bridge、Sniffing、Reverse Proxy 等,第 4 章)運作。
  • 本身不保存政策的「正本」:政策、Site Tree、Web Profile 都在 MX 上設定,再由 MX 推送到 Gateway【推論】。
  • 首次設定用 CLI 工具 impcfg,設定管理介面 IP、所屬 MX 位址並註冊(第 6 章);官方建議改 Gateway 運作模式、網路介面也用 impcfg。
  • 要連外取得情資時(ATO、FPS、Advanced Bot Protection、Attack Analytics 上傳),可在 Gateway Group 指定 HTTP proxy(見下方 HTTP Connection)。

Fail Mode 三種選項

選項說明
Fail Open硬體故障、斷電或系統停擺時,流量照樣在兩個埠之間通過但不檢查
Fail Close故障時流量不通過 Gateway
High Availability只有 Gateway Mode 為 STP Bridge 或 IMPVHA Bridge 時可選,且每台 Gateway 還要在 impcfg 開啟(Top > Gateway > Interfaces > Toggle HA on a bridge)

Fail Open 依賴具實體 bypass 能力的硬體網卡;沒有 bypass 的虛擬機只能 Fail Close(第 5 章)。

編輯 Gateway Group

Setup > Gateways,在 Filter 窗格選 By Mode、By Platform 或 By Server Group,點選群組後在 Gateway Group Details 窗格修改,完成按 Save。Details 窗格的重要區塊:

區塊欄位用途
General InfoName、Platform名稱可改;Platform 只顯示
Topology ConfigurationMode、Fail Mode、Overload PolicyMode 在此只顯示,不能直接改(改模式見第 4 章 4.10)
Allow Ambiguous PacketsAllow IP / TCP / UDP bad checksum、TCP sequence before ISN 等放行有瑕疵的封包;預設不要動,只在排查特定網路設備問題時調整
Performance ProfilingEnable效能除錯工具,只在原廠人員要求時開啟;長時間開啟會嚴重拖慢整個群組;VMware 上不提供
GatewaysGateway Name群組成員清單(唯讀)
HTTP ConnectionAllow Gateway to Connect with Outside Systems、HTTP Proxy、Validate CertificateGateway 對外連線;HTTP Proxy 從 Main > Setup > Global Objects > Gateway HTTP Proxy 選取,適用 Attack Analytics、ABP、威脅情資等第三方服務

另有 External Logger 區塊(syslog 傳輸方式、主次主機),官方註明 WAF-only 環境不提供;WAF 的告警外送改用 Action Interface(第 12 章)。

分群原則

  • 同一群組的 Gateway 模式相同、平台相同。Bridge 與 Reverse Proxy 要分不同群組。
  • 用到同一條 TRP 規則的群組成員,官方建議全部跑 ABR(第 4 章)。
  • 舊教材的「Gateway cluster」在 WAF v15.5 / 16.0 文件查無此功能名;WAF 的冗餘靠 Gateway Group 加上網路 HA 或 VRRP(第 5 章)。

三、WAF Management Server(MX)與 SOM

MX 的職責

舊簡報 p.39 列出的 MX 職責,今天大致不變:

職責說明
統一管理多台 Gateway所有 Gateway Group 與 Gateway 都在 MX 上管理
保存 Profile 與政策Site Tree、Web Profile、安全政策、Action Set 都存在 MX
告警、稽核與鑑識Alerts、Violations、Audit 集中查詢(第 12 章)
Web 管理介面瀏覽器連 https://10.0.30.10:8083
Role-based 管理依角色分權;【15.5】v15.4 起 SSO 改版,支援 SAML metadata、JIT、SLO
授權MX 與其管理的所有 Gateway 的授權都裝在 MX 上(見第四節)

新版另外增加:

  • REST API(WAF API Reference Guide):以 Basic Auth 登入取得 JSESSIONID cookie,閒置 30 分鐘逾時(第 12 章)。
  • 系統事件記錄(v15.0 起):記錄誰在什麼時候改了什麼。
  • Attack Analytics 匯出:把地端告警送到雲端分析(第 12 章)。

MX 停機時 Gateway 是否繼續以最後一版政策檢查流量,這次查證的官方頁面沒有明寫【待實機確認】。MX 的備援(MX-HA)見第 5 章。

SOM(WAF Management Server Manager)

  • 用途:統管多台 MX,適合多資料中心、多套 MX 的大型環境。只有一台 MX(如範例環境)就不需要 SOM【推論】。
  • v15.5 的 SOM 文件目錄涵蓋:瀏覽器支援、與舊 SOM 的相容性、註冊 MX(Registering MXs)、元件間通訊、匯入安全與稽核政策(Importing Security and Audit Policies)、ThreatRadar 相關操作。
  • 通訊:MX 與 SOM 之間雙向 TCP 8084;啟用 Trusted Connections 後另用 TCP 8085(見第五節)。
  • SOM 和 MX 一樣不能混管 WAF 與 DAM。
  • 【16.0】CA 版不支援 SOM。

四、ADC 內容更新與授權

ADC(Application Defense Center)是原廠研究團隊,也是內容更新的名稱:簽章、預先定義的政策與 correlation 規則、良性搜尋引擎清單等都隨 ADC 內容下載(舊簡報 p.60、p.92)。ADC 內容約每兩週發布一次。

手動更新(MX 無法直接上網時)

  1. 在 Admin 工作區按 ADC。
  2. 在 Manual ADC Update 下按 Download,存下 .mprv 檔(離線環境改從原廠知識庫說明的位置下載)。
  3. 用 Browse 選擇該檔,按 Upload。
  4. 部分更新要 Apply Settings 之後才生效。

排程自動更新

  1. Admin 工作區 > ADC。
  2. 在 Automatic ADC Update 選 Recurring,設定排程。
  3. 要立即更新按 Update Now。

ADC 更新成功的前提

  • Default Gateway 與 DNS 必須先用 impcfg 設好,ADC 更新才會成功。
  • 需要經 proxy 上網時,依官方 External HTTP Settings 設定。
  • MX 要能連 www.imperva.com:443(見第五節)。
  • 授權中的 Maintenance period 決定可以下載 ADC 內容的期間;維護合約過期,ADC 更新就停了。
  • Emergency Feed Services:重大漏洞時先推送簽章,相關政策預設停用,要手動啟用(第 9 章)。

授權

授權檔裝在 MX 上,涵蓋 MX 與它管理的所有 Gateway;續約時新授權會整份取代舊授權。

  • 【15.5】v15.5 Patch 10 新增不設吞吐上限的「CLOUD」虛擬型號,限 AppProtect / Flex Protect 授權,依 CPU 擴展(第 5 章)。
  • 上傳授權的 GUI 路徑【待實機確認】。

六、動手玩:防火牆開埠檢查

下面是上一節要請防火牆管理者開的規則。取消勾選代表「防火牆沒開」,看看哪些元件之間的通訊會斷、造成什麼後果。你也可以假設管理者電腦、Splunk 或 MX 與 Gateway 被放在不同網段,看看多出哪幾條規則。

防火牆實際放行的規則

網段假設

範例環境的管理者電腦、Splunk、MX 與 Gateway 都在 10.0.30.0/24,不會是這種情況;勾選後會多出 4 條規則:管理者連 MX、送 Splunk、Gateway ↔ MX 的兩條。

七、常見踩坑

ADC 一直更新失敗

多半是 impcfg 沒設 Default Gateway 或 DNS,或防火牆沒放行 www.imperva.com:443。

維護合約過期沒人發現

授權本身不限時,Gateway 照常運作,但 ADC 內容停在舊版,新漏洞的簽章進不來。

在 Details 窗格找不到改 Gateway Mode 的地方

Mode 在群組建立後只顯示,改模式要走 impcfg(第 4 章 4.10)。

Bridge 與 Reverse Proxy 的 Gateway 放同一群組

Gateway Mode 是群組屬性,模式不同要分群組。

隨手開 Performance Profiling

會拖慢整個群組,只在原廠要求時短暫開啟。

只開 *.impervacloud.com 卻漏了 thr-auth.service.imperva.com

v15.5 通訊表另外列出這個網域,情資驗證會失敗【推論】。
