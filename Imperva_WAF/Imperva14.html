講師導言

前面 13 章,我們都在談機房裡的 WAF Gateway。這一章換個角度:如果不想放設備,只要改 DNS,就能把網站交給 Imperva 全球各地的節點(PoP)代為擋攻擊,這就是 Cloud WAF。它聽起來很簡單,但「DNS 怎麼改」和「origin 怎麼保護」做錯,雲端防護就形同虛設。 這一章也會教你判斷:什麼網站該上雲、什麼該留在地端,或是兩者並用。

Goals 本章學習目標

  • 說明 Cloud WAF 的運作方式:DNS 導流、PoP 反向代理、TLS 在 Imperva 終結
  • 依網域型態決定 DNS 設定:子網域用 CNAME、裸網域用兩筆 A 記錄
  • 做好 origin 保護:防火牆只允許 Imperva IP,清單以官方 API 為準,不寫死
  • 比較 Cloud WAF 與 WAF Gateway,並依情境選擇雲端、地端或混合架構
  • 說出混合架構 B(Cloud WAF 串接 WAF Gateway)要特別處理的真實 IP 問題

本章是前 13 章地端 WAF Gateway 的延伸;第 15 章綜合實作會回頭引用本章的架構 B。

一、Cloud WAF 是什麼:不放設備,改 DNS

用「總機轉接」來想

  • 地端 WAF Gateway 像在自家大門口加一道安檢門:設備放在你的機房,流量從你家門口進來。
  • Cloud WAF 像把公司電話改成先轉到專業總機:所有訪客先打到總機(Imperva PoP),檢查過才轉給你,你只要改「電話簿」(DNS)。

名稱小卡

名稱說明
Imperva Cloud WAF雲端 WAF 服務,前身 Incapsula
Cloud Application Security產品線名稱,也併入了 Distil 的 Bot 技術
Web Protection文件中對「網站防護」服務的稱呼
Cloud Security Console雲端管理主控台(my.imperva.com)

運作方式:一個請求怎麼走

Cloud WAF 把網站的 DNS 改指向 Imperva 提供的位址,訪客依所在位置被解析到最近的 PoP。每個請求都在 PoP 終結,由反向代理做 WAF、DDoS 防護與 CDN,檢查通過才轉送到 origin(來源伺服器)。

  1. 1DNS 導流:網站的 DNS 改指向 Imperva 提供的 CNAME(例如 mysite.incapdns.net),依訪客位置解析到最近的 PoP。
  2. 2反向代理:每個請求都終結在 PoP,檢查通過才轉送到 origin。
  3. 3TLS 在 Imperva 終結:Imperva 代理上必須有憑證,使用者看到的是 Imperva 端憑證;origin 上的憑證另外保留。
  4. 4可限制 PoP:有資料駐留法規需求時,可限制只用特定 PoP。

和地端 WAF Gateway 最大的差別

Cloud WAF 只能保護「能透過公網 DNS 導流」的網站。內部系統如 erp.corp.example.com 不適用,請留給 WAF Gateway。

二、動手做:把 shop.example.com 接上 Cloud WAF

以範例環境的 shop.example.com 為例,使用新版精靈(官方文件 Onboard a Website)。

事前準備

  • 帳號權限:用 Imperva 受管站台憑證接入,需要 Add Sites 與 Manage SSL Certificates 兩項權限;不含憑證只需要 Add Sites。
  • 能修改 example.com 的 DNS。
  • 確認 origin:shop.example.com 目前對外 VIP 為 203.0.113.20。

示意畫面:部分英文欄位名稱待實機確認(Domain 填完整網域;Origin 填 IP 或 CNAME;Traffic Routing 為導流步驟),版面、按鈕位置與配色以實機為準。
  1. 1在 Cloud Security Console 進入 Application > Websites > Add website,輸入完整網域 shop.example.com。
  2. 2系統會嘗試自動找 origin;也可以手動填 origin IP 或 CNAME。若 origin 是會變動 IP 的負載平衡器 CNAME,要手動填 CNAME。
  3. 3SSL/TLS:依精靈指示新增一筆 DNS CNAME 記錄驗證網域所有權,由 Imperva 簽發受管站台憑證。注意:用站台憑證接入的網站不支援 non-SNI 用戶端;需要支援 non-SNI 要改用舊版精靈與帳號憑證。
  4. 4導流:子網域(shop.example.com、www.example.com)把 DNS 改成 CNAME 指向 Imperva 給的位址;裸網域(example.com)則設定 Imperva 給的兩筆 A 記錄。
  5. 5保護 origin:origin 防火牆只允許 Imperva IP(第三節)。
  6. 6完成:DNS 依 TTL 在 5 分鐘到 24 小時內逐步切換。

切換建議

  • 正式切換前幾天先把 DNS TTL 調低,切換後確認穩定再調回。
  • 切換期間同時有「直連 origin」與「經 Imperva」兩種流量,第 5 步的 origin 限制要在 DNS 完全生效後才收緊,否則會擋掉尚未切換的使用者【推論】。
  • 大量站台可改用 Terraform 接入(官方有 Terraform 文件)。

三、Origin 保護:一定要做的一件事

為什麼一定要做

攻擊者只要知道 origin 真實 IP,就能繞過 Cloud WAF 直接打 203.0.113.20。所以 origin 前的防火牆必須只接受 Imperva PoP 的來源 IP。

IP 清單從哪裡來

  • 官方 KB 列有 Cloud WAF 的 IP 段(IPv4 十餘段加 IPv6,例如 199.83.128.0/21、2a02:e980::/29)。IP 段以官方 API 為準,本教材不列完整清單,也不要把任何一份清單當固定值寫死在防火牆。
  • 官方 API 可取得 json、apache、nginx、iptables 等格式的最新清單,位址如下: 
    https://my.imperva.com/api/integration/v1/ips
    呼叫方式與驗證需求【待實機確認】。

建議做法

  1. 1用排程腳本定期呼叫官方 API 取清單,與現有防火牆物件比對;有差異時通知管理者審核後更新。
  2. 2防火牆物件命名如 OBJ-Imperva-CloudWAF(IP 段以官方 API 為準),origin 的 443 規則只允許此物件。
  3. 3注意 SIEM 記錄:官方公告 Cloud WAF 送 SIEM log 的舊來源 IP 已於 2026 年 8 月底退役,改用 Cloud WAF IP;接收端白名單也要跟著更新。
  4. 4已用 origin IP 限制後,origin 看到的來源 IP 都是 Imperva;真實用戶端 IP 要從 Imperva 帶入的 header 取得,應用程式與記錄要配合調整(header 名稱【待實機確認】)。

五、Cloud WAF 與 WAF Gateway 比較

兩者不是誰取代誰,而是各有擅長的場景。先看完整比較,再看第七、八節怎麼選。

比較項目Cloud WAFWAF Gateway(地端)

六、Elastic WAF 與混合架構

Imperva Elastic WAF

把 Cloud WAF 引擎做成容器版,裝在客戶自己的 Kubernetes,由 Cloud Security Console 集中管理。官方定位是讓雲端與自建環境有一致的體驗。適合應用程式已經跑在 Kubernetes、又希望用 Cloud WAF 規則與主控台的情境。

常見混合架構(以範例環境說明)

架構做法適合
A. 分工shop.example.com 走 Cloud WAF(DDoS + CDN);api.example.com 與 erp.corp.example.com 由 WAF Gateway 保護對外網站要抗 DDoS,API 與內部系統要細部政策
B. 串接Cloud WAF → origin 設為 WAF Gateway 前的 VIP 203.0.113.20 → GG-Shop → LB 10.0.10.20需要雲端 DDoS 吸收,又要保留地端 Dynamic Profiling 與資料留存
C. 統一分析兩邊告警都送 Attack Analytics想要單一事件檢視

架構 B 長什麼樣

架構 B 的注意事項

  • WAF Gateway 看到的來源 IP 全是 Imperva PoP。要讓地端政策、IP Block、報表以真實用戶端 IP 運作,Gateway 必須依 Imperva 帶入的 header 取得原始 IP;設定位置【待實機確認】。
  • 地端 IP 類政策(例如 IP Block)若沒設定好,會一次封鎖整個 PoP 位址,影響大量正常使用者。
  • 兩層都做 TLS:Imperva 一張憑證、地端 Gateway 一張。

目前限制

Attack Analytics 提供的是統一分析,不是統一政策管理;MX 與 Cloud Security Console 仍是兩套管理介面。能否在單一主控台同時管理兩邊政策,目前查不到官方說明【待實機確認】。

九、常見踩坑

沒做 origin IP 限制

Cloud WAF 形同虛設,攻擊者直連 origin。

把 IP 清單寫死

Imperva IP 段會調整,清單要以官方 API 定期更新。

太早收緊 origin

DNS 還沒全部切換就只允許 Imperva IP,TTL 內的使用者連不上。

non-SNI 用戶端連不上

用站台憑證接入不支援 non-SNI,老舊用戶端或設備要改用帳號憑證接入。

origin 是會變動 IP 的 LB

沒手動填 CNAME,origin IP 變動後 Imperva 轉送失敗。

串接架構沒處理真實 IP

地端 WAF 把 Imperva PoP 當攻擊者封鎖。
