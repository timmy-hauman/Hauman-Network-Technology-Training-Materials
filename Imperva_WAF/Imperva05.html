講師導言

模式選好之後,現場最常被問到的是:「跑在哪裡?買多大的?放負載平衡器前面還是後面?壞了怎麼辦?」這一章就是把這些問題一次回答完。 我們會看現行的 7G 硬體、上一代的生命週期、虛擬與公有雲支援,再把舊簡報「WAF 放 LB 前或後」的觀念,依 TLS 1.3 時代更新。最後用一個小幫手,輸入你的條件就能得到型號與 HA 建議。

Goals 本章學習目標

  • 列出選型要考慮的項目,並看懂 7G 硬體規格表
  • 說出 6G、5G 的生命週期,以及哪些舊機型不能升 v16.0
  • 分辨虛擬機與各公有雲在 v15.5 與 16.0 的支援差異
  • 比較 WAF 放在 LB 之前與之後的差別(TLS、來源 IP、Server Group)
  • 說明 Fail Open、Fail Close、High Availability 的行為與限制
  • 依模式選擇備援方式:STP / IMPVHA、VRRP、MX-HA

本章承接第 4 章的部署模式,完成後即可進入第 6 章安裝。

四、放在負載平衡器之前或之後

舊簡報比較過 WAF 放在 LB / Cluster VIP 之前與之後的差異。觀念仍然正確,但 TLS 1.3 普及後,「WAF 放 LB 前面、用 bridge 匯入憑證解密」這條路多半已經走不通(第 4 章第七節)。

項目A:WAF 在 LB 之前B:WAF 在 LB 之後
WAF 看到的目的位址LB 的 VIP各節點的實體 IP
Server Group 要列的 IPVIP;Bridge / Sniffing 時可能還要納入節點實體 IP每個節點的實體 IP;擴容新增節點時要記得加
WAF 看到的來源 IP真實用戶端 IP(前面沒有其他代理時)LB 若做 SNAT,看到的是 LB 位址,要靠 X-Forwarded-For 還原
TLS 由誰處理WAF 必須自己處理對外憑證;TLS 1.3 / PFS 要 Reverse Proxy 或 ABRLB 終結 TLS 後,WAF 可能看到明文而不必匯入憑證,或由 LB 重新加密
LB 對 session 的操作不影響 WAFLB 插入的 cookie、改寫的 header 會進入 Web Profile,要在學習時排除
WAF 故障的影響整個站台(視 HA 設計)LB 健康檢查可以把故障路徑拿掉【推論】

官方 Administration Guide 也有「Reverse Proxy with Load Balancer」的部署範例。選哪一種要看 TLS 由誰終結、來源 IP 怎麼保留、LB 團隊與 WAF 團隊怎麼分工;第 15 章以範例環境實際做一次決定。

示意畫面:欄位名稱依 Imperva 官方文件,版面、按鈕位置與配色以實機為準。
  1. 1Main > Setup > Gateways 新增群組,Name 填 GG-Shop。
  2. 2Gateway Mode 先決定(第 4 章),Fail Mode 的可選項目會受它影響。
  3. 3Fail Mode 依下表選 Fail Open、Fail Close 或 High Availability。選 High Availability 時,每台 Gateway 還要在 impcfg 開啟:Top > Gateway > Interfaces > Toggle HA on a bridge。
  4. 4Overload Policy 勾選 Block on Overload:超過 Gateway 容量時封鎖所有連線,直到流量下降。
  5. 5按 Create,再按 Save。
Fail Mode故障時的行為適用限制
Fail Open硬體故障、斷電、系統停擺時,流量照樣通過,但不檢查可用性優先的 bridge 部署需要具實體 bypass 的硬體網卡;VM 不支援
Fail Close故障時流量不通過 Gateway安全優先,或搭配上游備援VM 唯一選項
High Availability由網路 HA(STP / IMPVHA)處理切換兩台 bridge Gateway 的備援只有 STP Bridge / IMPVHA Bridge 可選;每台 Gateway 要在 impcfg 開啟 Toggle HA on a bridge

選擇原則

  • 電商網站通常寧可短暫不檢查,也不要整站斷線,傾向 Fail Open;但要有監控,Gateway 一進入 bypass 就告警【推論】。
  • 合規要求「未經檢查不得放行」的系統選 Fail Close,並搭配兩台 Gateway 的備援。
  • Fail Mode 處理的是 Gateway 本身故障;Gateway 正常但流量超過容量時,看的是 Overload Policy(Block on Overload)。兩者要一起規劃。沒勾 Block on Overload 時超載流量會怎麼處理,官方這頁沒寫【待實機確認】。

六、備援:網路 HA、VRRP 與 MX-HA

網路 HA:STP 與 IMPVHA

  • 只在 bridge 模式(STP / IMPVHA)可用,Reverse Proxy 與 Sniffing 沒有網路 HA。
  • STP Bridge:兩台 Gateway 分別串在兩條路徑上,由交換器的 Spanning Tree 決定哪條路徑在用、故障時切換。
  • IMPVHA Bridge:交換器不支援 STP、STP 太複雜或環境使用 RSTP 時使用。
  • 介面支援(官方 Network High Availability Support 表):
介面類型G-SeriesX-Series
Copper支援支援
1 G不支援支援
10 G不支援不支援
10 G with Bypass Support不支援支援

表中「1 G」所指的介面種類(推測為光纖)官方未說明【待實機確認】;10G 介面要選有 bypass 支援的型號才能做網路 HA。

非對稱路由

舊簡報提醒兩台 bridge Gateway 之間不同步狀態,而且非對稱路由有害(去程走 gw01、回程走 gw02,兩台都只看到一半)。新版是否仍無狀態同步,這次查證未找到官方說明【待實機確認】;非對稱路由的問題在所有 inline 檢查設備上都存在,規劃時要確保同一連線的去回程走同一台【推論】。

VRRP:Reverse Proxy 的備援

  • 適用於 Gateway 有自己的 IP、以非透通 Reverse Proxy 運作的部署;bridge 與 TRP 不適用。
  • 做法:把 Reverse Proxy 監聽用的 alias 設為 virtual(官方說明見 Configuring Aliases)。alias 的 GUI 位置與欄位名稱【待實機確認】。
  • 官方建議:若 VRRP 切換時出現長時間中斷,把兩台的 virtual router 都設為 Backup(不要設 Master)。
  • 範例環境:gw01、gw02 同屬 GG-Shop、以 Reverse Proxy 運作時,兩台共用一個 VRRP 虛擬位址作為服務入口(位址依第 15 章的網路規劃,本章不另定),由防火牆把 203.0.113.20:443 轉到這個虛擬位址【推論】。
  • 【16.0】CA 版的 Gateway HA 只有 VRRP。

MX-HA

MX-HA:兩台 MX 組成主動 / 備援,主機故障時自動切換。官方列出的元件:

元件用途
Linux Heartbeat兩台 MX 之間的存活偵測與切換
Oracle Standby Database(Data Guard)資料庫同步到備援機
SecureSphere ServerMX 服務本身
HA Health Check健康檢查
Imperva Watchdog監看並重啟服務
  • 不支援 Hyper-V、GCP、Azure;【16.0】CA 版完全不支援 MX-HA。
  • 官方文件分成 Overview、Implementation、Co-Locating、Components、安裝前 / 安裝 / 安裝後、Monitoring、Maintaining 等章節;安裝細節與兩台 MX 之間需要開放的埠,這次未查證【待實機確認】。
  • 範例環境只有 mx01。要做 MX-HA 時,第二台 MX 另配管理網段 10.0.30.0/24 的位址。
  • 沒有 MX-HA 時,至少要有定期備份與還原演練(第 13 章)。

以 shop.example.com 為例,進入安裝(第 6 章)前應該決定好:

  1. 1部署模式:Reverse Proxy、ABR、Bridge 或 Sniffing(第 4 章第八節)。
  2. 2TLS 由誰終結:WAF 或 LB;決定第四節的 A 或 B。
  3. 3平台與型號:硬體或 VM、型號、Gateway 台數(gw01、gw02)。
  4. 4Fail Mode 與 Overload Policy。
  5. 5Gateway 備援方式:網路 HA(bridge)或 VRRP(Reverse Proxy)。
  6. 6MX 備援:MX-HA 或備份還原。
  7. 7授權:傳統或 FlexProtect;Gateway 模組數量;維護期。
  8. 8防火牆規則:依第 3 章開好 ADC、情資、Syslog、DNS、NTP 的連線。
