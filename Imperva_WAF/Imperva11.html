講師導言

前面幾章把「站台怎麼掛上去、怎麼學、怎麼擋」都講完了。這一章收錄五個進階功能:用外部資料豐富比對條件的 Lookup Data Sets、追蹤登入者身分的 User Tracking、在記錄裡遮蔽敏感資料的 Data Masking、把弱點掃描結果轉成防護的 Web Scanner 整合,以及把 WAF Gateway 當成 API 流量感測器的 API Security Anywhere sensor。 它們都不是上線第一天必須開的功能,但碰到基本政策處理不了的情境時,就是你的備用武器。

Goals 本章學習目標

  • 說出五個進階功能各自解決什麼問題、需要什麼前提
  • 建立 Lookup Data Set,並說明為什麼名單要有擁有者與更新週期
  • 說明 User Tracking 如何判斷登入成功與失敗,以及為什麼上線前要用測試帳號驗證
  • 分辨 Sensitive Data Dictionaries 與 Masking Data in Elements,並知道 Data Masking 只影響 WAF 自己的記錄
  • 描述 Web Scanner 整合的三個步驟,以及 Virtual Patching 的定位
  • 說出 API Security Anywhere sensor 的工作模式限制與預設值

一、功能地圖:五個進階功能

功能解決什麼問題前提現況
Lookup Data Sets(查詢資料集)政策要比對「名單」或「外部屬性」(例如合作夥伴 IP、停權帳號)無,屬 Global Object(全域物件)仍存在,有預設資料集與 REST API
Web Application User Tracking(應用程式使用者追蹤)告警裡要看到「哪個帳號」而不只是 IP;依帳號封鎖網站有表單登入仍存在;Universal User Tracking (UUT) 已於 v14.2 移除
Data Masking(資料遮罩)告警與稽核記錄不能留下密碼、卡號等敏感資料無仍存在
Web Scanner 整合弱點已被掃到、程式還沒修,先用 WAF 擋(Virtual Patching,虛擬修補)支援的第三方掃描器報告仍存在
API Security Anywhere sensor需要 API 盤點、BOLA 等 API 專屬防護地端 Controller;Gateway 跑 NGRP 或 ABRv15.3 Patch 10 起;v15.4 起強化

二、Lookup Data Sets:讓政策去「查名單」

用門口的訪客名冊來想

警衛只看來客的臉,沒辦法知道他是不是合作夥伴。但手邊有一本名冊,拿來客的名字去查,就知道該不該放行。Lookup Data Set 就是那本名冊。

Lookup Data Set 是一張「鍵值 + 屬性」的表。政策比對時,用請求裡的某個值(例如來源 IP、帳號)去查表,取回屬性再判斷。它讓「只靠請求本身資訊做不到」的政策變得可行,舊簡報稱之為 Data Enrichment(資料豐富化)(舊簡報 p.69–70)。

建立來源

依官方 Creating a Lookup Data Set。

來源適用情境
Manually筆數少、變動少的名單(例如 5 個合作夥伴 IP)
From a CSV File由其他系統匯出的清單,定期重新匯入
From ThreatRadar威脅情資服務使用的資料集(見第 10 章)
From an External System直接連資料庫或外部系統抓資料
From ADC Template由 ADC 維護的範本(標準資料庫結構、LDAP 資訊)

預設資料集(節錄,WAF 相關)

名稱用途
IP Addresses of Known Anonymous Proxies已知匿名代理 IP;屬威脅情資的一部分,由 ADC 自動更新
User Roles - From Active Directory (no domain / with domain)從 LDAP 取使用者、部門、群組,讓告警與報表顯示易讀的使用者名稱;需先在 Query 頁指定 External System

其餘預設資料集(如 Default Database Account Mapping)屬資料庫稽核用途,WAF 用不到。

實務建議

  • 名單要有「擁有者」與更新週期。CSV 匯入是一次性的,來源系統更新後要重新匯入,否則政策會依過期資料判斷。
  • 資料集也能透過 REST API 維護(WAF API Reference Guide 有 Lookup Data Set 相關方法),適合讓會員系統在停權時自動推送(REST API 登入方式見第 12 章)。
  • 舊簡報寫上限為 1 百萬筆(舊簡報 p.69);現行版本的筆數上限未查到官方數字【待實機確認】。大型名單先在測試環境確認匯入時間與 MX 負載。

三、Web Application User Tracking:告警裡看得到「是誰」

WAF 預設只知道 IP 與 session。啟用 User Tracking 後,Gateway 會辨識「登入動作」:哪個 URL 是登入表單送出的位置(Action URL)、哪個欄位是帳號、登入成功或失敗。之後同一個 session 的違規告警就會帶上使用者名稱,並可對「使用者」做監控或封鎖(Action Interface 的 User Monitor、User Block,見第 12 章)。

設定步驟

  1. 1先讓 member 應用程式學習至少一段時間,確認 Web Profile 已出現 /member/login。
  2. 2在 Site Tree 選 member 應用程式,開啟 User Tracking 相關設定頁【待實機確認】。
  3. 3若系統沒有自動學到,手動指定 Action URL、帳號欄位(email),以及成功的判斷條件(導向 /member/home 或回應碼 302)【待實機確認】。
  4. 4以測試帳號各做一次成功與失敗登入,到 Web Profile – Web Application User Tracking 報表確認 Login Result 判斷正確。

注意

密碼欄位雖然會被識別,但一定要搭配下一節的 Data Masking,避免密碼值出現在告警明細。

四、Data Masking 與敏感資料字典

WAF 告警會記錄觸發違規的參數值。如果違規剛好發生在登入或結帳頁,記錄裡可能出現密碼、信用卡號、身分證字號。Data Masking 讓這些值在寫入 SecureSphere 記錄前就被換成星號。官方說明:遮罩後原始資料從記錄中刪除且無法取回,星號數等於被隱藏的位元組數。

兩種做法

官方 Configuring Sensitive Data Protection。

做法比對依據範例
Sensitive Data Dictionaries(敏感資料字典)值的樣式(pattern)信用卡號、美國社會安全碼等預設樣式;也可自訂
Masking Data in Elements(依元素遮罩)參數/元素名稱password、cvv 不管內容是什麼都遮

字典可以被政策引用,也可以直接掛在 service 上;字典以 Sensitive Data Dictionary Groups 管理,依元素遮罩則用 Data Masking List 管理。

範例環境建議清單

類型項目理由
依元素遮罩password、new_password、cvv、otp欄位名固定,用名稱比對最準
字典信用卡號(預設)卡號可能出現在任何參數
自訂字典台灣身分證字號樣式(1 碼英文 + 9 碼數字)預設字典以美國格式為主,需自訂【推論】

要分清楚的三件事

  • Data Masking 只影響「WAF 自己的記錄」,不會改動送往伺服器或回給使用者的內容。
  • 若要「阻擋回應中洩漏的敏感資料」,屬於政策層面的偵測(字典被政策引用),而且必須是 inline 模式;Sniffing 模式無法阻擋資料外洩(見第 4 章)。
  • 權限:使用者只能檢視或修改自己有 Edit 權限的字典,分權管理時要留意。

五、Web Scanner 整合與 Virtual Patching

弱點掃描找到 SQL injection 之後,程式修補、測試、上線常要數週。這段期間,WAF 可以依掃描報告產生針對性政策先擋住,這就是 Virtual Patching(虛擬修補)。

官方流程三步驟

步驟動作說明
1Run a Scan and Prepare Results用支援的第三方掃描器掃描,匯出結果檔
2Create a Scanner Integration Policy匯入掃描結果,建立整合政策
3Run Web Scanner Assessment Job執行評估工作,對掃到的弱點產生防護

範例:/member/orders?id= 有 SQL injection

對 shop.example.com 掃描後發現 /member/orders?id= 有 SQL injection。

  1. 1掃描範圍限定 https://shop.example.com/member/,並在掃描期間把掃描來源 IP 設為 Learning Exception,避免掃描流量污染 Web Profile(見第 8 章)。
  2. 2建立 Scanner Integration Policy,匯入結果檔,套用對象指定 SG-Shop > HTTPS-Shop > member。
  3. 3執行 Web Scanner Assessment Job,檢查產生的防護政策與對應弱點。
  4. 4開發修好之後重新掃描、重新匯入,確認該弱點已不在清單。

注意事項

  • 套用對象要對到正確的 Site Tree 節點,否則產生的政策掛錯地方等於沒有防護(舊簡報 p.88 的「Apply To」提醒仍適用【推論】)。
  • 舊簡報列出的掃描器清單(舊簡報 p.84)多家廠商已併購或改名;現行文件仍保留 WhiteHat Sentinel 章節,完整支援清單與報告格式【待實機確認】。
  • Virtual Patching 是爭取時間,不是修補。追蹤表上要同時記錄「WAF 已防護」與「程式預計修補日」。

六、API Security Anywhere sensor

WAF 擅長擋「攻擊」;API 安全產品擅長「理解 API」(盤點有哪些 endpoint、哪些欄位含敏感資料、是否存在 BOLA 這類授權缺陷)。API Security Anywhere 的做法是讓 WAF Gateway 當感測器(sensor),把非惡意流量(request 與 response)複製給地端的 Controller 分析。

架構重點

官方 Integration with API Security Anywhere。

元件說明
API Security Anywhere Controller以 Kubernetes 為基礎,可裝成獨立 VM 或放在 Kubernetes 叢集;建在 WAF 旁邊
WAF Gateway(sensor)轉送非惡意的 request + response;每個 Gateway Group 一組 sensor 設定
MX設定政策,填入 Controller 與 sensor 資訊
管理介面Cloud Management Console 管 Controller/sensor;API Management Console(雲端或自管)管 API 盤點

連線建立順序

連線分預設的安全模式與 insecure 模式;安全模式需要在 Controller 與 WAF 兩端額外設定 ingress controller 或負載平衡器。

限制與預設值

  • 只支援 ABR、NGRP 兩種工作模式;Bridge、Sniffing 的 Gateway Group 不能當 sensor(模式說明見第 4 章)。
  • 每個 Server Group 與 Gateway Group 只能有一個政策。
  • Gateway 預設最多送 1000 RPS 或 200 Mbps 給 Controller,可用 Gateway 進階設定調整。
  • Gateway CPU 達預設 90% 時暫停 API 流量轉送,降到 85% 才恢復,以確保 WAF 本業優先。
  • v15.4 起可依 application 粒度設定轉送、預設只送 API 流量,並可接收 Controller 回傳的 BOLA 阻擋決策。

範例環境規劃:api.example.com(203.0.113.21 → 10.0.10.31)若要納入,GG-Shop 必須跑 NGRP 或 ABR;Controller 放在管理網段旁的獨立網段,gw01、gw02 要能連到 Controller 的接收埠(埠號依 Controller 部署方式,【待實機確認】)。

八、常見踩坑

            

                
Lookup 名單過期

                
CSV 匯入後就沒人更新,停權已解除的會員還是被擋。名單要排程或用 API 同步。

            

            

                
User Tracking 判斷錯誤

                
網站登入失敗也回 302(例如導回登入頁加參數),系統把失敗當成功。上線前一定要用測試帳號驗證成功與失敗各一次。

            

            

                
只開 User Tracking、沒開遮罩

                
密碼欄位值出現在告警明細,稽核反而變成洩漏點。

            

            

                
誤以為 Data Masking 會改流量

                
它只遮 WAF 的記錄;要阻擋回應中的敏感資料外洩,要靠政策,而且要 inline 模式。

            

            

                
掃描流量污染 Profile

                
弱點掃描期間沒設 Learning Exception,Web Profile 學到大量攻擊性參數值。

            

            

                
Bridge 模式想接 API Security Anywhere

                
sensor 只支援 ABR、NGRP,要先規劃模式轉換(見第 4 章)。
