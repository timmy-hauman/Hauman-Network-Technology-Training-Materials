二、步驟一:規劃與防火牆 (第 2 章、第 3 章)

先確認 WAF Gateway 是對的工具:網站需要 L7 防護與正面模型;內部 ERP 未來也可能納入;需求表沒有大流量 DDoS,所以先不導入 Cloud WAF,但保留第 14 章架構 B 的彈性。

元件與位址(範例環境):mx01 10.0.30.10、gw01 10.0.30.11、gw02 10.0.30.12,同屬 Gateway Group GG-Shop。

三、步驟二:選部署模式與 HA (第 4 章、第 5 章)

決策過程:一題一題刪去

問題答案結論
要能阻擋並回錯誤頁嗎?要排除 Sniffing(只能送 TCP reset)
要檢查 TLS 1.3 / ECDHE 流量嗎?要排除 Sniffing 與純 Bridge(只能解 TLS 1.2 靜態 RSA)
剩下的選項Reverse Proxy(NGRP)或 ABR兩者都支援 TLS 1.3
未來要接 API Security Anywhere?可能NGRP、ABR 都支援(第 11 章)
是否在意 v16 路線?是v16.0 只支援 NGRP / ABR,選這兩者升級路線最順
平台是 VM是VM 只支援 Fail Close,HA 要靠第二台 Gateway

本案決定

GG-Shop 採 Reverse Proxy(NGRP),gw01 / gw02 以 VRRP 做冗餘。VRRP 是 Reverse Proxy 的冗餘方式;網路 HA 的 STP / IMPVHA 只適用 Bridge(第 5 章)。

放在 LB 前面還是後面

舊簡報 p.43–44 的觀念仍適用(第 5 章)。本案把 WAF 放在 LB 前面:

  • WAF 在 LB 前:Server Group 的伺服器只需填 LB VIP 10.0.10.20;擴充 web 節點時 WAF 不用改。
  • 代價:WAF 看到的是單一後端;LB 的健康檢查與 session 黏著仍由 LB 負責。
  • 若 LB 也要看到真實用戶端 IP,要規劃 X-Forwarded-For 類 header 的處理(Forwarded Connections,第 7 章)。

選型(第 5 章):依尖峰 TLS 交易量與吞吐選 V2500 或 V4500;官方未公布 V4500 吞吐數字,要用實際流量壓測確認。

四、步驟三、四:安裝註冊與 Site Tree (第 6 章、第 7 章)

步驟三:安裝與註冊

  1. 1在 vCenter 部署 MX 與 Gateway 的 OVF(MX 與 GW 必須分開 VM)。
  2. 2以 impcli admin 登入,第一次登入改密碼;依首次設定精靈設定管理 IP、DNS、NTP(第 6 章、第 13 章)。
  3. 3在 gw01、gw02 用 impcfg 設定 Gateway 工作模式並註冊到 mx01,S 存檔、A 套用。
  4. 4登入 https://10.0.30.10:8083,匯入授權、執行 ADC 更新。
  5. 5確認兩台 Gateway 都出現在 MX、屬於 GG-Shop,Gateway Mode 為 Reverse Proxy。

驗收點

MX 看到兩台 Gateway 上線;impctl status 正常;ADC 內容為最新版本。

步驟四:Site Tree 與 Web Service

示意畫面:部分欄位名稱待實機確認,版面、按鈕位置與配色以實機為準。
  1. 1建 Server Group SG-Shop,伺服器填 LB VIP 10.0.10.20。
  2. 2建 Web Service HTTPS-Shop,port 443;匯入 shop.example.com 的憑證與私鑰。
  3. 3在 Global Objects 的 TLS Settings 建立只允許 TLS 1.2 / 1.3 的設定並套用(v14.4 起 cipher 與協定集中在此)。
  4. 4SNI 在 service 的 Reverse Proxy 頁設定(v14.3 起)。
  • 設定 Error Page,讓被擋的使用者看到含事件編號的友善頁面,方便客服回報。
  • 建 Web Application shop(預設)與 member。拆分理由:會員區有登入、個資、訂單參數,安全需求和商品瀏覽不同(第 7 章拆分原則)。
  • 第二階段:api.example.com 另建 Server Group(伺服器 10.0.10.31)與對應 Web Service、Application,名稱依公司命名規則(本例不展開)。

驗收點

從管理者電腦連 https://shop.example.com(hosts 暫指 Gateway VIP)可正常瀏覽;MX 上 shop 與 member 都開始出現流量。

五、步驟五到七:學習、轉保護、情資與 Bot

步驟五:學習期 (第 8 章、第 11 章)

  1. 1確認 shop、member 的 Dynamic Profiling 在 Learning 狀態。
  2. 2設定 Learning Exceptions:內部測試機、弱點掃描器、監控探針的 IP 不納入學習。
  3. 3啟用 Web Application User Tracking:登入 POST /member/login,成功 302 導向 /member/home(第 11 章),用測試帳號驗證成功、失敗各一次。
  4. 4啟用 Data Masking:password、cvv、信用卡號字典、自訂身分證字號字典(第 11 章)。
  5. 5學習期涵蓋完整業務週期(至少包含一次促銷或月結等尖峰),期間每天看 Web Profile 是否學到異常參數。
  6. 6開發團隊若在學習期上新功能,記下 URL,學習期結束前確認已學到。

驗收點

主要 URL 已從 Learning 轉為 Protect;Profile 中沒有掃描器或攻擊性參數值。

步驟六:轉保護 (第 9 章)

  1. 1檢視 Web Service 層的 HTTP Protocol Validation、Signatures 與 Correlated Validation 政策,確認套用到 HTTPS-Shop。
  2. 2先告警、後阻擋:第一週政策只告警,每天依第 12 章流程分類告警,誤報回到 Profile 或政策調整。
  3. 3誤報收斂後,高信心政策(協定違規、簽章高嚴重度、Correlation 命中)改為阻擋。
  4. 4建立 Action Set:阻擋 + 送 Splunk(步驟八);高風險另加 IP Block(Trusted IPs 填管理網段 10.0.30.0/24 與合作夥伴固定 IP)。
  5. 5開啟 ADC 自動更新排程;訂閱 Emergency Feed,重大事件時手動啟用對應政策(Emergency Feed 政策預設停用)。

驗收點

用測試字串打 /member/orders?id= 會被阻擋並看到錯誤頁;正常會員流程(登入、下單、查訂單)全數通過。

步驟七:威脅情資與 Bot (第 10 章)

  1. 1啟用 Threat Intelligence Services 的 Reputation 類別:Malicious IPs、Anonymous Proxies、TOR IPs 等,先告警觀察一週。
  2. 2評估 Advanced Bot Protection:需 MX / GW v14.7 以上與 ABP 授權,GW 能經 443 連 *.imperva.com、*.impervaabp.net、*.distil.ninja。
  3. 3會員登入頁特別留意撞庫(credential stuffing):搭配 User Tracking 的登入失敗資訊,必要時以 User Block 處置(第 11、12 章)。

驗收點

情資告警出現在 MX;合法搜尋引擎與監控探針沒被誤擋。

六、步驟八、九:告警送 Splunk 與交接維運

步驟八:告警送 Splunk (第 12 章)

  1. 1建 Action Set AS-Splunk-GW,Action Interface 選「Gateway Log - Security Event - System Log (syslog) - CEF Format (Extended)」,Protocol TCP、Primary Host 10.0.30.50、Port 514,Message 以預設 Splunk 範本為基礎。
  2. 2在步驟六的安全政策 Followed Action 加入此 Action Set。
  3. 3系統事件(Gateway 斷線等)另以 MX 的 Server System Log 系統事件 Action Interface 送出。
  4. 4若已購買 Attack Analytics,依第 12 章開啟匯出。

驗收點

觸發一筆測試違規,Splunk 在一分鐘內收到,違規 ID 能對回 MX。

步驟九:交接維運 (第 13 章)

  1. 1執行第一次 full_expimp.sh 完整匯出,備份檔與報表目錄複製到備份主機。
  2. 2建立 REST API 專用帳號(最小權限),交付自動化腳本(第 12 章)。
  3. 3決定是否啟用 Sealed 模式;啟用的話把解封密碼存入密碼保管系統,不要用 seal --strict。啟用 Sealed 時 admin 不能切 root,例行匯出改用 impcli 的 export-local / export-remote(確切語法待實機確認)。
  4. 4例行工作排程:每週匯出(未啟用 Sealed 用 full_expimp.sh;啟用 Sealed 改用 export-local / export-remote)、root 密碼 90 天更換、ADC 更新檢查、每月檢視 EOS 表。
  5. 5交付文件:拓撲、防火牆規則、Site Tree、政策與 Action Set 清單、開案資訊範本(第 13 章)。

提醒

八、常見踩坑

為了「不改網路」選 Sniffing

TLS 1.3 流量完全看不到,上線後才發現沒有告警。

學習期太短

沒涵蓋月結或促銷,尖峰當天大量誤報,被迫關政策。

Server Group 填 web01 / web02 實體 IP

WAF 在 LB 前時,流量目的是 LB VIP,填錯就整批沒檢查。

Trusted IPs 沒填管理網段

管理者測試觸發 IP Block,把自己鎖在外面。

只測阻擋,沒測正常流程

上線後才發現結帳流程某個參數被擋。

沒有回退方案

WAF 出問題時不知道怎麼繞過,只能等排障。
