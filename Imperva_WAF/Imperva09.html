講師導言

上一章的 Dynamic Profiling 負責抓「偏離正常」的請求;這一章的其他政策負責兩件事:已知攻擊(協定驗證、簽章、關聯分析)和你自己定的規則(自訂政策)。 每條政策都由四個零件組成:套用對象(Apply To)、比對條件、動作(Action)和後續動作(Followed Action)。 最後我們還會走一遍「從一條告警走到調整政策」的處理流程,這是上線後最常用到的功夫。

Goals 本章學習目標

  • 說出政策的四個零件,以及 Basic 與 Additional 兩種類別的差別
  • 依 Server Group、Web Service、Web Application 三個層級,找到對應的政策類型
  • 知道簽章政策的內容從哪來,以及 Emergency Feed 出廠停用,要啟用服務並套用政策才會生效
  • 分辨 Action、Action Set、Followed Action 與 Action Interface
  • 建立一條自訂政策的範例,並依「告警 → 判斷 → 修正」的流程處理誤報

承接第 8 章(Dynamic Profiling),並為第 10 章(威脅情資與反自動化)打底。

一、政策的組成與兩種類別

用大樓警衛來想

  • Apply To 像「這位警衛站哪一層樓」。
  • 比對條件 像「看到什麼樣子的人要注意」。
  • Action 像「當場怎麼處理」,Followed Action 像「事後還要通報誰」。

三、簽章、ADC 與 Emergency Feed

簽章政策(HTTP Protocol Signatures、Web Application Signatures、Stream Signature)的內容來自 ADC 內容更新(第 6 章 6.6),約每兩週一次。更新後部分內容要 Apply Settings 才生效。

Emergency Feed Services:重大漏洞的緊急簽章

ADC 正式內容製作通常要三天以上,而且難以回收。遇到重大漏洞時,Imperva 先經 Threat Intelligence 推送緊急簽章,等正式 ADC 內容出來再取代。

  • 簽章放在專用的預定義字典,由 Threat Intelligence 週期性更新。
  • 對應的預建 ADC custom policy 在載入 ADC 內容時建立,出廠為停用。
  • 要生效必須同時做到兩件事:啟用 Emergency Feed 服務,並把政策套用到 site / server group / service / application。
Emergency Feed 政策範圍
Emergency - Detection只偵測
Emergency - Blocking GET requests阻擋 GET
Emergency - Blocking POST requests阻擋 POST
Emergency - Blocking General requests阻擋一般請求
Emergency - Blocking Authenticated Sessions阻擋已驗證 session 中的請求

建議作法

平時把 Emergency - Detection 套到全部站台;重大漏洞公告時觀察告警,確認無誤報後,再套對應的 Blocking 政策。

啟用 Emergency Feed 服務的 GUI 位置【待實機確認】。

四、HTTP Protocol Validation 與 Correlation

HTTP Protocol Validation:先擋掉畸形請求

這條政策依 RFC 檢查 HTTP 本身:畸形請求、異常 header、編碼規避等。它在 service 層,profile 還沒學好之前就能擋掉大量掃描工具與規避手法。調校重點:

  • 老舊或自製的 client(IoT、舊版 App)常有不合 RFC 的 header,先在 Simulation 觀察。
  • 例外限定在特定 URL 或來源,不要整條關掉【待實機確認:各違規子項的開關與例外欄位】。

【15.5】新功能

Patch 20 新增 Ghost Bits 編碼正規化,處理以非標準編碼規避檢查的手法(第 12 章另有新功能整理)。

Correlation:確認是攻擊再阻擋

舊版的核心觀念仍然成立:單一跡象不足以判定攻擊時,把多層、多時間點的偵測結果交給關聯引擎,以多個條件組合判定「確定的攻擊」,降低阻擋的誤報。

現行名稱層級說明
Web Service Correlated ValidationWeb Service防多階段 Web 應用攻擊
Web Correlation Policy—關聯規則政策,REST API 也提供 CRUD

舊簡報列出的 ADC 預建關聯規則(XSS、Forceful Browsing、SQL injection、Session Attribute Changes、相同回應碼過多,跨時間、跨政策),在現行 ADC 內容中的實際規則名稱與清單【待實機確認】。

六、Action、Action Set 與 Followed Action

四個名詞很容易搞混,先看圖:政策命中後,Action 馬上反應;Followed Action 掛的是一個 Action Set,裡面由一個或多個 Action Interface 組成。

名詞意義
Action政策命中時的立即反應,例如阻擋來源連線(Web client 可同時給錯誤頁)。Action 不屬於 Action Set,而是在政策中設定
Action Set一個或多個 action interface 的組合,作為 followed action 掛到物件上;系統內建若干預定義 Action Set
Followed Action已掛到某物件(政策、系統事件、報表、排程工作)上的 Action Set,條件成立時執行。例:除了立即阻擋 session 劫持,再封鎖該來源 30 分鐘
Action Interface執行方式,如寄 e-mail、執行 shell 指令、送 syslog;另支援 CEF / ArcSight、Splunk placeholder(第 12 章)

七、從告警到調整政策

收到告警別急著關政策。照下面六步走,通常可以用最小的改動解決問題。

  1. 1看告警:在 MX 的告警檢視找到該事件,記下政策名稱、violation 類型、URL、參數、來源 IP【待實機確認:告警檢視的 GUI 路徑,第 12 章會整理】。
  2. 2判斷真偽:對照請求內容。看到 SQL 語法、路徑穿越、已知掃描器 User-Agent 是真攻擊;正常業務參數則是誤報。
  3. 3找出是哪一層判定:Profile violation 看第 8 章 8.7;簽章看第三節;協定驗證看第四節;自訂政策則檢查條件是否寫太寬。
  4. 4最小範圍修正:優先修 profile 或縮小政策的 Apply To;不得已才加例外,例外限定 URL + 參數 + 來源。
  5. 5紀錄:工單記錄修改內容;系統事件也會留下誰改了什麼(第 12 章)。
  6. 6觀察 24 到 72 小時:確認同類告警消失、沒有新的漏報【推論:實務建議】。

八、動手玩:政策判定流程模擬器

選一個範例請求,再調整政策的套用狀態、模式、Action 與 Followed Action,看看它經過哪些政策層、最後怎麼處置。

簡化示意:依官方檢查順序,先 Server Group、再 Service、最後 Application;本模擬假設每個請求最多命中一條政策;Simulation 模式視為「只觀察、不阻擋」。
