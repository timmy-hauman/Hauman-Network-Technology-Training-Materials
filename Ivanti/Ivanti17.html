Ivanti Connect Secure SSL VPN 實戰課程

單元 17:安全公告與加固

講師導言

SSL VPN 閘道直接面對 Internet,又握有進入內網的鑰匙,所以是攻擊者最想拿下的設備。2024 年以來,Connect Secure 多次出現「不用登入就能遠端執行程式」的漏洞,而且常常在修補推出之前就已經被拿來攻擊。 這一章不要你背 CVE 編號,而是學會三件事:怎麼查自己的版本有沒有中、懷疑被入侵時依什麼順序處理、平常要把哪十件事做好。

資料時效

本章的漏洞、版本與日期,資料以 2026-10-31 查證為準,上課前請重查 Ivanti 最新安全公告。這一章的內容會持續變動,公告一更新,下面的對照表與工具結果就要跟著檢查。

Goals 本章學習目標

  • 說明為什麼 SSL VPN 閘道是攻擊者的首要目標,以及「0-day」是什麼意思
  • 看懂近年重大漏洞表,並用版本對照工具找出自己的版本受哪些漏洞影響
  • 說出 Integrity Checker Tool(ICT)能做什麼、不能做什麼,以及 Ivanti 與 CISA / Volexity 的說法有什麼不同
  • 依順序說出疑似遭入侵時的五個處置步驟
  • 用十項加固檢查清單檢查自己的設備

本章是觀念與流程章,沒有對應的設定畫面。升級的操作方法在第 16 章,本章講「為什麼要升、什麼時候要升」。

一、為什麼要獨立一章

用大樓大門來想

  • SSL VPN 閘道像公司大樓面向馬路的大門,誰都看得到,門後又放著通往每一層樓的鑰匙。
  • 0-day 像是鎖廠還沒發現鎖有缺陷,小偷就已經學會開了。等廠商推出新鎖(修補),門可能早就被開過。
  • 修補只是換新鎖;被開過的門,還要檢查有沒有留下複製的鑰匙,這就是「重建設備、換掉所有密碼」的原因。

先記住兩個詞:CVE(漏洞的公開編號)和 0-day(修補還沒推出,攻擊就已經發生)。其他名詞看下面的名詞小卡。

三份舊版教材都沒有這部分內容。但設備一旦被入侵,攻擊者拿到的不只是一台 VPN,而是進入內網的入口,所以新版教材必須獨立補上這一章。

名詞小卡

CVE

資安漏洞的公開編號,格式是 CVE-年份-流水號。看到編號,就能到公告裡查影響哪些版本、修補版本是哪一版。

0-day

廠商還沒推出修補,攻擊就已經發生的漏洞。「當時已完全修補」的設備也擋不住,所以不能只靠更新。

KEV

美國 CISA 公布的「已知遭利用漏洞清單」。下面漏洞表的「已遭利用」一欄,就是依這份清單。

未驗證遠端執行

攻擊者不用登入,就能從網路上讓設備執行他指定的指令。對放在 Internet 邊界的 VPN 來說,這是最危險的一類。

ICT

Integrity Checker Tool(完整性檢查工具)。把設備上的檔案和預期的快照比對,找出被新增或修改的檔案。第三節會講它的限制。

IoC

入侵指標(Indicator of Compromise)。入侵留下的特徵,資安團隊會拿它來比對設備上有沒有出現同樣的跡象。

教學重點

  • CVE-2025-22457 的受害者包括已終止支援的 9.1x 設備,而 9.1x 不會有修補。這是「為什麼不能繼續用舊版」最直接的例子。

三、Integrity Checker Tool(ICT):用途與限制

Integrity Checker Tool(ICT)把設備上的檔案和預期的快照(snapshot)比對,找出被新增或修改的檔案。

用現場照片來想

ICT 像保全替機房拍的「現場照片」,和標準照片一比,就看得出多了一個箱子、少了一個櫃子(檔案被新增或修改)。但如果小偷拍照前就把痕跡清乾淨,或是只把東西放在腦子裡、沒有留在房間(惡意指令只在記憶體裡跑),照片就比對不出來。

ICT 能做什麼

  • 分為內建(internal)與外部(external)兩種。官方說明與下載見 Ivanti KB44755。
  • 外部 ICT 會產生可自行檢視的快照;2024-05 之後的版本執行外部掃描,不再需要重開機。
  • 22.7R2.8 起,外部 ICT 可以用 REST API 觸發掃描並下載結果,同一時間只能跑一個掃描。

ICT 的限制:兩種說法並陳

Ivanti 的說法

  • 官方自己寫明:它只是某個時間點的快照。攻擊者若事先清除痕跡,就偵測不到。
  • 它不掃描惡意程式,也不比對入侵指標(IoC)。
  • 曾有攻擊者試圖竄改內建 ICT,所以官方建議跑外部 ICT,並搭配持續監控。
  • 針對 2026-10 這一波,Ivanti 的公告仍建議定期執行 ICT。

CISA 與 Volexity 的說法

  • 針對 2026-10 這一波,兩者都指出 ICT 可能偵測不到。
  • 原因是惡意指令是在記憶體裡執行,沒有留下 ICT 比對得出來的檔案變動。

教學時兩種說法都要講

不要只講其中一邊。實務上可以定期跑外部 ICT,但它沒發現異常,不能當成「設備沒事」的證明。這也是第五節清單把「定期執行外部 ICT,但不要只靠 ICT」寫在一起的原因。

四、疑似遭入侵的處置流程

發現可疑跡象時,最怕的是慌張之下直接重置、換密碼,結果證據全沒了,也不知道攻擊者拿走了什麼。下面是整理自 Ivanti 與 CISA 公告的五個步驟,順序不能顛倒。

每一步在做什麼

步驟做法為什麼
① 保全證據先通報資安單位、隔離設備、保存鑑識映像,再動手修復重置之後證據就沒了,無法回頭查攻擊者做了什麼
② 重建設備實體設備做 Factory Reset;虛擬機與雲端不要 Factory Reset,改部署全新的映像公告的指示:兩種環境的重建方式不同
③ 安裝修補安裝最新的修補版本後,再還原設定先換上已修補的版本,再放回設定,設備才不會帶著漏洞重新上線
④ 更換密碼與憑證管理員密碼、API 金鑰、本機使用者與服務帳號密碼;網域帳號重設兩次,並撤銷 Kerberos 票證與雲端 token;撤銷並重新簽發設備上儲存的憑證,重設授權伺服器的連線帳密設備上的帳密與憑證都可能已被攻擊者看過
⑤ 持續監控重建完成後仍要持續監控,不要以為做完前四步就結束CISA 在 2024 年曾指出,攻擊者可能取得能撐過 Factory Reset 的持久性

五、加固檢查清單:十個重點

加固(hardening)就是把設備的設定調到最安全的狀態,讓攻擊者能下手的地方變少。下面十項是平常就要做的事,第六節有可以勾選的版本。

項目做法白話原因
版本維持在支援中的版本線,訂閱 Ivanti 安全公告,修補一推出就排程更新第二節的漏洞都有被實際利用,有些還在修補推出前就被利用
舊設備已終止支援的 PSA、9.1Rx 設備盡快汰換9.1x 不會有修補,CVE-2025-22457 就是例子
管理介面只從 Internal / Management port 管理,Admin Realm 限制來源 IP,管理員加第二因素管理介面權限最大,只讓管理網段連得到,再加第二因素,密碼被偷也進不去
TLS只開 TLS 1.2 / 1.3,啟用 OCSP / CRL舊版協定的安全性較差,只留現行版本;OCSP / CRL 讓設備能查出已被撤銷的憑證
憑證到期前 30–60 天更新,SAN 涵蓋所有網址憑證過期,使用者會看到警告或連不上;網址沒列在 SAN,瀏覽器會說憑證不符
驗證LDAP 用 LDAPS,查詢帳號用唯讀服務帳號,使用者一律雙因素明文 LDAP 的帳密在網路上看得到;唯讀帳號被偷也改不了目錄;雙因素讓只偷到密碼的人進不來
存取控制VPN Access Control 最小權限,預設全部走隧道只放行必要的 IP、埠與協定,帳號被盜用時能碰到的範圍也有限(第 9 章)
設定檔匯出的設定檔加密碼保護並妥善保管設定檔含有設備的完整設定,外流就等於把內部細節交給別人
日誌Syslog 送到 SIEM(TCP / TLS 並開 Fault tolerance),SNMP 監控暴力登入告警日誌另存在別台機器,設備出事時紀錄還在;暴力登入告警能及早發現有人在猜密碼
完整性定期執行外部 ICT,但不要只靠 ICTICT 有盲點(第三節),只能當其中一道防線

【25.x】25.1.3.0 已收緊的預設值

  • IKEv2 預設 AES-256 / SHA-256 / DH 2048 以上。
  • SAML 2.0 簽章驗證預設啟用。
  • 新建的 LDAP 伺服器預設驗證憑證。
  • Session 結束時刪除所有 cookie。
  • 暫時移除自訂登入頁上傳。

七、常見踩坑與版本差異

ICT 沒報異常,就當作設備沒事

ICT 只是某個時間點的快照,不掃惡意程式、不比對 IoC;2026-10 這一波還可能因為惡意指令在記憶體執行而偵測不到。ICT 乾淨,只代表「比對得出來的部分」沒問題。

以為裝到最新版就不會被入侵

2026-10 這一波,10 月第一週已有「當時已完全修補」的設備被入侵,因為是 0-day。所以更新之外,還要靠加固清單縮小攻擊面、靠日誌與監控及早發現。

虛擬機被入侵,卻直接 Factory Reset

虛擬機與雲端環境不要 Factory Reset,要部署全新的映像。而且重建之前要先保全證據,不要一發現就急著重置。

換密碼換得不夠徹底

網域帳號要重設兩次,並撤銷 Kerberos 票證與雲端 token;設備上儲存的憑證要撤銷並重新簽發,連授權伺服器的連線帳密也要重設。只換管理員密碼是不夠的。

9.1x 設備「先放著,等修補」

9.1x 已終止支援,CVE-2025-22457 不會有修補。唯一的處理方式是汰換成支援中的版本線。

版本差異

  • 9.1x 已終止支援;22.x 是過渡版本,2027-01-31 終止支援;新版基準是 25.1.x。
  • CVE-2026-104935 的影響版本註明「22.7 不受影響」;但 CVE-2026-111357、CVE-2026-118527 的影響版本沒有列出 22.7,是否受影響要查 Ivanti 公告。所以第六節對照表對 22.7R2.6 以後的 22.7 只顯示「待確認」,不會判定為安全。2025 年以前的表列漏洞已在 22.7R2.6 修補。
  • ICT 的 REST API 觸發掃描,從 22.7R2.8 起提供;外部掃描不用重開機,則是 2024-05 之後的版本。
