單元 2:核心觀念:存取管理模型

講師導言

這一章是全書的骨架。後面大部分章節,都是在設定下面五個元件裡的其中一個。三份舊版教材講的都是同一套模型,到 25.1 仍然成立,官方的選單位置也沒有變。 先把「五個元件各管什麼」和「一次登入會經過哪 12 個關卡」記起來,之後遇到「使用者說登入了卻打不開網頁」,你就知道該往哪一關去查。

Goals 本章學習目標

  • 說出五個元件各自回答什麼問題,以及它們在管理介面的選單位置
  • 說明元件之間「多對多」的關係
  • 依 12 個關卡的順序,判斷登入失敗卡在哪一關
  • 分辨「登入成功」和「能存取資源」是兩回事
  • 依相依關係,決定元件的設定順序

一、五個元件各管什麼

用公司大樓來想

  • Sign-in Policy 像大樓的各個入口(正門、後門、訪客門):你從哪個門進來,決定你看到哪一種櫃台。
  • User Realm 像入口後面的櫃台通道:員工走員工通道、訪客走訪客櫃台。
  • Auth Server 像人事資料庫:櫃台拿你的識別證去查真假。
  • User Role 像門禁卡的等級:一般卡只能進辦公區。
  • Resource Policy 像每扇房門上的名單:卡的等級夠了,名單上還要有你才打得開。

一句話記住:Realm 是「一群使用者」,Role 是「一組權限」。 使用者從網址進來,依序經過下面這幾個元件:

五個元件對照表

元件回答的問題選單位置
Auth Server帳號密碼對不對?Authentication > Auth. Servers
User Realm這群人用哪台伺服器驗證?能拿到哪些角色?Users > User Realms
User Role拿到這個角色,能用哪些功能?Users > User Roles
Resource Profile / Resource Policy具體能連到哪些資源?Users > Resource Profiles、Users > Resource Policies
Sign-in Policy從哪個網址進來、看到哪個登入頁、能選哪些 Realm?Authentication > Signing In > Sign-in Policies

多對多的關係

一個 Sign-in Policy 可以開放多個 Realm。

一個 Realm 可以對應多個 Role。

一個 Role 可以被多個 Realm 使用。

一條 Resource Policy 可以套用到多個 Role。

二、登入評估流程:12 個關卡

舊版簡報把登入過程畫成 12 步。官方文件從 9.1R17、22.8R2 到 25.1R1 都寫成 13 項,順序完全一樣:前 12 項就是舊簡報的 12 步,第 13 項是新增的附註。

#系統做什麼失敗時
1使用者在瀏覽器輸入網址—
2依序比對 Sign-in Policy,先比管理員網址、再比使用者網址,直到主機名稱符合找不到對應頁面
3執行登入前限制(pre-authentication),例如來源 IP、瀏覽器、Host Checker。通過後顯示登入頁,有多個 Realm 時讓使用者選直接拒絕
4使用者送出帳密,系統執行登入後限制(post-authentication),例如密碼規則拒絕
5帳密送到 Realm 指定的 Auth Server 驗證;可選擇向 LDAP 查群組與屬性;有第二驗證伺服器時再驗一次登入失敗
6套用 Realm 的 Role Mapping 規則,算出「可用角色」沒有任何角色時登入失敗
7檢查每個可用角色的 Restrictions,只留下符合條件的角色被過濾掉的角色不生效
8建立 Session:多個角色合併(permissive merge),或讓使用者自選—
9使用者要求某個資源時,先確認 Session 角色有啟用對應的存取功能拒絕
10由上而下比對 Resource Profile / Policy,第一條符合的規則決定允許或拒絕拒絕
11系統把請求轉給目標伺服器(需要時代入帳密做單一登入),再把結果傳回—
12使用者存取資源。登出、逾時或動態政策重新評估不通過時,Session 結束—
13附註:Realm、Role、Role Mapping 規則可以比對憑證的 Enhanced Key Usage(EKU)—

教學重點

「登入成功」和「能存取資源」是兩回事。前 8 項是登入,第 9 項以後才是存取資源。使用者說「登入了但打不開網頁」,通常卡在第 9 或第 10 項(表中粉紅色的兩列),不是帳密問題。

三、設定順序與相依關係

兩份舊版文件與官方建議的順序不同,但都能做出來,差別只在相依關係:後面的元件要「選」前面的元件,所以被選的要先存在。

來源順序
舊版教材(約 2006 年的安裝流程)Role → Resource → Auth Server → Realm → Sign-in Policy
舊版設定手冊(2009–2010 年)初始化 → Auth Server → Role → Realm → Resource Policy → Sign-in Policy → 端點安全(選配)
Ivanti 官方系統與網路 → 日期時間 → 升級到最新 Service Package → 安裝授權 → 規劃測試情境 → Auth Server → User Role → User Realm → Sign-in Policy → Resource Profile
  • Realm 要選 Auth Server,做 Role Mapping 時要選 Role,所以 Auth Server 與 Role 要先存在。
  • Sign-in Policy 要選 Realm,所以 Realm 要先存在。
  • Resource Profile 要指派給 Role,所以 Role 要先存在。

本課程大致依官方順序編排(升級 Service Package 放到第 16 章);第 18 章的實作則完全照官方順序。

  1. 1Authentication > Auth. Servers:建立驗證伺服器(例如 AD-LDAPS),回答「帳號密碼對不對」。最先建。
  2. 2Users > User Roles:建立角色,決定拿到這個角色能用哪些功能。也要在 Realm 之前建好。
  3. 3Users > User Realms:建立 Realm,選 Auth Server,再用 Role Mapping 把使用者對應到角色。
  4. 4Authentication > Signing In > Sign-in Policies:決定哪個網址進來、看到哪個登入頁、能選哪些 Realm。
  5. 5Users > Resource Profiles 與 Users > Resource Policies:決定具體能連哪些網站、檔案、網段,並指派給角色。

Resource Profile 與 Resource Policy 的差別,在第 8 章說明。

六、常見踩坑與版本差異

把「登入成功」當成「一切正常」

使用者說「登入了但打不開網頁」,別先去重設密碼。登入成功只代表前 8 項過關,接下來要查第 9 項(角色有沒有啟用對應的存取功能)和第 10 項(Resource Policy 由上而下,第一條符合的規則是不是 Deny)。

設定順序做反

先去建 Realm,才發現下拉選單裡沒有想要的 Auth Server,或沒有角色可以指派。記得:Auth Server 與 Role 先存在,才能建 Realm;Realm 先存在,才能建 Sign-in Policy。

帳密正確卻登入失敗

第 6 項算不出任何角色時,即使帳密對了也會登入失敗。這時要檢查 Realm 的 Role Mapping 規則有沒有命中(第 7 章)。

版本差異

  • 登入評估流程的 13 項,從 9.1R17、22.8R2 到 25.1R1 的官方文件都寫成同樣的順序。
  • 五個元件的官方選單位置沒有變,舊版教材的觀念可以直接沿用。
  • 舊版簡報的 12 步,對應現行文件的前 12 項;第 13 項(憑證 EKU 的附註)是新增的。
